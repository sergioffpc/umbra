# Sessions launched from the operator's machine

> **Superseded by [ADR 0021](0021-plug-and-play-workers-in-a-named-cluster.md).** There is no launch script: Workers run permanently and join any Render Job announced in their Cluster. The Coordinator still runs on the operator's machine. ADR 0021 restates the rules that carry over: the start-up order, the absence of any wait for Workers, the heartbeat from `Welcome` and the bounded restart, which the Coordinator now counts.

The Coordinator always runs on the operator's machine, as a local process of `scripts/workers up`. A Session then starts in a fixed order: build, parse, listen, and only then the Workers. Each Worker Slot is restarted automatically within a bound. Decided in [Session start-up and Worker joining](https://github.com/sergioffpc/umbra/issues/59). This amends [ADR 0012](0012-per-cpu-binaries-locked-to-one-commit.md), which let the Coordinator run on any machine with the P620 as default.

- **Coordinator on the operator's machine.** The operator's machine is wherever `scripts/workers up` runs. The script has no `--coordinator <host>` option. The Coordinator and its optional local Worker run there without SSH. It reads the Scene File and its assets from the local disk and writes the image and the Render Job Report locally, so nothing is copied to or from a remote Coordinator. The operator who wants the Coordinator on the P620 runs the script there. That is the documented choice for large Scenes, because the P620 is the strongest machine.
- **Start-up order.** The script builds (`--ref`) or pulls (`--version`) on every host in parallel, including the local one, and aborts on any failure. It then starts the Coordinator. The Coordinator parses the Scene File and builds the Scene and the Reproduction Record before it opens its UDP port. On an invalid Scene File it exits non-zero and no Worker is ever started, so no close code is needed for a failed parse. Once it listens, it prints a readiness line on stderr. The script waits for that line before it starts the Workers over SSH, and passes each one the operator's address as that host sees it (`$SSH_CLIENT`).
- **No retry of the initial connection.** A Worker is started only once the Coordinator listens. If its first connection fails, it logs the error and exits non-zero, as for any other loss of the Coordinator ([arc42 §8.13](../architecture/08-crosscutting-concepts.md#813-wire-protocol)).
- **No wait for Workers.** Assignment answers `RequestWork`, so the Render Job starts with the first ready Worker, local or remote. There is no "wait for N Workers" rule.
- **Bounded automatic restart.** The script restarts a Worker Slot (one host and NUMA node, [ADR 0017](0017-one-worker-per-numa-node.md)) whose Worker process or SSH session ends abnormally: `Fatal`, a crash, an OOM kill, a lost Coordinator, or a lost SSH session after a reboot or a network drop. It does not restart after `FINISHED`, `JOB_CANCELLED`, `REJECTED` or `PROTOCOL_ERROR`, which the Worker reports through distinct exit codes. Restarts reuse the binary already built or pulled, and the new process joins as a new Worker that receives the whole Scene again ([ADR 0016](0016-one-render-job-per-quic-connection.md)). A slot gets at most three consecutive restarts, after 2 s, 10 s and 30 s. Its counter resets when a restarted Worker delivers its first Work Result. After the third failure the slot gives up and the script logs why. Hosts outside the starting host list cannot join a running Session.
- **No Workers left.** When every slot has given up and there is no local Worker, the status line shows `waiting: no Workers`, and the Render Job waits for the operator's Ctrl-C ([ADR 0009](0009-pull-based-pass-major-scheduling.md)).
- **Heartbeat from `Welcome`.** A Worker opens its heartbeat stream right after `Welcome`, from a task of the network runtime that is independent of Scene reception and BVH construction. The 5 s death rule therefore covers a loading Worker without false positives. While loading, a heartbeat carries loading progress (Scene bytes received, and the phase, `receiving` or `building BVH`) instead of per-Work-Unit Pixel Samples. A Worker whose loading progress stops for the stall time is shown as `stalled`, never declared dead. It holds no Work Units, so it blocks nothing.

## Considered options

- **A Coordinator on any host, with the Scene File's directory copied there by `rsync`**: rejected. It needs a scene cache on the Coordinator's host and a copy of the image back to the operator, and logging into the P620 gives the same placement without either.
- **The Scene File path read on the Coordinator's host**: rejected. The operator would keep scenes in sync by hand on every possible Coordinator.
- **Starting the Coordinator and the Workers together, with Workers retrying the connection**: rejected. It saves the parse time, but Workers then wait on a Scene that may fail to parse, and need a close code for it.
- **A heartbeat stream that starts with the first `RequestWork`**: rejected. A Worker that dies or hangs while loading would never be detected.
- **Manual join of a Worker with `scripts/workers join <host>`**: rejected in favour of the automatic restart. It needs the operator to notice the dead Worker, and adding hosts mid-Session was not a requirement.
- **Unbounded restart**: rejected. A crash that this Scene causes every time, such as a panic or an out-of-memory error, would loop and resend the Scene each time.

## Consequences

- The operator's machine must accept UDP on the Coordinator's port (7470) in its firewall.
- The Worker's exit codes become part of the contract between the Worker and `scripts/workers`. Their values were decided in [Closing connections: dead Workers and cancellation](https://github.com/sergioffpc/umbra/issues/60): the script restarts on any exit status except `0` (finished), `2` (invalid usage), `3` (refused: `Reject`, `PROTOCOL_ERROR`) and `130` (cancelled or stopped), listed in [arc42 §8.13](../architecture/08-crosscutting-concepts.md#813-wire-protocol).
- The Render Job Report counts restarts per Worker Slot.
