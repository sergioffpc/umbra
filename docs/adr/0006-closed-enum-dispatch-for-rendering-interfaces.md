# Closed enum dispatch for rendering interfaces

> **Amended on 2026-11-12, decided with the owner.** There are no image writers: `Image::write` takes the format from the path's extension through the `image` crate ([ADR 0020](0020-bit-identical-exr-final-image.md)). The other `dyn` seams below still apply.

Every pbrt-v4 base interface on the per-ray or per-Pixel-Sample path is dispatched through a closed Rust `enum` and an explicit `match`, never through `dyn Trait`. This covers Shape, Primitive (including the acceleration structure), Material, BxDF, Light, FloatTexture, SpectrumTexture, Medium, PhaseFunction, Sampler, Camera and Filter. It is the Rust counterpart of pbrt-v4's `TaggedPointer` and `Dispatch`. pbrt-v4 dropped virtual functions for the same reasons that apply here: a vtable holds CPU code addresses that mean nothing on a GPU, Rust GPU toolchains cannot compile dynamic dispatch, and an indirect call cannot be inlined ([pbrt-v4 CPU/GPU shared-code architecture](https://github.com/sergioffpc/umbra/issues/15)).

- **A trait per interface, an enum per set.** Each interface is a trait that carries the book's name and is the documented contract (`trait Shape`). Each concrete type keeps its pbrt-v4 name (`Sphere`, `DiffuseBxDF`, `ZSobolSampler`) and implements that trait. The enum that gathers them is named `<Interface>Kind` (`ShapeKind`, `BxDFKind`, `LightKind`, …) and also implements the trait with one hand-written `match` per method that delegates to the variant. pbrt-v4's own `LightType` (delta position, delta direction, area, infinite) keeps its name, and the doc comments of `LightType` and `LightKind` state the difference. Signatures elsewhere take the `*Kind` enum.
- **Hand-written dispatch.** The `match` arms are written out, not generated by `enum_dispatch` or a macro, so each one can be read, searched and stepped through. A local `macro_rules!` may replace them later if the boilerplate becomes a real cost, decided then.
- **Exhaustive matches.** A `match` on a `*Kind` enum lists every variant and never uses `_`, so adding a variant is a compile error at every place that must handle it. A lint enforces this in the rendering core.
- **Per-call dispatch even when the type is fixed.** Sampler, Camera and Filter have one variant per Render Job, but they are still matched on every call, as pbrt-v4's CPU path does; the branch is perfectly predicted. Hoisting the `match` out of the Pixel Sample loop into a monomorphised generic function is an aggressive optimisation: it needs a benchmark showing the gain, an isolated contract, and the per-call version as its test reference. Generics that are not interface dispatch (`Vector3<T>`, `Bounds3<T>`) are unrestricted.
- **`dyn Trait` only at coarse seams.** `dyn` is allowed only for code called at most once per Work Unit or outside rendering: the Integrator (`dyn Integrator`, since path, volpath, BDPT, MLT and SPPM differ widely and stay CPU-only in this form), the network transport, image writers, the parser's `ParserTarget`, and telemetry.
- **BxDFs by value.** A Material returns its BxDF as a `BxDFKind` value that lives on the stack inside the `BSDF`, with no scratch arena and no lifetime. A compile-time assertion bounds `size_of::<BxDFKind>()` to 256 bytes, so growing a variant past it is a deliberate change. `MixMaterial` chooses one of its materials stochastically before any BxDF is built, as in pbrt-v4, so there is no mixed BxDF.
- **Two texture enums, no `TextureEvaluator`.** `FloatTextureKind` and `SpectrumTextureKind` follow the book. pbrt-v4's `TextureEvaluator` exists only so the wavefront driver can sort materials by texture complexity, and it returns with that driver if one is ever built.

How the enums store their data and refer to one another (index handles into per-type arenas) is decided separately with the memory and allocation strategy.

## Considered options

- **`dyn Trait` everywhere**: rejected. It needs a `Box` per object, prevents inlining on the hottest paths, and puts vtables in data that a GPU port could not use.
- **Generics and monomorphisation as the main mechanism**: rejected. A Scene mixes Shapes, Materials and Lights of different types in one collection, which generics cannot hold, and monomorphising whole loops multiplies compile time and binary size.
- **`enum_dispatch` or a generated `match`**: rejected for now. It removes boilerplate but hides the dispatch, adds a proc-macro dependency and produces harder compile errors.
- **Enum named after the book, trait with an `Interface` suffix** (`Shape` / `ShapeInterface`): rejected in favour of keeping the book's name on the contract and marking the dispatch enum with `Kind`.
- **BxDFs in a per-thread scratch arena behind a handle**, as in pbrt-v4's CPU path: rejected. It adds an allocator, lifetimes on `BSDF` and a reset per Pixel Sample, for a smaller enum the stack does not need.

## Consequences

- The sets are closed. Adding a shape, material or light means a new variant and a new arm in every dispatching `match`, which the exhaustive-match lint points to.
- `enum` size is the largest variant. Variants with large payloads must stay small or move their data behind an index handle.
- rust-gpu cannot yet compile data-carrying enums, so whatever a GPU port shares must be plain handles, not the enums themselves. The GPU-readiness constraints take this up.
