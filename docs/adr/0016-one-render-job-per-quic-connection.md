# Wire protocol: one Render Job per QUIC connection, unverified TLS

The Coordinator and a Worker exchange exactly one Render Job over one QUIC connection, with no protocol version, no asset cache and no TLS certificate verification ([Wire protocol between Coordinator and Workers](https://github.com/sergioffpc/umbra/issues/47)). Workers are started per Session by `scripts/workers up` and exit when it ends ([arc42 §7.3](../architecture/07-deployment-view.md#73-deployment-and-launch)), every binary in a Render Job is built from the same commit ([ADR 0012](0012-per-cpu-binaries-locked-to-one-commit.md)), and hostile nodes are out of scope. Within those limits each of these choices removes a mechanism the protocol would otherwise need. The message set and the stream mapping are in [arc42 §8.13](../architecture/08-crosscutting-concepts.md#813-wire-protocol).

- **One Render Job per connection.** The Worker is the QUIC client and connects to the Coordinator's UDP port (7470 by default). The connection closes when the Render Job ends, and a second Render Job is a new Session. Messages carry no Render Job identifier.
- **No protocol version.** The handshake compares Build Identity commits. Two binaries on the same commit speak the same protocol, so a version number would add nothing, and any malformed or out-of-order message is a bug that closes the connection with `PROTOCOL_ERROR`.
- **Whole Scene on every connection, no cache.** The Coordinator streams the Scene structure and then every asset to each Worker, and the Worker checks each asset's content hash. Workers keep no state on disk between Sessions.
- **TLS only because QUIC requires it.** The Coordinator generates a self-signed certificate at start-up, and Workers accept any certificate. Mistakes of operation, such as a Worker reaching the Coordinator of another Session, are caught by the handshake instead: the Coordinator admits only a Worker that presents its Session identifier and its commit.

## Considered options

- **Several Render Jobs per connection**: rejected. It needs Render Job identifiers on every message, Scene unloading, and asset reuse between Render Jobs, for a Session lifetime that §7.3 does not have.
- **A content-addressed asset cache on each host**: rejected for now. It saves resending large assets when the same Scene is rendered repeatedly, but it adds persistent state, invalidation and disk usage to every host. On 1 GbE a 1 GB Scene costs about 9 s per Worker. If that is measured to matter, the cache is an aggressive optimisation with its own decision.
- **A pinned certificate fingerprint**, generated by the launch script and passed to Workers: rejected. It only protects against an impostor Coordinator, which is out of scope, and the Session identifier already catches honest mistakes.
- **A private CA with mutual TLS**: rejected as out of proportion to a trusted LAN.
- **A protocol version or compatibility negotiation**: rejected, as in ADR 0012.

The connection's close code is also how a Render Job ends for each side ([Closing connections: dead Workers and cancellation](https://github.com/sergioffpc/umbra/issues/60)): the Coordinator closes a Worker it declared dead by heartbeat with `WORKER_TIMED_OUT`, a Worker stopped by the operator closes with `WORKER_STOPPED`, and Ctrl-C on the Coordinator closes every connection with `JOB_CANCELLED`. No message announces any of them first.

## Consequences

- Traffic is encrypted but not authenticated. Anyone on the LAN who learns a Session identifier can join as a Worker or impersonate the Coordinator. This is acceptable only while hostile nodes stay out of scope.
- Large Scenes delay the start of every Render Job by their transfer time, and the Mac on Wi-Fi more so. The Render Job Report shows it as the Worker's loading phase.
- The Session identifier must be generated by `scripts/workers up` and passed to the Coordinator and to every Worker.
