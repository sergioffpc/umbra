# x86-64 only

Umbra builds and runs on x86-64 with the `x86-64-v3` baseline only: the Lenovo P620 and the Dell R630. Support for arm64 is dropped. Decided with the owner on 2026-11-09: arm64 was to stay only if it was nearly free, and it is not. This amends [ADR 0005](0005-chiseled-release-container-image.md), [ADR 0009](0009-pull-based-pass-major-scheduling.md), [ADR 0012](0012-per-cpu-binaries-locked-to-one-commit.md), [ADR 0014](0014-gpu-ready-no-std-rendering-core.md) and [ADR 0021](0021-plug-and-play-workers-in-a-named-cluster.md).

arm64 costs a second backend for every SIMD kernel, with NaN and rounding behaviour matched across two instruction sets, plus its own CI jobs and its own tuning. With 8-wide AVX2 kernels now open to the x86 machines, every one of them would also need a two-register NEON version. In return it would add a few cores to the 60 of the P620 and the R630.

- **One backend.** `umbra-math` has one backend for the `Vec4`/`Mask4` facade and the scalar primitives: x86-64 with SSE4.1, AVX2 and FMA. The NEON backend is removed. Any other target stops the build with a `compile_error!`. A GPU port adds its own backend ([ADR 0024](0024-a-gpu-backend-on-the-roadmap.md)). Code above `umbra-math` stays architecture-independent.
- **Two targets.** The P620 runs `znver2` and the R630 runs `broadwell` ([ADR 0012](0012-per-cpu-binaries-locked-to-one-commit.md)). The release image stays `linux/amd64` only ([ADR 0005](0005-chiseled-release-container-image.md)).
- **`umbra render` on a target machine.** The Coordinator still runs where the operator runs `umbra render` ([ADR 0021](0021-plug-and-play-workers-in-a-named-cluster.md)). That is the P620, the operator's workstation, or the R630.
- **The `no_std` check without a bare-metal target.** CI used to build the core crates for `aarch64-unknown-none`. `x86_64-unknown-none` cannot replace it: it is a soft-float target, and LLVM fails to compile the SSE and AVX code for it. Instead, the workspace has a member `ci/no-std-check/`: a `#![no_std]` library with its own `#[panic_handler]` that uses the seven core crates. If any of them, or any dependency, links `std`, the crate stops compiling with a duplicate `panic_impl` lang item (E0152). Every `cargo check`, `clippy`, `build` and `test` therefore runs the check, and CI needs no job of its own. Linking `alloc` needs no allocator until a final artifact is linked, so an integration test of that crate rejects `extern crate alloc` in the core crates' sources, as CI's `git grep` did before. Both failures were checked by injecting them into `umbra-camera`.
- **CI runs on Linux x86-64 only.**

## Considered options

- **arm64 as best effort**: keep the existing NEON backend, write new kernels for x86 only and give them a scalar fallback on arm64. Rejected: it still means two backends to maintain and test, plus a scalar fallback as a third code path.
- **arm64 for the Coordinator only**, with a scalar backend so an arm64 machine could parse Scenes and run `umbra render`: rejected. It keeps a backend for a machine that renders nothing.
- **A `staticlib` with `panic = "abort"`, in its own workspace, built by a script in a CI job of its own**: rejected. It also catches `alloc` in dependencies, but it costs a script, a CI job, a second workspace with a copied lockfile, and a check that does not run locally unless someone remembers it.
- **Building the core with `-Zbuild-std` for a custom hard-float bare-metal target**: rejected. It needs nightly, and the workspace member catches the same mistakes on stable.

## Consequences

- Development happens on the target machines. A dev container on an arm64 host no longer builds `umbra-math`.
- Kernels can use AVX2's 8 lanes without emulating them on NEON (arc42 §8.14).
- Adding arm64 back means a new `umbra-math` backend and a CI job. The code above the facade needs no change.
