# Milestones defined by the Reference Scenes they unlock

Umbra reaches all of pbrt-v4 on CPU through a sequence of milestones. Each one is defined by the Reference Scenes it makes fully renderable, not by book chapters or by infrastructure layers. Decided in [Milestone sequencing](https://github.com/sergioffpc/umbra/issues/31). The roadmap itself is in [arc42 §4.1](../architecture/04-solution-strategy.md#41-delivery-roadmap).

- **Scope of a milestone.** A milestone's scope is the smallest `.pbrt` subset its new Reference Scenes need ([ADR 0003](0003-pbrt-v4-scene-files-parsed-on-the-coordinator.md)). Strict validation rejects everything outside that subset. Inside a milestone, issues follow the book's order and the crate dependency graph ([arc42 §5.1](../architecture/05-building-block-view.md#51-level-1-the-workspace)).
- **Done means validated and measured.** A milestone closes only when two issues pass for every Reference Scene it has unlocked so far. The manual validation issue runs `umbra validate` ([ADR 0013](0013-statistical-validation-against-a-published-pbrt-v4-reference.md)), and the benchmark measurement issue checks QS-1, QS-5 and QS-6 ([arc42 §8.4](../architecture/08-crosscutting-concepts.md#84-performance-measurement), §10). Every integrator milestone must also support tracing ([ADR 0011](0011-pixel-traces-by-deterministic-re-execution.md)).
- **One milestone, one release.** Each milestone is released from `release/0.N.0` and tagged `v0.N.0` on `main`, and the GitHub Milestone is named `v0.N.0 — <name>`. The benchmark and validation reports are filed under that version. `v1.0.0` is the last milestone.
- **First light carries the tooling.** `v0.1.0` renders a single Reference Scene, `killeroos/killeroo-simple`. It is the simplest in the pinned collection: triangles, a sphere, Loop subdivision, diffuse and coated diffuse materials, and one diffuse area light. The milestone also delivers everything the closing issues need: `umbra bench`, `umbra validate`, the pbrt-v4 reference script and release, golden Film hashes in CI, the allocation test, and `umbra trace` with glTF export. Its integrator is pbrt-v4's default `volpath`, written once and faithfully, and its light sampler is the default `bvh`. Media are rejected until a later milestone. Its benchmark sets the first baseline, so there is no regression check.
- **Distribution is the only milestone without new Scenes.** `v0.2.0` adds remote Workers and re-renders the Reference Scenes of `v0.1.0`. It is accepted on QS-2 (three machines, one Worker killed), QS-7 and QS-8. It comes second because it is what puts [ADR 0004](0004-deterministic-film-for-a-fixed-render-job.md) to the test, and the integrator is still simple. From then on every benchmark measurement issue also records scaling efficiency.
- **Reference Scene Variants for features no Reference Scene uses.** Some pbrt-v4 features appear in no scene of the pinned collection: `mlt`, `lightpath` and the simple integrators, several cameras, filters, samplers, lights and textures, `rgbgrid`, the `spectral` film, and some directives. Each such feature joins the milestone that builds its family and is validated through a Reference Scene Variant. A variant is a Reference Scene with one declared, minimal edit to its Scene File. The reference script applies the same edit before pbrt-v4 renders it, so pbrt-v4 still judges the same input. This amends [ADR 0013](0013-statistical-validation-against-a-published-pbrt-v4-reference.md): validation still uses only the pinned collection, but a Reference Scene may now carry a declared edit.
- **Parity is a milestone of its own.** `v1.0.0` adds no feature. It works through the per-architecture tuning backlog ([ADR 0017](0017-one-worker-per-numa-node.md), [arc42 §8.14](../architecture/08-crosscutting-concepts.md#814-per-architecture-tuning)) until QS-5 reaches its last-milestone target: a speed ratio ≥ 1.0 against pbrt-v4 on each machine, with no Reference Scene below 0.8. It then validates every Reference Scene and variant again. Before it, every milestone must meet only QS-5's target of ≥ 0.5.

## Considered options

- **Book order** (one milestone per block of chapters): rejected as the criterion. A milestone could end with no Reference Scene it can render, and then neither of its closing issues would have anything to check. The book still orders the issues inside a milestone.
- **Infrastructure first** (parser, cluster and tooling on a trivial Scene, then features): rejected. The trivial Scene would not be a Reference Scene, so nothing could be validated against pbrt-v4. And it would leave the tooling, which is cheapest to build against the simplest Scene, without a real Scene to run on.
- **Distribution in the first milestone, or alongside the second set of features**: rejected. The first would put the parser, the BVH, the integrator and the distributed system into one milestone. The second would mix two sources of regression in one benchmark.
- **A path integrator first**: rejected. Every Reference Scene but two uses `volpath`, most of them by default, and the format may not be extended to choose another ([ADR 0003](0003-pbrt-v4-scene-files-parsed-on-the-coordinator.md)). A temporary `path` would only be thrown away.
- **Features without a Reference Scene in one final milestone**: rejected. It would gather unrelated features into one milestone with no theme.
- **Features without a Reference Scene covered by unit and sampling tests only**: rejected. Whole integrators such as `mlt` and `lightpath` would never be compared with pbrt-v4 image against image.
- **Scenes written for Umbra**: rejected, as in ADR 0013.

## Consequences

- There are fifteen milestones, from `v0.1.0` to `v1.0.0`. Their order and contents are in [arc42 §4.1](../architecture/04-solution-strategy.md#41-delivery-roadmap). When a milestone is detailed, a Reference Scene may move to the next milestone if it turns out to need a feature that milestone delivers.
- `v0.1.0` is heavy on tooling and light on rendering. Until it closes, correctness rests on unit and sampling tests alone.
- The reference script and the Reference Scene list must express variants: the Reference Scene, its edit, and its own settings and statistics.
- Two milestones grow beyond their Reference Scenes because they absorb a family of unused features: `v0.3.0` (integrators, filters, samplers) and `v0.7.0` (cameras, lights, film).
- Image output had to be decided before the image writer of `v0.1.0` could be built. [ADR 0020](0020-bit-identical-exr-final-image.md) decides it.
