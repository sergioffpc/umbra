# A bounded asset cache on each Worker host

Each Worker keeps the assets it receives in an Asset Cache on disk, named by content hash and bounded in size. When a Worker joins a Render Job, the Coordinator sends only the assets the Worker does not already hold. Decided with the owner on 2026-11-11. This amends [ADR 0016](0016-one-render-job-per-quic-connection.md), which sent every asset on every connection and rejected a cache "for now", and [ADR 0021](0021-plug-and-play-workers-in-a-named-cluster.md), whose consequences kept that rule.

ADR 0016 rejected a cache because it would add persistent state, invalidation and disk usage to every host, for Workers that lived only for one Session. Since ADR 0021, Workers run permanently and serve one Render Job after another, often for the same Scene, so every Render Job pays the full transfer again: about 9 s per GB and per Worker on 1 GbE, and the R630's two Workers each pay it (RK-3). Content addressing means a cached asset never needs to be invalidated: a hash names exactly one content, whatever the commit. A size bound settles the disk usage.

- **On disk, one file per asset.** The cache is a directory of files, each named by the asset's content hash and holding the asset's bytes exactly as they travel on the wire, never a decoded form, so the cache does not depend on the commit. It survives a Worker restart, including one after an out-of-memory kill. It takes no memory from rendering, and an idle Worker still holds almost nothing in memory. Writes go to a temporary file in the same directory and are renamed into place, so several Workers on one host can share the directory. A Worker deletes leftover temporary files when it starts.
- **Where.** `--cache-dir <path>` or `UMBRA_CACHE_DIR`, by default `$XDG_CACHE_HOME/umbra/assets`, or `~/.cache/umbra/assets` when `XDG_CACHE_HOME` is not set. The release image sets `UMBRA_CACHE_DIR=/var/cache/umbra`, and the README mounts one named volume there for every Worker of a host (`-v umbra-cache:/var/cache/umbra`), so the R630's two Workers share one cache. Without a volume, the cache lives in the container's layer: it survives `--restart unless-stopped` and is lost when the container is recreated.
- **How big.** `--cache-size <bytes>` or `UMBRA_CACHE_SIZE`, with binary suffixes such as `500MiB` or `20GiB`, by default 20 GiB. `0` turns the cache off, and the Worker then asks for every asset, as before this decision. The bound covers the whole directory, so Workers sharing it share the bound. When they are given different values, each evicts down to its own, so the smaller one prevails in practice. The flag wins over the environment variable, which wins over the default, as for `--cluster` and `--port`.
- **Least recently used goes first.** A Worker updates a cached file's `mtime` each time it uses it, because `atime` is unreliable under `noatime` and `relatime`. Before writing a new asset, it deletes the files with the oldest `mtime` until the new one fits. An asset larger than the whole bound is never written: the Worker receives it and keeps it in memory only. Evicting an asset of the Render Job in progress is harmless, since it is already in memory. When a Scene does not fit, the most recent assets stay and the next Render Job is sent the rest.
- **The manifest and `NeedAssets`.** After the Render Job options and the Scene structure, the Scene stream carries an asset manifest: the content hash and size of every asset of the Scene. The Worker looks each hash up in its cache and answers on the control stream with `NeedAssets { hashes }`, the hashes it lacks. The Coordinator then sends exactly those assets, in that order, on the Scene stream, whose end still ends the Scene. The Worker loads the assets it found while the others arrive. This costs one round trip per Render Job. A `NeedAssets` that names a hash absent from the manifest, names one twice, or arrives out of order is a `PROTOCOL_ERROR`.
- **Every byte is checked.** The Worker checks the content hash of every asset, received or read from the cache. A received asset whose hash does not match is `Fatal`, as before. A cached file whose hash does not match is deleted and asked for like a missing one, so a corrupt cache costs a transfer, never a wrong image.
- **A cache that cannot be used is no cache.** If the directory cannot be created or written, the Worker logs a warning and runs as with `--cache-size 0`. A write that fails during a Render Job, such as on a full disk, is logged and skipped. The cache is an optimisation: it never stops a Worker from rendering.
- **Local Workers.** The CPU Local Worker shares the Coordinator's Scene and has no cache. A GPU Local Worker joins over QUIC like a remote Worker ([ADR 0026](0026-gpu-workers-from-the-first-milestone.md)), so it uses the cache of its host.
- **Measured.** While loading, the heartbeat reports the bytes read from the cache apart from the bytes received. The Render Job Report records both for each Worker, so the gain is measured rather than assumed.

## Considered options

- **A cache on the Coordinator**: rejected. The Coordinator already reads and parses each asset once per Render Job ([ADR 0003](0003-pbrt-v4-scene-files-parsed-on-the-coordinator.md)). A cache there, in memory or on disk, would save parsing at most, while every Worker would still receive every byte.
- **A cache in the Worker's memory**: rejected by the owner. It needs no volume and no coordination between processes, but it is lost when the supervisor restarts a Worker killed for running out of memory, which is exactly when the Scene is large. It is also duplicated by every Worker of a host, and it holds between Render Jobs the memory the next Render Job needs.
- **A bound as a fraction of free disk space**: rejected. It adapts to each host, but the cache's size then depends on everything else on the disk.
- **The cache off unless configured**: rejected. It is more conservative, but a Cluster set up from the README alone would never benefit.
- **Least frequently used, or first in first out**: rejected. LFU needs counters kept apart from the files and holds on to assets that were popular once. FIFO evicts an asset in constant use because it was written early.
- **The Worker lists its whole cache in `Hello`**: rejected. The list can be large, and most of it concerns other Scenes.
- **One round trip per asset**: rejected. The Coordinator would send each hash and wait for a yes or no before its bytes, one round trip per asset instead of one per Render Job.

## Consequences

- A Worker host now keeps state between Render Jobs: up to 20 GiB of disk by default, which the operator can bound, move or turn off.
- A Worker reaches readiness faster when it already holds the Scene's assets. The Scene replication time in the Render Job Report shrinks with it, and RK-3 is mitigated, not removed: a Scene seen for the first time, or larger than the cache, still costs its full transfer.
- The Scene stream is no longer one-way in practice: its assets wait for a `NeedAssets` on the control stream. A Worker that never answers is still covered by the heartbeat and the stalled rule (§8.10).
- The release README documents the cache volume and the two options. The R630's two Workers must mount the same volume to share one cache.
- Content hashes become persistent names on disk. If the hash function ever changes, files named by the old hashes are simply never found again, and eviction removes them as the cache fills.
