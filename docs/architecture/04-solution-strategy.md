# 4. Solution Strategy

Umbra reaches pbrt-v4 by following it closely: the same algorithms, the same Scene format and the same numerics, ported to idiomatic Rust and distributed over a LAN. Sections 4.1 and 4.2 say in which order it gets there. Sections 4.3 to 4.5 summarise the fundamental decisions and how they serve the quality goals; the detail is in the ADRs (section 9) and the crosscutting concepts (section 8).

## 4.1 Delivery roadmap

Umbra reaches all of pbrt-v4 on CPU through fifteen milestones ([ADR 0019](../adr/0019-milestones-defined-by-the-reference-scenes-they-unlock.md), [Milestone sequencing](https://github.com/sergioffpc/umbra/issues/31)).

- **Scope and order.** Each milestone is defined by the Reference Scenes from the pinned `mmp/pbrt-v4-scenes` that it makes fully renderable, and its scope is the smallest `.pbrt` subset they need. A feature no Reference Scene uses joins the milestone that builds its family and is validated on a Reference Scene Variant (§8.11).
- **Releases.** Each milestone is a GitHub Milestone and a release tagged `v0.N.0` on `main`.
- **Closing issues.** Every milestone closes with a benchmark measurement issue (§8.4) and a manual validation issue (§8.11). Both check every Reference Scene and variant unlocked so far against the targets of section 10.

## 4.4 Decomposition

- **A `no_std` core and a `std` shell.** The `#![no_std]` crates without `alloc` hold every line that runs per Pixel Sample, in pbrt-v4's chapter order. The `std` crates around them parse, build Scenes, render Work Units, distribute them and offer the command line (§5, [ADR 0015](../adr/0015-layered-workspace-with-a-seven-crate-no-std-core.md)). The core reads the Scene only through a borrowed `SceneView` ([ADR 0014](../adr/0014-gpu-ready-no-std-rendering-core.md)).
- **One Coordinator, N Workers.** The Coordinator parses the Scene File once, replicates the Scene to every Worker, hands out Work Units (one Tile for one Pass) and merges Work Results into the one Film. Each Worker builds its own BVH and renders with every core of its NUMA node (§8.8, [ADR 0009](../adr/0009-pull-based-pass-major-scheduling.md), [ADR 0017](../adr/0017-one-worker-per-numa-node.md)).
- **One code path for every use.** A local `render`, a distributed `render`, `bench` and `validate` all go through `coordinate`; `trace` re-runs Pixel Samples through the same `Renderer` (§5.3).

## 4.5 How the quality goals are reached

| Goal                | Main approach                                                                                                                                                                                                                                                                                                                       |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 Correctness       | Follow pbrt-v4 algorithm by algorithm and port its unit tests; test every sampling routine statistically; validate images per pixel against published pbrt-v4 renders; make each Pixel Sample a pure function of Scene, seed, pixel and sample index on one machine, so a changed golden hash means a changed result (§8.3, §8.11). |
| 2 Comprehensibility | Book structure and names in the core crates, strict lint thresholds, simple contracts between crates, and readable reference implementations kept beside every optimisation (§5.2, §8.6, QS-3).                                                                                                                                     |
| 3 Performance       | Closed-enum dispatch, allocation-free arenas, SIMD behind a facade and an `x86-64-v3` baseline from the start; everything more aggressive waits for a benchmark showing an end-to-end gain and goes through the tuning backlog (§8.4, §8.14).                                                                                       |
| 4 Scalability       | Pull-based, Pass-major scheduling that adapts to machines of very different speeds, a speculative tail, one Worker per NUMA node, and reassignment that never loses a Pixel Sample (§8.8).                                                                                                                                          |
| 5 Debuggability     | Pixel Traces by deterministic re-execution through a monomorphised `Recorder`, so a Render Job pays nothing for them and every pixel of an image rendered locally can be traced on that machine (§8.9).                                                                                                                             |
