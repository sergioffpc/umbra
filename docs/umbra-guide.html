Umbra Guide

Umbra turns a pbrt-v4 Scene File into an image, on every core of a machine, on its GPU and, later, on every machine of a LAN. Fourteen crates share that work. This guide is the map: what each crate is for, how a Render Job travels through them, the rules they all follow, and which crate guide explains each piece in depth.

How to read this guide. It explains how the pieces fit, never what happens inside one: each time a topic belongs to a crate, the guide gives one sentence and a link to that crate's guide, where the pictures and the maths are. Sections start with a blue In plain words box; most have a figure to click. Words in capitals, such as Work Unit or Pixel Sample, are defined in the glossary. Looking for one topic? Use the search in section 5.

What Umbra is for

In plain wordsUmbra is a port of pbrt-v4, the renderer of the book Physically Based Rendering, to Rust. It should compute what pbrt-v4 computes, read like the book, run fast, use every machine available, and let you inspect any pixel afterwards. When two of those wishes pull in different directions, the one higher on the list wins.

Its only input is a pbrt-v4 .pbrt file, unextended. Its output is an EXR image plus a Render Job Report. Between them, five quality goals decide every design question, in this order:

The milestones of section 8 add pbrt-v4's features one family at a time, each milestone defined by the pbrt-v4 example scenes it makes renderable. Measurable targets for each goal are in arc42 §10.

2arc42 §6.2 · crates/umbra/src/render.rs

A Render Job, from command to image

In plain wordsTyping umbra render scene.pbrt starts a chain of handovers. Each crate does one job and passes a value to the next: a path becomes a checked Scene, the Scene becomes a list of Work Units, each Work Unit becomes a Work Result, and the Work Results add up to one image. Step through it below; each step names its crate and the guide that explains it.
3arc42 §5.2 · §8.12 · ADR 0028

Inside one Pixel Sample

In plain wordsA Pixel Sample is one estimate of the light that reaches one point of one pixel. Step 8 of the journey runs it millions of times. It passes through the seven core crates in the order of the book's chapters, so each crate answers one question: which numbers, which colours, which ray, what is hit, what the light does there, how it adds up, and what the sensor records.

Who runs the chain: one core, two drivers

The core crates compile twice, for x86_64 and for the GPU's nvptx64, and the same functions run on both (ADR 0028). What differs is the loop around them. On the CPU, each thread takes one Pixel Sample through every step before starting the next. On the GPU, each step is a kernel that runs on a queue of many Pixel Samples at once, so the order is turned on its side. That is why core functions take and return plain values and never see a queue or a thread index.

The crate map

In plain wordsThe crates form three groups. The core is the code that runs for every Pixel Sample: it uses no operating system and allocates no memory, so it can also run on a GPU. The shell around it reads files, builds Scenes, splits the work, talks over the network and offers the command line. The GPU pair compiles the core for the graphics card and drives it from the host. An arrow means "is used by".

Inside a core crate, each module follows a chapter or section of the book, with pbrt-v4's names. The order of the core crates is the book's order too, which is why the map reads left to right like its table of contents.

7arc42 §7 · §8.8 · §8.13 · ADR 0017 · ADR 0021 · ADR 0026

From one machine to a Cluster

In plain wordsYou start a Worker on each machine once and leave it running. When anyone runs umbra render, that process becomes the Coordinator and announces the Render Job on the local network. Idle Workers with the same Cluster Name join, render their share and go back to waiting. Nobody writes a host list. A machine gets one CPU Worker per NUMA node (a group of cores with its own memory) and one GPU Worker per GPU.

Every Worker of a Render Job must run the same build, checked by its Build Identity, the commit it was built from. On one machine a Pixel Sample then computes the same bits every time; across machines the image is statistically the same, not bit for bit (ADR 0022). Running Workers, the release image and the commands are in the repository README.

8arc42 §4.1 · §4.2 · ADR 0019

The road to parity

In plain wordsUmbra grows in fourteen milestones. Each one is defined by the pbrt-v4 example scenes it makes renderable, its Reference Scenes, and adds the smallest set of features they need. Each lands on the CPU and the GPU together, except three integrators that stay CPU-only. The last milestone adds no feature: it tunes until Umbra is as fast as pbrt-v4.
