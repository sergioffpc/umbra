# Contributing to Umbra

Thanks for your interest in contributing! This guide explains how work flows
through the repository.

## Reporting bugs and requesting features

Open an issue using one of the [issue templates](https://github.com/sergioffpc/umbra/issues/new/choose).
Search existing issues first to avoid duplicates. For security issues, follow
[SECURITY.md](SECURITY.md) instead of opening a public issue.

## Branching model

Umbra uses [git flow](https://nvie.com/posts/a-successful-git-branching-model/):

| Branch           | Branches from | Merges into          | Purpose                         |
| ---------------- | ------------- | -------------------- | ------------------------------- |
| `main`           |               |                      | Released code, tagged `vX.Y.Z`  |
| `develop`        | `main`        |                      | Integration of upcoming changes |
| `feature/<name>` | `develop`     | `develop`            | New features and fixes          |
| `release/X.Y.Z`  | `develop`     | `main` and `develop` | Release preparation             |
| `hotfix/X.Y.Z`   | `main`        | `main` and `develop` | Urgent fixes to a release       |

Open pull requests against `develop`. A `release/X.Y.Z` or `hotfix/X.Y.Z`
branch gets two pull requests, one into `main` and one into `develop`. Repository rulesets block merges into `develop` and `main` unless
every CI job passes and CodeQL code scanning reports no open alert on the
pull request. The CI jobs are grouped into three workflows:
[`rust.yml`](.github/workflows/rust.yml) (fmt, clippy, doc, test, Miri and
AddressSanitizer), [`dependencies.yml`](.github/workflows/dependencies.yml)
(`cargo deny`) and [`lint.yml`](.github/workflows/lint.yml). A pull request
that touches no crate, workspace or toolchain configuration, check script, CI
image or workflow, such as one with documentation only, skips the Rust, Miri
and AddressSanitizer jobs and runs only `lint` and `cargo deny`.

## Commit messages

Commits follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>(<optional scope>): <description>

[optional body]

[optional footer(s)]
```

Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
`build`, `ci`, `chore`, `revert`. Mark breaking changes with `!` after the type
and a `BREAKING CHANGE:` footer. Pull request titles use the same format.

Examples:

```text
feat(integrator): add path tracing integrator
fix(bvh): handle degenerate bounding boxes
```

### Changelog

[CHANGELOG.md](CHANGELOG.md) is generated by [git-cliff](https://git-cliff.org)
from commit headers ([`cliff.toml`](cliff.toml)); do not edit it by hand.
`feat` lands under Added, `refactor`, `perf` and `revert` under Changed, `fix`
under Fixed. `build`, `ci`, `chore`, `docs`, `style` and `test` are left out
unless they are breaking. Write the commit description as the changelog entry
a user should read.

Preview the next release with `git cliff --unreleased`. On a `release/X.Y.Z`
branch, regenerate the file with:

```sh
git cliff --tag vX.Y.Z -o CHANGELOG.md
```

## Toolchain

[`rust-toolchain.toml`](rust-toolchain.toml) pins one dated nightly for the
whole workspace ([ADR 0027](docs/adr/0027-a-pinned-nightly-toolchain.md)), and
`rustup` installs it automatically the first time you run `cargo` in the repo.
There is no `rust-version` in [`Cargo.toml`](Cargo.toml): a nightly has no
version to state. To upgrade, bump `channel` to a date that has every listed
component, in its own `build:` commit, and fix any new lints.

Use stable language and library features only. `#![feature(...)]` belongs in
`umbra-kernels` alone, for what the GPU kernels cannot do without; every other
crate builds as if on stable.

Tools used by the hooks, CI and the checks below. Install them all, at the
versions CI uses, with:

```sh
scripts/install-tools.sh
```

[`scripts/install-tools.sh`](scripts/install-tools.sh) is the one place where
their versions are pinned; CI and the dev container install them with it too.
It needs `curl` and, for Prettier and markdownlint-cli2, `npm`. `shellcheck`
comes from your system package manager.

- [`cargo-nextest`](https://nexte.st): test runner, configured in
  [`.config/nextest.toml`](.config/nextest.toml).
- [`cargo-llvm-cov`](https://github.com/taiki-e/cargo-llvm-cov): test
  coverage. `cargo cov --open` runs the tests under nextest and opens the HTML
  report. CI reports coverage only on demand (the Coverage workflow), with no
  threshold: use it to find untested code, not as a target.
- [`cargo-deny`](https://github.com/EmbarkStudios/cargo-deny): checks
  dependencies for security advisories, licenses, banned crates and sources
  against [`deny.toml`](deny.toml).
- [`cargo-shear`](https://github.com/Boshen/cargo-shear): finds unused
  dependencies; `cargo shear --fix` removes them.
- [`typos`](https://github.com/crate-ci/typos): spell checker. Accept false
  positives in [`_typos.toml`](_typos.toml).
- [`git-cliff`](https://git-cliff.org): generates the changelog (see
  [Changelog](#changelog)).
- [`shellcheck`](https://www.shellcheck.net): lints the shell scripts in
  `.githooks/`, `scripts/` and `.devcontainer/`.
- [`actionlint`](https://github.com/rhysd/actionlint): lints the GitHub
  Actions workflows.
- [`editorconfig-checker`](https://github.com/editorconfig-checker/editorconfig-checker):
  checks files against [`.editorconfig`](.editorconfig).
- [`prettier`](https://prettier.io) and
  [`markdownlint-cli2`](https://github.com/DavidAnson/markdownlint-cli2):
  Prettier formats JSON, YAML and Markdown
  ([`.prettierrc.yaml`](.prettierrc.yaml)), markdownlint lints Markdown
  ([`.markdownlint-cli2.yaml`](.markdownlint-cli2.yaml)). Fix formatting with
  `prettier --write <files>`.
- [`taplo`](https://taplo.tamasfe.dev): formats and checks TOML
  ([`.taplo.toml`](.taplo.toml)), the same engine as the Even Better TOML
  extension. Fix formatting with `taplo fmt`.

## Git setup and hooks

Run the setup script once per clone. It enables the hooks and the commit
message template, and applies recommended local git settings (rebase on pull,
prune on fetch, `rerere`, `zdiff3` conflicts, histogram diffs):

```sh
scripts/setup-git.sh
```

- `pre-commit` checks staged whitespace and, when Rust code, a manifest or a
  TOML configuration is staged, `cargo fmt` and `cargo clippy`. It then runs
  the linters that replace editor extensions: `typos`, `editorconfig-checker`
  on the staged files, `prettier`, `taplo` and `markdownlint-cli2` on the
  staged JSON, TOML, YAML and Markdown files, `shellcheck` on the shell
  scripts, `actionlint` when a workflow is staged, and `cargo deny check`
  when `Cargo.toml`, `Cargo.lock` or `deny.toml` is staged. Each linter is
  skipped with a warning if it is not installed.
- `commit-msg` rejects messages that are not Conventional Commits (see
  [Commit messages](#commit-messages)): valid type, lowercase scope and
  description, no trailing period, header of at most 72 characters, a blank
  line before the body, and a `BREAKING CHANGE:` footer whenever `!` is used.
  Git-generated merge, revert, `fixup!` and `squash!` messages are allowed.
- `pre-push` rejects branches and tags outside the git flow names above
  (`main`, `develop`, `feature/<name>`, `release/X.Y.Z`, `hotfix/X.Y.Z`,
  tags `vX.Y.Z`).

## Editor and dev container

[VS Code](https://code.visualstudio.com) is the reference editor. The
repository ships its workspace configuration in [`.vscode/`](.vscode):

- `extensions.json`: only the essential extensions (rust-analyzer, CodeLLDB,
  Even Better TOML, Claude Code, Dev Containers). VS Code offers to install
  them when you open the folder. Spelling, EditorConfig, JSON, YAML and
  Markdown formatting, shell scripts, workflows, dependencies and commit
  messages are checked by the git hooks instead.
- `settings.json`: format on save with rustfmt, clippy on save with the same
  flags as the hook and CI, rust-analyzer in its own target directory so it
  never blocks `cargo build`, commit message rulers at 72 characters.
- `tasks.json`: builds for every profile (`Ctrl/Cmd+Shift+B` is the dev
  build), tests with nextest, an HTML coverage report, and one `check:` task
  per group of [`scripts/check.sh`](scripts/check.sh). `check: all` runs
  everything CI runs but Miri and AddressSanitizer.
- `launch.json`: CodeLLDB configurations for the binary (dev, `profiling` and
  `checked` profiles), `umbra render` and `umbra worker` alone or together in
  a `debug` Cluster, attaching to a running `umbra`, the binary's unit tests,
  and the unit tests of a library crate chosen at launch.

Personal settings belong in your user settings, not in `.vscode/`; other
files in `.vscode/` are ignored by git.

### Dev container

[`.devcontainer/`](.devcontainer) defines an Ubuntu 26.04 LTS container, the
release the [release image](Dockerfile) builds and ships on, with the pinned
toolchain, `rust-src`, `gh`, Claude Code and every tool listed under
[Toolchain](#toolchain). With Docker running and the Dev Containers
extension installed, run **Dev Containers: Reopen in Container**. On creation
it runs `scripts/setup-git.sh` and `cargo fetch`, so the hooks work inside the
container.

- `target/` and the cargo download cache are Docker volumes, not bind mounts:
  builds stay fast and survive container rebuilds. The container's
  `target/` is separate from the host's.
- Tool versions come from [`scripts/install-tools.sh`](scripts/install-tools.sh);
  Dependabot updates the base image and features.
- A git worktree cannot be opened in the container: its `.git` file points
  to a path on the host. Open the main clone instead.
- On a host whose Docker has the NVIDIA Container Toolkit, such as the P620,
  the container gets the host's GPUs, with the driver capabilities OptiX
  needs (`compute,graphics`, arc42 §7), and the GPU tests run in it
  (`cargo nextest run --profile gpu`):
  the image holds CUDA's `libdevice.10.bc`, the only file of CUDA the build
  needs. Elsewhere it starts without a GPU.

## Lint and formatting rules

- Formatting: [`rustfmt.toml`](rustfmt.toml) and [`.editorconfig`](.editorconfig);
  for JSON, YAML and Markdown [`.prettierrc.yaml`](.prettierrc.yaml), for TOML
  [`.taplo.toml`](.taplo.toml). Markdown prose keeps its line breaks.
- Lints: the `[lints]` table in [`Cargo.toml`](Cargo.toml) (rustc lints, clippy
  `all`, `pedantic`, `cargo` and selected `restriction` lints) plus
  [`clippy.toml`](clippy.toml). Every warning is an error in the hook and in CI.
- Functions do one thing. Lints enforce the measurable part: at most 40 lines,
  cognitive complexity at most 10, nesting at most 3 levels, at most 5
  arguments. Split a function rather than silencing these.
- Enums over bools: a function parameter or struct field is never `bool`; use
  an enum with named variants (`Visibility::Hidden`, not `visible: false`).
  `bool` stays for predicates such as `is_empty()`.
- Least privilege: items are private by default. Use `pub(crate)` (or
  narrower) for anything shared inside the crate; `pub` only for the essential
  API of the crate. `unreachable_pub` rejects `pub` that is not reachable from
  outside, `missing_docs` requires docs on every public item, and
  `partial_pub_fields` rejects structs that mix public and private fields.
- Performance: besides clippy `perf` and the perf lints in `pedantic`, the
  nursery and restriction lints that catch wasted work are on: redundant
  clones and collects, eager `or_*` arguments, locks held too long, `Mutex`
  where an atomic fits, and stack frames over 64 KiB. `missing_asserts_for_indexing`
  asks for one `assert!` on the length before indexing a slice several times,
  so LLVM can drop the per-index bounds checks.
- `unsafe` is denied. An exception is an aggressive optimisation
  ([ADR 0007](docs/adr/0007-unsafe-code-as-an-aggressive-optimisation.md)):
  it needs a benchmark, a safe contract and a safe reference implementation it
  is tested against, under Miri (or AddressSanitizer where Miri cannot run the
  code). Open it with `#[expect(unsafe_code, reason = "...")]` on the narrowest
  item, one unsafe operation per block, each with a `// SAFETY:` comment.
- No `_` arm in a `match` on an enum: list the variants, so adding one breaks
  the build wherever it is not handled. On a `#[non_exhaustive]` enum from
  another crate, a `_` arm is allowed after the known variants.
- Numerics ([ADR 0022](docs/adr/0022-determinism-on-one-machine-statistical-equality-across-machines.md)):
  `std`'s transcendental float methods (`sin`, `exp`, `powf`, …) are banned in
  favour of `umbra-math`: its own kernels (`sin_cos`, `atan2`, `erf`,
  `Vec4::exp`, `Vec4::pow`) where they exist, and otherwise its safe wrappers
  of the C functions, which call glibc on x86-64 and `libdevice` on
  `nvptx64`: the `f32` ones at the crate root (`umbra_math::tanf`), the `f64`
  ones in `umbra_math::double`. Vendor-dependent approximate reciprocal intrinsics and
  flush-to-zero are banned too. The list is `disallowed-methods` in [`clippy.toml`](clippy.toml).
  The GPU is the exception: `umbra-math`'s `nvptx64` backend uses PTX's
  approximate instructions, directly and inside `libdevice`, whose results
  are statistical only
  ([ADR 0028](docs/adr/0028-one-core-for-cpu-and-gpu.md)).
- No `f64` in the seven core crates
  ([ADR 0028](docs/adr/0028-one-core-for-cpu-and-gpu.md)): consumer GPUs run
  it at a small fraction of `f32`'s rate. `disallowed-types` in
  [`clippy.toml`](clippy.toml) lists it, and each core crate's `lib.rs` turns
  the lint on; `umbra-math`'s x86-64 backends `#[expect]` it. The `std`
  crates, tests and build scripts keep `f64`.
- No `print!` or `eprint!` outside tests: use `tracing`.
- To silence a lint, use `#[expect(clippy::lint_name, reason = "...")]` on the
  narrowest item possible. `#[allow]` and reasonless attributes are rejected.

## Workspace layout

The crates of
[arc42 §5.1](docs/architecture/05-building-block-view.md#51-level-1-the-workspace)
live in `crates/<name>/`. The root [`Cargo.toml`](Cargo.toml) holds the
package metadata, lints and dependencies they inherit, and the build profiles.
Every crate sets `lints.workspace = true` and takes its dependencies with
`workspace = true`: declare a new dependency in `[workspace.dependencies]`
first.

- The core crates of
  [arc42 §5.2](docs/architecture/05-building-block-view.md#52-level-2-the-core)
  are `#![no_std]` and never `extern crate alloc`
  ([ADR 0014](docs/adr/0014-gpu-ready-no-std-rendering-core.md),
  [ADR 0015](docs/adr/0015-layered-workspace-with-a-seven-crate-no-std-core.md)).
  Their dependencies use `default-features = false` and must build without
  `std`. Nothing checks this automatically
  ([ADR 0023](docs/adr/0023-x86-64-only.md)): keep `std` and `alloc` out of
  the core in review, including through dependency features.
- Each core crate has a `serde` feature, off by default, that enables its
  dependencies' `serde` features. `umbra-scene` turns it on.

### Crate READMEs

Every crate has a `README.md`: the guide to the crate from the inside, as it
is built. Arc42 §5 describes how the crates fit together; the README describes
what is in one of them and why, and refers to arc42 and the ADRs by name
rather than repeating them. It is also the crate's rustdoc documentation: the
crate root starts with `#![doc = include_str!("../README.md")]`, and its
examples run as doctests. So it uses no relative links (they break in
rustdoc) and no intra-doc links (they show as text on GitHub): ADRs and arc42
sections are cited by name ("ADR 0007", "arc42 §5.1"), issues by their full
URL.

Each README has these sections, in this order:

- `# <crate>`: what the crate is, where it sits in the graph of arc42 §5.1,
  whether it is a core crate, the PBR 4e chapters it covers if any, and a
  short example.
- `## What is in it`: each module with its pbrt-v4 source and contents, then
  what looks as if it belongs here but lives elsewhere, or comes later.
- `## Design decisions`: the crate's own decisions and the reasons for them.
- `## Things to know when using it`: contracts and traps the signatures do not
  show.
- `## Performance`: only in crates with benchmarks.
- `## Tests`: what is tested, and against what.

A crate with no code yet has only the first section, without the example, and
a status line naming the issue that brings its first code. That issue's pull
request writes the other sections and removes the status line.
The `readmes` group of [`scripts/check.sh`](scripts/check.sh), part of `lint`
and run by the pre-commit hook, checks that every crate has its README and
includes it; review checks that the README is current.

## Build profiles

| Profile     | Command                           | Use                                                                                      |
| ----------- | --------------------------------- | ---------------------------------------------------------------------------------------- |
| `dev`       | `cargo build`                     | Day-to-day work: `opt-level = 1`, dependencies at 3, full debug info, all checks         |
| `release`   | `cargo build --release`           | Fastest binary: fat LTO, one codegen unit, `panic = "abort"`, line tables for backtraces |
| `profiling` | `cargo build --profile profiling` | Release speed with full debug info for profilers                                         |
| `checked`   | `cargo build --profile checked`   | Release speed with debug assertions and overflow checks, for long renders                |

Build scripts are optimised in `dev` and `release`: the one of
`umbra-spectrum` computes the sRGB RGB-to-spectrum table, about a CPU-minute
optimised
([ADR 0022](docs/adr/0022-determinism-on-one-machine-statistical-equality-across-machines.md)).

[`.cargo/config.toml`](.cargo/config.toml) builds for the local CPU
(`target-cpu=native`), on the x86-64 target only: `nvptx64` builds use that
target's default. Override `RUSTFLAGS` for binaries that must run on
other machines. An override must keep at least `-C target-cpu=x86-64-v3`:
`umbra-math` requires FMA, SSE4.1 and AVX2 and stops the build without them
([ADR 0023](docs/adr/0023-x86-64-only.md)).

## Before opening a pull request

Run the checks CI runs:

```sh
scripts/check.sh            # everything: rust, lint and deny
scripts/check.sh rust       # or one group: fmt, clippy, doc, tests
scripts/check.sh miri asan  # the crates that call glibc, under Miri and ASan
```

[`scripts/check.sh`](scripts/check.sh) is the one list of these checks: each
CI job runs one of its groups. `miri` and `asan` are not in the default run
(Miri takes minutes); `miri` needs the `miri` and `rust-src` components, added
to the pinned toolchain with `rustup component add miri rust-src`.

CI runs the Rust groups (`rust`, `miri`, `asan`) in the `ci` stage of the
[`Dockerfile`](Dockerfile): the Ubuntu digest and toolchain the release image
is built with, so the tests, oracles and hashes see the glibc the release
ships, not the runner's. To run a group in that same image (Docker or
Podman):

```sh
scripts/in-ci-image.sh scripts/check.sh rust
scripts/in-ci-image.sh scripts/check.sh miri asan
```

[`scripts/in-ci-image.sh`](scripts/in-ci-image.sh) builds the image, mounts
the checkout at `/src` and keeps the image's target directory and cargo
registry in Docker volumes. Run it from a clone, not a git worktree, whose
`.git` points outside the mount. The dev container is on the same Ubuntu
release but not the same digest, so a glibc point release can still differ.

Then:

- Make sure the commit headers read as changelog entries (see
  [Changelog](#changelog)); do not edit CHANGELOG.md.
- Add or update tests for the behaviour you changed.
- Update the README of every crate whose modules, decisions or contracts you
  changed (see [Crate READMEs](#crate-readmes)).
- Keep each pull request focused on one change.

## Release container image

Pushing the `vX.Y.Z` tag on `main` runs
[`release-image.yml`](.github/workflows/release-image.yml), which builds the
[`Dockerfile`](Dockerfile) for `x86-64-v3` and publishes one image to
`ghcr.io/sergioffpc/umbra`, tagged `X.Y.Z`. There is no `X.Y` or `latest` tag.
One job builds, smoke-tests and pushes the image, with its provenance, SBOM
and attestation. The job fails if the tag is not
on `main` or does not match `version` in `Cargo.toml`, so bump the crate
version on the `release/X.Y.Z` branch. Push `main` before the tag (or both
with `git push --follow-tags`). Design notes:
[ADR 0005](docs/adr/0005-chiseled-release-container-image.md) and
[ADR 0025](docs/adr/0025-one-x86-64-v3-release-image.md).

To build and run the image locally (Docker or Podman):

```sh
docker build -t umbra .
docker run --rm umbra
```

The image builds for `linux/amd64` only.

The build context is limited by [`.dockerignore`](.dockerignore): add new
crate sources (`build.rs`, workspace members) there. A dependency on a system
library needs its Chisel slice added in the `Dockerfile`.

## pbrt-v4 reference

[`reference/scenes.toml`](reference/scenes.toml) holds the pinned `mmp/pbrt-v4`
and `mmp/pbrt-v4-scenes` commits and the Reference Scenes, each with its
benchmark, validation and golden settings.
[`scripts/pbrt_reference.py`](scripts/pbrt_reference.py) turns them into the
reference that `umbra validate` judges against
([ADR 0013](docs/adr/0013-statistical-validation-against-a-published-pbrt-v4-reference.md)):
it builds pbrt-v4 (CPU) at the pinned commit, fetches only the needed
directories of the scenes, applies each Reference Scene Variant's edit and
makes the Film write 32-bit floats (`savefp16`, recorded in the manifest), renders
every Reference Scene with seeds 0–15 at its validation settings and its
Reference Image at 64 × its benchmark Pixel Samples per pixel, and publishes
the per-pixel mean and variance EXRs, the Reference Image and a manifest with
their SHA-256 as assets of the release `pbrt-v4-reference/<pbrt-v4 commit>`.

Only whoever moves a pin or adds a Reference Scene runs it, by hand on a target
machine, never in CI. It needs Python 3.11 or later, git,
CMake, a C++17 compiler and an authenticated `gh`:

```sh
scripts/pbrt_reference.py                 # every Reference Scene not yet published
scripts/pbrt_reference.py --no-publish    # render into target/pbrt-reference/out only
scripts/pbrt_reference.py --scene killeroo-simple
```

Rerunning it skips every Reference Scene already published from the same
inputs. A published reference is immutable: if a Reference Scene's pins,
settings or edit change, the script refuses it until its assets are deleted
from the release.

Keep GitHub's release immutability off for this repository (Settings →
General → Releases). Each milestone adds its Reference Scenes to the existing
release, and an immutable release accepts no new assets once published. A tag
name once used by an immutable release can never be reused: that is why the
tag is `pbrt-v4-reference/<commit>` and not the earlier
`pbrt-v4-reference-<commit>`.
