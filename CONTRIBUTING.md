# Contributing to Umbra

Thanks for your interest in contributing! This guide explains how work flows
through the repository.

## Reporting bugs and requesting features

Open an issue using one of the [issue templates](https://github.com/sergioffpc/umbra/issues/new/choose).
Search existing issues first to avoid duplicates. For security issues, follow
[SECURITY.md](SECURITY.md) instead of opening a public issue.

## Branching model

Umbra uses [git flow](https://nvie.com/posts/a-successful-git-branching-model/):

| Branch           | Branches from | Merges into          | Purpose                         |
| ---------------- | ------------- | -------------------- | ------------------------------- |
| `main`           |               |                      | Released code, tagged `vX.Y.Z`  |
| `develop`        | `main`        |                      | Integration of upcoming changes |
| `feature/<name>` | `develop`     | `develop`            | New features and fixes          |
| `release/X.Y.Z`  | `develop`     | `main` and `develop` | Release preparation             |
| `hotfix/X.Y.Z`   | `main`        | `main` and `develop` | Urgent fixes to a release       |

Open pull requests against `develop`. A `release/X.Y.Z` or `hotfix/X.Y.Z`
branch gets two pull requests, one into `main` and one into `develop`. Repository rulesets block merges into `develop` and `main` unless
every CI job in [`ci.yml`](.github/workflows/ci.yml) passes and CodeQL code
scanning reports no open alert on the pull request.

## Commit messages

Commits follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
<type>(<optional scope>): <description>

[optional body]

[optional footer(s)]
```

Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
`build`, `ci`, `chore`, `revert`. Mark breaking changes with `!` after the type
and a `BREAKING CHANGE:` footer. Pull request titles use the same format.

Examples:

```text
feat(integrator): add path tracing integrator
fix(bvh): handle degenerate bounding boxes
```

### Changelog

[CHANGELOG.md](CHANGELOG.md) is generated by [git-cliff](https://git-cliff.org)
from commit headers ([`cliff.toml`](cliff.toml)); do not edit it by hand.
`feat` lands under Added, `refactor`, `perf` and `revert` under Changed, `fix`
under Fixed. `build`, `ci`, `chore`, `docs`, `style` and `test` are left out
unless they are breaking. Write the commit description as the changelog entry
a user should read.

Preview the next release with `git cliff --unreleased`. On a `release/X.Y.Z`
branch, regenerate the file with:

```sh
git cliff --tag vX.Y.Z -o CHANGELOG.md
```

## Toolchain

[`rust-toolchain.toml`](rust-toolchain.toml) pins the Rust version, and
`rustup` installs it automatically the first time you run `cargo` in the repo.
`rust-version` in [`Cargo.toml`](Cargo.toml) matches it. To upgrade, bump both
in one `build:` commit and fix any new lints.

Optional tools used by the hook and CI:

- [`typos`](https://github.com/crate-ci/typos) (`brew install typos-cli` or
  `cargo install typos-cli`): spell checker. Accept false positives in
  [`_typos.toml`](_typos.toml).
- [`cargo-deny`](https://github.com/EmbarkStudios/cargo-deny)
  (`cargo install cargo-deny`): checks dependencies for security advisories,
  licenses, banned crates and sources against [`deny.toml`](deny.toml).
- [`cargo-nextest`](https://nexte.st) (`brew install cargo-nextest` or
  `cargo install cargo-nextest`): test runner, configured in
  [`.config/nextest.toml`](.config/nextest.toml).
- [`cargo-llvm-cov`](https://github.com/taiki-e/cargo-llvm-cov)
  (`brew install cargo-llvm-cov` or `cargo install cargo-llvm-cov`): test
  coverage. `cargo cov --open` runs the tests under nextest and opens the HTML
  report. Coverage is reported in CI but has no threshold: use it to find
  untested code, not as a target.
- [`cargo-shear`](https://github.com/Boshen/cargo-shear)
  (`brew install cargo-shear` or `cargo install cargo-shear`): finds unused
  dependencies; `cargo shear --fix` removes them.
- [`git-cliff`](https://git-cliff.org) (`brew install git-cliff` or
  `cargo install git-cliff`): generates the changelog (see
  [Changelog](#changelog)).
- [`shellcheck`](https://www.shellcheck.net) (`brew install shellcheck`):
  lints the shell scripts in `.githooks/`, `scripts/` and `.devcontainer/`.
- [`actionlint`](https://github.com/rhysd/actionlint)
  (`brew install actionlint`): lints the GitHub Actions workflows.
- [`editorconfig-checker`](https://github.com/editorconfig-checker/editorconfig-checker)
  (`brew install editorconfig-checker`): checks files against
  [`.editorconfig`](.editorconfig).
- [`prettier`](https://prettier.io) and
  [`markdownlint-cli2`](https://github.com/DavidAnson/markdownlint-cli2)
  (`npm install --global prettier markdownlint-cli2`): Prettier formats JSON,
  YAML and Markdown ([`.prettierrc.yaml`](.prettierrc.yaml)), markdownlint
  lints Markdown ([`.markdownlint-cli2.yaml`](.markdownlint-cli2.yaml)). Fix
  formatting with `prettier --write <files>`.
- [`taplo`](https://taplo.tamasfe.dev) (`brew install taplo`): formats and
  checks TOML ([`.taplo.toml`](.taplo.toml)), the same engine as the Even
  Better TOML extension. Fix formatting with `taplo fmt`.
- [`yamllint`](https://github.com/adrienverge/yamllint)
  (`brew install yamllint`): lints YAML ([`.yamllint.yaml`](.yamllint.yaml)).

## Git setup and hooks

Install [Git LFS](https://git-lfs.com) first (`brew install git-lfs` on
macOS). Images (`.exr`, `.hdr`, `.pfm`, `.png`, `.jpg`, `.tga`) and meshes
(`.ply`, `.obj`) are stored in LFS; see [`.gitattributes`](.gitattributes).

Then run the setup script once per clone. It enables the hooks, the commit
message template and the LFS filters, downloads LFS content, and applies
recommended local git settings (rebase on pull, prune on fetch, `rerere`,
`zdiff3` conflicts, histogram diffs):

```sh
scripts/setup-git.sh
```

- `pre-commit` checks staged whitespace, `cargo fmt`, `cargo clippy`,
  then runs the linters that replace editor extensions: `typos`,
  `editorconfig-checker` on the staged files, `prettier`, `taplo`,
  `yamllint` and `markdownlint-cli2` on the staged JSON, TOML, YAML and
  Markdown files, `shellcheck` on the shell scripts, `actionlint` when a
  workflow is staged, and `cargo deny check`
  when `Cargo.toml`, `Cargo.lock` or `deny.toml` is staged. Each linter is
  skipped with a warning if it is not installed.
- `commit-msg` rejects messages that are not Conventional Commits (see
  [Commit messages](#commit-messages)): valid type, lowercase scope and
  description, no trailing period, header of at most 72 characters, a blank
  line before the body, and a `BREAKING CHANGE:` footer whenever `!` is used.
  Git-generated merge, revert, `fixup!` and `squash!` messages are allowed.
- `pre-push` rejects branches and tags outside the git flow names above
  (`main`, `develop`, `feature/<name>`, `release/X.Y.Z`, `hotfix/X.Y.Z`,
  tags `vX.Y.Z`), then uploads LFS objects.
- `post-checkout`, `post-commit` and `post-merge` run the matching Git LFS
  hooks. Every hook that uses LFS stops with an error if `git-lfs` is missing.

## Editor and dev container

[VS Code](https://code.visualstudio.com) is the reference editor. The
repository ships its workspace configuration in [`.vscode/`](.vscode):

- `extensions.json`: only the essential extensions (rust-analyzer, CodeLLDB,
  Even Better TOML, Claude Code, Dev Containers). VS Code offers to install
  them when you open the folder. Spelling, EditorConfig, JSON, YAML and
  Markdown formatting, shell scripts, workflows, dependencies and commit
  messages are checked by the git hooks instead.
- `settings.json`: format on save with rustfmt, clippy on save with the same
  flags as the hook and CI, rust-analyzer in its own target directory so it
  never blocks `cargo build`, commit message rulers at 72 characters.
- `tasks.json`: builds for every profile (`Ctrl/Cmd+Shift+B` is the dev
  build), a portable `x86-64-v3` release, tests with nextest, an HTML coverage
  report, and one `ci:` task per CI check. `ci: all checks` runs them all in
  order.
- `launch.json`: CodeLLDB configurations for the binary (dev and `profiling`
  profiles) and its unit tests.

Personal settings belong in your user settings, not in `.vscode/`; other
files in `.vscode/` are ignored by git.

### Dev container

[`.devcontainer/`](.devcontainer) defines a Debian 13 container with the
pinned toolchain, `rust-src`, Git LFS, `gh`, Claude Code and every tool listed
under [Toolchain](#toolchain). With Docker running and the Dev Containers
extension installed, run **Dev Containers: Reopen in Container**. On creation
it runs `scripts/setup-git.sh` and `cargo fetch`, so the hooks work inside the
container.

- `target/` and the cargo download cache are Docker volumes, not bind mounts:
  builds stay fast on macOS and survive container rebuilds. The container's
  `target/` is separate from the host's.
- On Apple silicon the container is `aarch64-unknown-linux-gnu`, a platform no
  Worker runs; use it for development, and the host or CI for anything that
  depends on the target platform.
- Tool versions are `ARG`s in the [`Dockerfile`](.devcontainer/Dockerfile);
  Dependabot updates the base image and features.
- A git worktree cannot be opened in the container: its `.git` file points
  to a path on the host. Open the main clone instead.

## Lint and formatting rules

- Formatting: [`rustfmt.toml`](rustfmt.toml) and [`.editorconfig`](.editorconfig);
  for JSON, YAML and Markdown [`.prettierrc.yaml`](.prettierrc.yaml), for TOML
  [`.taplo.toml`](.taplo.toml). Markdown prose keeps its line breaks.
- Lints: the `[lints]` table in [`Cargo.toml`](Cargo.toml) (rustc lints, clippy
  `all`, `pedantic`, `cargo` and selected `restriction` lints) plus
  [`clippy.toml`](clippy.toml). Every warning is an error in the hook and in CI.
- Functions do one thing. Lints enforce the measurable part: at most 40 lines,
  cognitive complexity at most 10, nesting at most 3 levels, at most 5
  arguments. Split a function rather than silencing these.
- Enums over bools: a function parameter or struct field is never `bool`; use
  an enum with named variants (`Visibility::Hidden`, not `visible: false`).
  `bool` stays for predicates such as `is_empty()`.
- Least privilege: items are private by default. Use `pub(crate)` (or
  narrower) for anything shared inside the crate; `pub` only for the essential
  API of the crate. `unreachable_pub` rejects `pub` that is not reachable from
  outside, `missing_docs` requires docs on every public item, and
  `partial_pub_fields` rejects structs that mix public and private fields.
- Performance: besides clippy `perf` and the perf lints in `pedantic`, the
  nursery and restriction lints that catch wasted work are on: redundant
  clones and collects, eager `or_*` arguments, locks held too long, `Mutex`
  where an atomic fits, and stack frames over 64 KiB. `missing_asserts_for_indexing`
  asks for one `assert!` on the length before indexing a slice several times,
  so LLVM can drop the per-index bounds checks.
- `unsafe` is denied. An exception is an aggressive optimisation
  ([ADR 0007](docs/adr/0007-unsafe-code-as-an-aggressive-optimisation.md)):
  it needs a benchmark, a safe contract and a safe reference implementation it
  is tested against, under Miri (or AddressSanitizer where Miri cannot run the
  code). Open it with `#[expect(unsafe_code, reason = "...")]` on the narrowest
  item, one unsafe operation per block, each with a `// SAFETY:` comment.
- No `_` arm in a `match` on an enum: list the variants, so adding one breaks
  the build wherever it is not handled. On a `#[non_exhaustive]` enum from
  another crate, a `_` arm is allowed after the known variants.
- Bit-identical floats ([ADR 0002](docs/adr/0002-bit-identical-results-across-architectures.md)):
  `std`'s transcendental float methods (`sin`, `exp`, `powf`, …) are banned in
  favour of the `libm` crate, as are approximate reciprocal intrinsics and
  flush-to-zero. The list is `disallowed-methods` in [`clippy.toml`](clippy.toml).
- No `print!` or `eprint!` outside tests: use `tracing`.
- To silence a lint, use `#[expect(clippy::lint_name, reason = "...")]` on the
  narrowest item possible. `#[allow]` and reasonless attributes are rejected.

## Workspace layout

The twelve crates of
[arc42 §5.1](docs/architecture/05-building-block-view.md#51-level-1-the-workspace)
live in `crates/<name>/`. The root [`Cargo.toml`](Cargo.toml) holds the
package metadata, lints and dependencies they inherit, and the build profiles.
Every crate sets `lints.workspace = true` and takes its dependencies with
`workspace = true`: declare a new dependency in `[workspace.dependencies]`
first.

- The seven core crates (`umbra-math` to `umbra-integrators`) are
  `#![no_std]` and never `extern crate alloc`
  ([ADR 0014](docs/adr/0014-gpu-ready-no-std-rendering-core.md),
  [ADR 0015](docs/adr/0015-layered-workspace-with-a-seven-crate-no-std-core.md)).
  Their dependencies use `default-features = false` and must build without
  `std`. Check with
  `RUSTFLAGS="-D warnings" cargo build --target aarch64-unknown-none -p umbra-math`
  (and the other six). Setting `RUSTFLAGS` drops `target-cpu=native`, which
  does not apply to that target.
- Each core crate has a `serde` feature, off by default, that enables its
  dependencies' `serde` features. `umbra-scene` turns it on.

## Build profiles

| Profile     | Command                           | Use                                                                                      |
| ----------- | --------------------------------- | ---------------------------------------------------------------------------------------- |
| `dev`       | `cargo build`                     | Day-to-day work: `opt-level = 1`, dependencies at 3, full debug info, all checks         |
| `release`   | `cargo build --release`           | Fastest binary: fat LTO, one codegen unit, `panic = "abort"`, line tables for backtraces |
| `profiling` | `cargo build --profile profiling` | Release speed with full debug info for profilers                                         |
| `checked`   | `cargo build --profile checked`   | Release speed with debug assertions and overflow checks, for long renders                |

[`.cargo/config.toml`](.cargo/config.toml) builds for the local CPU
(`target-cpu=native`). Override `RUSTFLAGS` for binaries that must run on
other machines.

## Before opening a pull request

Run the same checks CI runs:

```sh
cargo fmt --all -- --check
cargo clippy --all-targets --all-features --locked -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --document-private-items --all-features --locked
cargo nextest run --all-features --locked
cargo test --doc --all-features --locked
RUSTFLAGS="-D warnings" cargo build --locked --target aarch64-unknown-none \
  -p umbra-math -p umbra-sampling -p umbra-spectrum -p umbra-geometry \
  -p umbra-shading -p umbra-camera -p umbra-integrators
cargo deny check
cargo shear
typos
git ls-files -z '.githooks/*' '*.sh' | xargs -0 shellcheck
actionlint
git ls-files -z | xargs -0 editorconfig-checker
git ls-files -z '*.json' '*.yml' '*.yaml' '*.md' | xargs -0 prettier --check
git ls-files -z '*.toml' | xargs -0 taplo fmt --check
git ls-files -z '*.toml' | xargs -0 taplo lint
git ls-files -z '*.yml' '*.yaml' | xargs -0 yamllint --strict
git ls-files -z '*.md' | xargs -0 markdownlint-cli2
```

CI runs the build, lint and test checks on Linux and macOS, and a coverage
report on Linux (in the run summary, with the HTML report as an artifact).

Then:

- Make sure the commit headers read as changelog entries (see
  [Changelog](#changelog)); do not edit CHANGELOG.md.
- Add or update tests for the behaviour you changed.
- Keep each pull request focused on one change.

## Release container image

Pushing the `vX.Y.Z` tag on `main` runs
[`release-image.yml`](.github/workflows/release-image.yml), which builds the
[`Dockerfile`](Dockerfile) and publishes `ghcr.io/sergioffpc/umbra` with the
tags `X.Y.Z`, `X.Y` and `latest`. The job fails if the tag is not on `main` or
does not match `version` in `Cargo.toml`, so bump the crate version on the
`release/X.Y.Z` branch. Push `main` before the tag (or both with
`git push --follow-tags`). Design notes:
[ADR 0005](docs/adr/0005-chiseled-release-container-image.md).

To build and run the image locally (Docker or Podman):

```sh
docker build -t umbra .
docker run --rm umbra
```

On Apple silicon this builds a native `linux/arm64` image for testing; the
published image is `linux/amd64` only. The build context is limited by
[`.dockerignore`](.dockerignore): add new crate sources (`build.rs`, workspace
members) there. A dependency on a system library needs its Chisel slice added
in the `Dockerfile`.
