Umbra Math Guide

Every pixel Umbra renders comes out of a long chain of f32 operations, and umbra-math is where that chain starts: floats and their rounding, error bounds, compensated arithmetic, vectors, frames and transforms. This guide explains the crate topic by topic, and each topic has a figure you can play with.

You write 0.1_f32. Umbra stores the nearest of the 2³² bit patterns, which is exactly:
0.100000001490116119384765625
1 sign bit · 8 exponent bits · 23 significand bits = 0x3DCCCCCD. The red digits are rounding error, and the rest of this guide is about keeping errors like that under control.

umbra-math is the bottom of the seven no_std core crates (arc42 §5.1); every other core crate builds on it. The maths of the crates above it is explained next to their code, for example the Umbra Camera Guide, which uses perspective().

How the figures compute: every figure runs in emulated f32 (JavaScript's Math.fround after each operation, with an exactly rounded FMA). It performs the same operations, in the same order, as the Rust function it names. Where a figure compares against an exact answer, it says how that answer was obtained. Section references (“PBR 4e §6.8.1”) point to Physically Based Rendering, 4th edition, which Umbra follows.

umbra-math

Arithmetic you can trust

umbra-math holds the numeric ground floor: floats and their rounding, interval bounds, compensated products, vectors, frames and transforms. Everything is f32 (ADR 0001) and gives the same bits on x86-64 and arm64 (ADR 0002).

1umbra-math · float.rs · PBR 4e §6.8.1

The f32 number line

An f32 is 32 bits: 1 sign bit s, 8 exponent bits e and 23 significand bits f. A normal value is

v = (−1)s × 1.f × 2e − 127

So floats are not evenly spaced. Between one power of two and the next there are always exactly 2²³ of them, and the gap between neighbours, one ULP (unit in the last place), doubles at every power of two. Near 1 an ULP is 1.19 × 10⁻⁷. Near 100 000, a plausible scene coordinate, it is 0.0078.

Umbra never changes the hardware rounding mode (ADR 0002). Every + − × ÷ √ rounds to the nearest float, so each result is off by at most half an ULP. That is a relative error of at most ε = 2⁻²⁴ ≈ 5.96 × 10⁻⁸, the constant MACHINE_EPSILON. When the code needs a result rounded outward instead, it takes the nearest result and steps one float further with next_float_up or next_float_down, which add or subtract 1 from the bit pattern.

2umbra-math · gamma() · PBR 4e §6.8.1 · ADR 0004

How error grows: γ(n)

One rounded operation multiplies the exact result by some factor in [1 − ε, 1 + ε]. A chain of n operations multiplies it by up to (1 ± ε)n, and the book bounds that product with one number:

(1 + ε)n ≤ 1 + γ(n),  γ(n) = nε ⁄ (1 − nε) gamma(n: u16) → f32

Umbra's gamma is that formula, evaluated in f32. Shapes use it to state how far a computed intersection can be from the true one. The figure checks the bound on the simplest chain there is: adding 0.1_f32 to itself n times. For a sum, the standard bound is |error| ≤ γ(n − 1) · Σ|xi|.

Addition is not associative

Each addition rounds, so (a + b) + c and a + (b + c) can differ in the last bits. Below are eight f32 values. Two of them nearly cancel, as bright and dark samples do. Shuffle their order and the f32 sum changes. This is why ADR 0004 fixes a canonical summation order: each pixel sums its Pixel Samples in ascending sample index, so the Film is bit-identical however the Work Units were spread across Workers.

3umbra-math · interval.rs, Point3fi · used by umbra-geometry · PBR 4e §6.8.2–§6.8.6 · ADR 0001

Intervals, and where the next ray starts

An Interval is a pair [low, high] that contains the exact result of the computation that produced it. Each operation rounds its bounds outward: the low bound uses a round-down operation (add_round_down, mul_round_down, …) and the high bound a round-up one. A product takes all four bound products and keeps the extremes. If the inputs contained the exact values, the output does too. That holds by construction, not by testing.

Why a renderer pays for this: when a ray hits a surface, the computed hit point p is almost never exactly on the surface. It can land a fraction of an ULP inside. A shadow or bounce ray that starts there can hit the same surface again at t ≈ 0, which shows up as the speckled artefact called shadow acne. pbrt-v4, and Umbra after it, keeps a conservative error box with every hit point (a Point3fi is a point made of Intervals). For a sphere the box is γ(5)·|p| per axis. offset_ray_origin then pushes the origin along the normal just far enough to leave that box, and steps one more float outward.

ADR 0001 rejected the alternative, a fixed epsilon offset, “because they are fragile under changes of scene scale”. Change the scale below to see why.

4umbra-math · math.rs · PBR 4e §B.2.9–§B.2.10

Cancellation, and the FMA that repairs it

Subtracting two nearly equal floats is exact. The trouble is that the subtraction exposes the rounding error both operands already carried, which can be larger than the true difference. This is catastrophic cancellation, and a·b − c·d is the textbook case. It appears in every 2 × 2 determinant, every cross product, and the discriminant b² − 4ac that decides whether a ray hits a quadric.

A fused multiply-add computes a·b + c with a single rounding. So fma(a, b, −a·b) is the exact rounding error of the product a·b, which is what two_prod returns. difference_of_products (Kahan's algorithm) uses that to put the lost error of c·d back:

fn difference_of_products(a: f32, b: f32, c: f32, d: f32) -> f32 {
    let cd = c * d;
    let difference = fma(a, b, -cd);   // a·b − cd, rounded once
    let error = fma(-c, d, cd);       // exactly cd − c·d
    difference + error
}

Long sums: two_sum and CompensatedSum

two_sum does for addition what two_prod does for products, with plain operations (Knuth): s = a + b, and the exact error is recovered from s − a. CompensatedSum applies the same idea to a running sum. It carries the low-order bits each addition drops in a second variable and feeds them into the next term, so that adding many small terms to a large total does not stall.

5umbra-math · transform.rs, normal.rs · PBR 4e §3.5, §3.9–§3.10

Points, vectors and normals transform differently

Umbra has three types for three different things, as pbrt-v4 does. A Point3f is a position, so a translation moves it. A Vector3f is a direction with a length, so a translation leaves it alone (in homogeneous coordinates its w is 0). A Normal3f is perpendicular to a surface and must stay perpendicular after the surface is transformed. Multiplying it by M does not keep it perpendicular once M scales unevenly. Normals transform by the inverse transpose:

n · t = 0  ⇒  ((M−1)T n) · (M t) = nT M−1 M t = 0

That is why every Transform stores both m and m_inv. Normals need the inverse anyway, so keeping it costs nothing at run time.

6umbra-math · frame.rs, spherical.rs · PBR 4e §3.3.3, §3.8

Shading frames and spherical coordinates

A BSDF is written in a local shading frame where the surface normal is +z. In that frame cos θ is just w.z, and all the trigonometry a BSDF needs comes from reading coordinates: cos_theta, sin2_theta, cos_phi and the rest in spherical.rs. No acos is ever called.

Frame::from_z(n) builds that frame from the normal with coordinate_system, the construction of Duff et al. (2017). It produces two unit vectors, perpendicular to n and to each other, from one copysign and a handful of multiplies, and it has no singularity anywhere on the sphere:

pub fn coordinate_system(v: Vector3f) -> (Vector3f, Vector3f) {
    let sign = 1.0_f32.copysign(v.z);
    let a = -1.0 / (sign + v.z);
    let b = v.x * v.y * a;
    (
        Vector3f::new(1.0 + sign * v.x * v.x * a, sign * b, -sign * v.x),
        Vector3f::new(b, sign + v.y * v.y * a, -v.y),
    )
}
7umbra-math · octahedral.rs · PBR 4e §3.8.4

A unit vector in 32 bits

Three f32 make a unit vector 12 bytes. OctahedralVector stores it in 4. First the vector is projected onto the octahedron |x| + |y| + |z| = 1. The upper half (z ≥ 0) projects straight down onto a diamond. The lower half is folded outward over the diamond's edges into the four corners. The whole sphere then lies flat on the square [−1, 1]², and each coordinate is quantised to a u16.

8umbra-math · perspective() · used by umbra-camera · PBR 4e §5.2.2

The perspective projection

perspective(fov, n, f) is the matrix a perspective camera uses to relate camera space to screen space. It divides x and y by depth, scales them by 1 ⁄ tan(fov ⁄ 2) so that the field of view spans [−1, 1], and maps depth z ∈ [n, f] onto [0, 1]:

x′ = x ⁄ (z · tan(fov⁄2)),  z′ = f (z − n) ⁄ (z (f − n))

A ray tracer runs the map backwards. The camera takes a raster position, applies the inverse to reach camera space, and shoots a ray from the origin through that point. The depth mapping matters little here, since there is no depth buffer. What matters is the field-of-view scale.

9umbra-math · platform/libm.rs · tools/libm-bench · ADR 0022

What libm costs

umbra-math exports nineteen f32 functions of the C library, from sinf to roundf. For each it offers one of three things: a kernel of its own (sin_cos, atan2, erf, Vec4::exp, Vec4::pow), the hardware instruction (sqrt, fma, floor, ceil), or a safe wrapper that calls glibc. The figure times each function three ways on every benchmark machine:

  • glibc: the scalar function of glibc's libm.so.6, called once per element. On the GPU, CUDA's libdevice (__nv_sinf, …) takes its place.
  • umbra-math: what the crate offers today. Where it is a wrapper, it costs what glibc costs.
  • best SIMD: the fastest form there is, whatever Umbra's rules say. On the CPU that is glibc's libmvec, 8 lanes of AVX2 on x86-64 and 4 of AdvSIMD on arm64, for the transcendentals, and the vector instruction for the exact operations. On the GPU it is the approximate intrinsics (__nv_fast_sinf, ex2.approx, …). This column gives up the 1 ULP bound Umbra keeps (ADR 0022): libmvec promises 4 ULP, and the GPU's intrinsics bound only the absolute error, which near a zero of the result is thousands of ULP.

Each function maps 1024 inputs from the range a renderer gives it, the same inputs on every machine, and every result passes through black_box, so no scalar call is vectorised behind the benchmark's back. A CPU time is the median of 201 runs on one pinned core, per element. The error is the largest over the 1024 inputs, in ULPs from the correctly rounded result, taken from glibc's f64 routine.

A GPU time is throughput, not latency: a launch of 2³¹ evaluations spread over the whole device, divided by their number, in picoseconds. It says how many the GPU does per second, not how long one takes. The cheapest functions all sit on the same floor, which is the cost of the loop around them: one load and one XOR per evaluation.

To refresh a machine's results, run scripts/bench-libm.sh p620 (or r630, m2) in the dev container and commit this file. The script replaces that machine's lines in the results block at the end of this page and leaves the others alone. On the M2 the dev container is linux/arm64 (ADR 0034), so all three machines run the dev container's glibc.
