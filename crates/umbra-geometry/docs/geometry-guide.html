Umbra Geometry Guide

A renderer spends most of its time asking one question: where does this ray hit something? umbra-geometry holds the pieces that question needs: the ray itself, the box drawn around an object, the sphere and the test that finds where a ray first meets it, and the numbered handles the Scene uses to name its objects. This guide explains each one in pictures first and formulas second. It assumes only school maths.

Part I · Theory

Rays, boxes and spheres

Three shapes of thought carry this crate: a line that starts somewhere and goes on forever, a box whose sides line up with the axes, and a ball. Every question the crate answers is about how they meet.

0background · used by every section

The maths toolkit, in pictures

In plain wordsThis crate needs four ideas beyond school arithmetic: the dot product of two arrows, the formula that solves a t² + b t + c = 0, taking the smaller or larger of two numbers axis by axis, and a number stored together with its possible error. Points, vectors, matrices and normalising are already drawn in the camera guide's toolkit, and how f32 numbers round is in the math guide.

The dot product

Multiply the two arrows' xs, their ys and their zs, and add. The result is one number: the length of u times the length of v's shadow on u. An arrow dotted with itself gives its length squared, which is how the sphere test measures distance from the centre.

u·v = uxvx + uyvy + uzvz   v·v = |v|²

The quadratic and its roots

A curve a t² + b t + c is a U shape. Its roots are the t values where it crosses zero. The discriminant b² − 4ac says how many there are: positive gives two, zero gives one (the U just touches), negative gives none. A ray and a sphere meet at the roots of exactly such a curve.

t = (−b ± √(b² − 4ac)) ⁄ (2a)

Min and max, axis by axis

Given two points, take the smaller x and the smaller y: that is one corner of the box between them. The larger of each gives the opposite corner. Each axis is handled on its own, so the result need not be either of the two points.

min(p, q) = (min(px, qx), min(py, qy), min(pz, qz))

A number with error bars

Each computer operation rounds its result a little. An interval carries a lower and an upper bound that the true value is certain to lie between. Questions become safe: “is t above 0?” is answered yes only if even the low end is above 0. The math guide's section 3 shows the rules.

[a, b] + [c, d] = [a + c, b + d] (rounded outward)

A ray: a start and a direction

In plain wordsA ray is a laser pointer: a spot where it starts, o, and an arrow saying which way it points, d. Every point on the beam can be named by one number t: start at o and take t steps of the arrow. t = 0 is the start, t = 2 is two arrow-lengths along. Negative t would be behind the pointer, and that is not part of the ray.

Umbra's Ray is just those two fields. pbrt-v4's ray also carries a time and the medium it travels through; Umbra adds those with the features that read them.

pub struct Ray {
    pub o: Point3f,   // the origin
    pub d: Vector3f,  // the direction, not necessarily normalised
}

pub fn at(&self, t: f32) -> Point3f {
    self.o + self.d * t
}

Note “not necessarily normalised”. The camera makes rays of length 1, but a ray moved into a sphere's own coordinates (see section 4) can be stretched or shrunk. The hit distance t_hit is always counted in steps of the ray's own d, so the same t means the same point before and after such a move. That is why nothing needs to re-normalise the direction.

Maths used here
p(t) = o + t·d,   t ≥ 0
The point at t. Start at o, add t copies of the arrow d. Only t ≥ 0 belongs to the ray: it starts at o and goes forward. Ray::at
distance from o = t · |d|
How far that is. Each step of t moves one arrow-length. With |d| = 1 the two are the same.

Boxes that line up with the axes

In plain wordsTesting a ray against a complicated object is slow. Testing it against a plain box is fast. So renderers wrap every object in the smallest box they can find whose walls run along the x, y and z axes, an axis-aligned bounding box. Such a box needs only two corners to describe it: the one with the smallest coordinates and the one with the largest.

A box can be built from any two opposite corners in any order: Bounds3f::new sorts them, axis by axis, with min and max. So new(a, b) and new(b, a) give the same box, and so does a pair of the box's other opposite corners.

pub fn new(p1: Point3f, p2: Point3f) -> Self {
    Self { p_min: p1.min(p2), p_max: p1.max(p2) }
}

Bounds2f is the flat version, a rectangle, with the same new. It adds one operation, lerp: give it two fractions (tx, ty) between 0 and 1 and it returns the point that far across the rectangle. (0, 0) is p_min, (1, 1) is p_max, (½, ½) is the middle. The camera uses a Bounds2f for its screen window, and its filter uses lerp to place the cells of its table (see the camera guide).

Maths used here
pmin = min(p₁, p₂),   pmax = max(p₁, p₂)
The box from two corners. Smaller of each coordinate for one corner, larger for the other. Bounds3f::new, Bounds2f::new, via Point3f::min and max
corner(i) = (i&1 ? xmax : xmin, i&2 ? ymax : ymin, i&4 ? zmax : zmin)
Corner number i. “i & 2” means “is the 2s bit of i set?”. corner, private to bounds.rs
lerp(t, a, b) = (1 − t)·a + t·b
Blend. t = 0 gives a, t = 1 gives b, in between slides along the straight line. lerp in umbra-math
Bounds2f::lerp(t) = (lerp(tx, xmin, xmax), lerp(ty, ymin, ymax))
A point by fractions. One blend per axis. Bounds2f::lerp

Moving a box, and why it grows

In plain wordsA sphere is defined sitting at the centre of its own little world, with its own box from −r to r on every axis. To place it in the scene, a transform slides, turns or stretches it. Turning the box tilts it, and a tilted box no longer lines up with the axes. So Umbra moves all eight corners and draws a fresh axis-aligned box around them. That new box is safe (it contains everything) but it can be bigger than needed.
pub fn transform(&self, t: &Transform) -> Self {
    let first = t.apply(self.corner(0));
    (1..8).fold(Self::new(first, first), |bounds, i| {
        let p = t.apply(self.corner(i));
        Self { p_min: bounds.p_min.min(p), p_max: bounds.p_max.max(p) }
    })
}

The code starts with a box that is just the first moved corner, then widens it to take in each of the other seven. For a sphere this gives Sphere::bounds:

pub fn bounds(&self) -> Bounds3f {
    let r = self.radius;
    Bounds3f::new(Point3f::new(-r, -r, -r), Point3f::new(r, r, r))
        .transform(&self.render_from_object)
}

A box that is too big is never wrong, only slower: a ray that hits the box but misses the sphere costs one wasted sphere test. A box that is too small would be wrong, because a ray could miss the box and skip a sphere it actually hits. pbrt-v4 makes the same trade.

Maths used here
ci′ = M ci,   i = 0 … 7
Move each corner with the transform's matrix M. Transform::apply in umbra-math
pmin′ = mini ci′,   pmax′ = maxi ci′
The new box: the smallest and largest coordinate over all eight, axis by axis. Bounds3f::transform
width′ = 2r (|cos θ| + |sin θ|)
How much it grows when a cube of side 2r turns by θ about one axis. At θ = 45° that is 2r · √2. The sphere itself still needs only 2r.
4umbra-geometry · sphere.rs · Sphere::intersect, QuadricIntersection · PBR 4e §6.2.2

Where a ray meets a sphere

In plain wordsA point is on a sphere when its distance from the centre equals the radius. Walk along the ray and keep asking “how far am I from the centre?”. That distance shrinks, then grows again. It equals the radius at most twice: once going in, once coming out. Writing that down gives a quadratic in t, the kind from school, and its two roots are the two crossings. The nearer crossing ahead of the ray is the hit.

Write the ray's point as o + t d and ask that its squared length be r². Multiplying out with the dot product gives three numbers a, b, c that depend only on the ray and the radius. The quadratic formula then gives the roots. Of the two, the code keeps the smaller as t₀.

Which root is the hit? Only crossings with t above 0 (ahead of the origin) and at most tmax count. tmax is how far the caller cares to look, usually the distance to the nearest hit found so far. The diagram shows the four cases:

pub fn intersect(&self, ray: &Ray, t_max: f32) -> Option<QuadricIntersection> {
    let oi = self.render_from_object.apply_inverse(Point3fi::from(ray.o));
    let di = self.render_from_object.apply_inverse(Vector3fi::from(ray.d));
    let (t0, t1) = self.quadratic_roots(oi, di)?;          // None: the line misses
    if t0.upper_bound() > t_max || t1.lower_bound() <= 0.0 {
        return None;                                            // too far, or all behind
    }
    let t_shape_hit = if t0.lower_bound() > 0.0 { t0 } else { t1 };
    if t_shape_hit.upper_bound() > t_max {
        return None;
    }
    let t_hit = f32::from(t_shape_hit);
    let p_hit = Point3f::from(oi) + Vector3f::from(di) * t_hit;
    let p_obj = p_hit * (self.radius / distance(p_hit, Point3f::default()));
    Some(QuadricIntersection { t_hit, p_obj })
}

The i in oi, di, Point3fi stands for interval: every number carries its error bars. That is the subject of section 5; for now read lower_bound() and upper_bound() as the number itself. The answer, a QuadricIntersection, holds t_hit and the hit point p_obj in the sphere's object space. pbrt-v4's version also holds the angle φ, which only partial spheres and the full surface interaction need; Umbra will add it with them.

The last line nudges the hit point onto the sphere. Rounding leaves phit a hair inside or outside. Scaling it so its distance from the centre is exactly r puts it back on the surface, far more precisely than the ray maths alone could.

Rounding errors, kept in check

In plain wordsComputers round every result to a nearby number they can store. Usually that doesn't matter. In a hit test it can: a ray leaving a surface may “hit” the very surface it is leaving, because rounding put its start a hair behind it. The result is black speckles in the image. Umbra avoids this in three ways: it computes the discriminant in a form that rounds less, it carries error bars on every number and only says “ahead of the ray” when it is sure, and it starts moved rays slightly forward, past their own error.

1 · A discriminant that rounds less

2 · Error bars on t

The error bars start at the ray. Point3fi::from(ray.o) makes an interval of zero width (the origin is taken as exact), and apply_inverse widens it by the rounding of the matrix maths. Every +, × and sqrt on Intervals rounds its lower bound down and its upper bound up, so the true value never escapes. At the end, f32::from(t_shape_hit) takes the interval's midpoint as the answer. The rules of interval arithmetic are in the math guide's section 3.

3 · Moving a ray without moving it backwards

pub fn transform(&self, t: &Transform) -> Self {
    let mut o = t.apply(Point3fi::from(self.o));
    let d = t.apply(self.d);
    let length_squared = d.length_squared();
    if length_squared > 0.0 {
        let dt = dot(d.abs(), Vector3f::from(o.error())) / length_squared;
        o += Vector3fi::from(d * dt);
    }
    Self::new(Point3f::from(o), d)
}

ULP(x) ≈ |x| · 2⁻²³
The gap between neighbouring f32 numbers near x. It grows with x. When b² ≈ 4L² is huge, its gap can exceed the whole discriminant.
b² − 4ac = 4a (r² − |v|²) = 4a (r + |v|)(r − |v|)
Same value, safer form. r² − |v|² is the squared half-length of the chord inside the sphere (Pythagoras). quadratic_roots
[a, b] ∘ [c, d] ⊆ [low ↓, high ↑]
Interval arithmetic. Any operation ∘ gives an interval containing every possible result, with the low end rounded down and the high end rounded up. Interval in umbra-math
ahead ⇔ low(t₀) > 0;   in reach ⇔ high(t) ≤ tmax
Safe comparisons. lower_bound, upper_bound
e = half-width of each component of o

Numbers instead of pointers

In plain wordsScene objects point at each other: a shape names its material, a light names its shape. In many programs that “naming” is a memory address. Umbra instead keeps all objects of one type in one numbered list, an arena, and names an object by its position in the list. That name is a Handle. Numbers can be copied to another machine or a GPU and still mean the same thing; memory addresses can't.

A Handle<T> is a u32, and nothing more at run time:

#[repr(transparent)]
pub struct Handle<T> {
    index: u32,
    target: PhantomData<fn() -> T>,   // zero bytes: only remembers T for the compiler
}

let h: Handle<Sphere> = Handle::new(1);
let i: usize = h.into();   // From<Handle<T>> for usize: index into a slice

new makes one from an index, index() gives the number back, and usize::from turns it into a slice index. Only the Scene builder mints handles (ADR 0008), so a handle always names an object that was really added to that Scene. A handle from one Scene used in another is not caught: the type system knows the object type, not which Scene. ADR 0008 lists that as an accepted cost. Following a handle costs one indexed load and one bounds check.

This crate holds Handle even though it has no arena: the hit records it will produce will name their Material, area Light and Medium by handle, and the type belongs to the lowest crate that needs it.

Part II · Implementation

How the crate is built

umbra-geometry is a core crate: #![no_std] without alloc, no f64, no trait objects, so the same code runs on the CPU and, compiled for nvptx64, on the GPU (ADR 0014, ADR 0015, ADR 0028). It covers parts of PBR 4e chapters 3, 6 and 7, and so far only what the GPU tracer bullet (#126) and the camera (#77) need.

8umbra-geometry · sphere.rs · ADR 0028, ADR 0026

One sphere test for the CPU and the GPU

In plain wordsUmbra renders on processors and on graphics cards. Rather than write the sphere test twice, once per machine, it writes it once as a plain function: values in, a value out, nothing shared, nothing allocated. The CPU calls it directly. On the GPU, NVIDIA's OptiX ray tracer asks “does this ray hit your custom shape?”, and Umbra answers by calling the very same function.

ADR 0028's rule is “the core works on values”: each step of a path is a function that takes and returns Copy values and never touches a queue, a buffer or a thread index. Sphere::intersect fits it: it reads a Sphere and a Ray, both Copy, and returns an Option<QuadricIntersection>. It follows pbrt-v4's BasicIntersect operation for operation, interval arithmetic included, so the GPU gets the same guarantee that no hit is reported behind the ray's origin. umbra-gpu's GPU tests check the GPU's answers against Sphere::intersect run on the CPU.

9umbra-geometry · bounds.rs, sphere.rs · ADR 0028

Fixed byte layouts

In plain wordsSpheres and boxes are stored in the Scene and copied to the graphics card as raw bytes, without translation. That only works if both machines agree on where each field sits inside those bytes. Rust normally may reorder fields as it likes, so Umbra pins the order with #[repr(C)] and writes down the expected sizes and positions as checks that stop the build if they are ever wrong.
#[repr(C)]
pub struct Sphere {
    render_from_object: Transform,
    radius: f32,
}

const _: () = {
    use core::mem::offset_of;
    assert!(size_of::<Sphere>() == 272, "...");
    assert!(align_of::<Sphere>() == 16, "...");
    assert!(offset_of!(Sphere, render_from_object) == 0, "...");
    assert!(offset_of!(Sphere, radius) == 256, "...");
};

The const _ block runs at compile time, on both targets. If a field were added, reordered or resized, the build would stop with the message in the assertion rather than the GPU quietly reading the wrong bytes. Bounds3f has the same kind of block: 24 bytes, aligned to 4, p_min at byte 0 and p_max at 12. Ray is different: it is made fresh per Pixel Sample and never stored in an arena, so it keeps Rust's default layout. Bounds2f isn't stored in an arena either and has no layout block.

10umbra-geometry · handle.rs

A handle's traits, written by hand

In plain wordsA handle is a number, so copying, comparing and sorting it should always work, whatever it points to. Rust's shortcut for adding those abilities, #[derive], would quietly demand them of the pointed-to type too. So handle.rs spells each one out, comparing just the numbers.
// Implemented by hand: deriving them would require `T` to implement them
// too, and a handle is a `u32` whatever it points to.
impl<T> Clone for Handle<T> { fn clone(&self) -> Self { *self } }
impl<T> Copy for Handle<T> {}
impl<T> PartialEq for Handle<T> { fn eq(&self, other: &Self) -> bool { self.index == other.index } }
// … Eq, PartialOrd, Ord, Hash, Debug the same way

The marker field is PhantomData<fn() -> T>, not PhantomData<T>. The plain form would tell the compiler that a handle owns a T, which affects whether a handle may cross threads. The function-pointer form says only “this produces a T”, so a handle is safe to share between threads whatever T is, as a u32 should be. The conversion to usize uses TryFrom with an expect, since a u32 always fits in a usize on Umbra's 64-bit targets.

12umbra-geometry · roadmap

Not here yet

pbrt-v4 has much more geometry than this. The crate grows as the milestones need it; the Shapes arrive with #79 Emissive spheres visible to the camera.

  • The ray's time and medium, for motion blur and participating media, and ray differentials, for texture filtering.
  • Partial spheres (zmin, zmax, phimax), the angle phi in QuadricIntersection, and the surface interaction a hit becomes (pbrt-v4's InteractionFromIntersection, SurfaceInteraction), with normals, partial derivatives and the error bounds used to spawn the next ray.
  • The other Shapes (triangles, bilinear patches, cylinders, disks, curves), shape sampling for lights, and the closed enum ShapeKind (ADR 0006).
  • The rest of pbrt-v4's box operations: union, intersection, inside tests, surface area, offset, bounding sphere, and the ray–box slab test (Bounds3::IntersectP) that a BVH relies on.
  • The BVH: its node layout and traversal.
