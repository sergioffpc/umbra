Umbra CPU Guide

A Worker that renders on a CPU is handed a Work Unit, one Tile for one Pass, and must send back its Work Result: two sums per pixel. umbra-cpu is the piece in between. It shares the Tile's rows among the cores of one machine, computes each Pixel Sample with the core's own code, and makes sure the answer does not depend on how many cores took part. What a Work Unit and a Work Result are, and what happens to the Work Result next, is told in the Umbra Render Guide. This guide explains the CPU's part in pictures first and code second. It assumes only school maths.

Part I · Theory

How a CPU renders a Work Unit

A Work Unit holds thousands of Pixel Samples, and a CPU has a few dozen threads. This part explains where the crate sits among the others, how it shares a Work Unit among the threads, and why the sharing cannot change a single bit of the answer.

0umbra-cpu · README.md · ADR 0033 · arc42 §5.1

One contract, one renderer per Render Device

In plain wordsA Render Device is the hardware a Worker renders on: the cores of one machine, or one GPU. Both must answer the same question, “here is a Work Unit, give me its Work Result”, so the question and the answer live in one crate, umbra-render, and each Render Device has a crate of its own that answers it. This crate is the CPU's.

The CPU's renderer takes one Work Unit at a time; several run at once on the Worker's threads:

pub fn new(scene: &'s Scene, options: &RenderJobOptions) -> Result<Self, Error>;
pub fn render(&self, unit: WorkUnit, cancel: &Cancellation) -> Rendered;

The GPU's takes the Work Units it keeps in flight as one batch, and returns one Rendered for each, or an error when the GPU fails. Both answer with the same Rendered of the same contract.

umbra-cpu brings two things the contract does not have: rayon, the library that shares work among threads, and the pixel loop that calls umbra_integrators::evaluate_pixel_sample once per Pixel Sample. The integrator itself, and the composition of its steps for one Pixel Sample, stay in the no_std core, where the GPU's programs reuse them. The CPU calls that composition as it is.

Rendering one Work Unit

In plain wordsRendering a Work Unit means: for every pixel of the Tile, compute that Pass's Pixel Samples one after another, and add each into the pixel's sums. The Tile's rows are shared out among the CPU's threads. A thread always takes whole rows, so a pixel's sums are never split between threads, and the answer is the same with 1 thread or 64. Before starting each row, a thread checks whether someone asked to stop.
// PixelLoop::render, slightly shortened
let bounds = job.decomposition.tile_bounds(unit.tile);
let samples = job.decomposition.sample_indices(unit.pass);
let mut pixels = vec![PixelSum::default(); bounds.area()];   // the one allocation
let rows = pixels.par_chunks_mut(bounds.width()).zip(bounds.min.y..bounds.max.y);
let outcome = rows.try_for_each(|(row, y)| {
    self.render_row(job, row, Point2i::new(bounds.min.x, y), &samples)
});
match outcome {
    Ok(()) => Rendered::Done(WorkResult::new(unit, pixels)),
    Err(Cancelled) => Rendered::Cancelled,
}

par_chunks_mut is rayon's way of saying “cut this list into rows and let the threads take them”. Each row gets its own copy of the sampler, a small value, and computes each pixel with a fold:

samples.clone().fold(PixelSum::default(), |mut sum, sample_index| {
    let id = PixelSampleId { pixel, sample_index };
    sum += evaluate_pixel_sample(&self.0, &job.view, id, state);
    sum
})

evaluate_pixel_sample lives in umbra-integrators. It resets the sampler for this pixel and sample index, picks the wavelengths, asks the camera for a ray, asks the integrator for the light along it, and converts that light to sensor RGB with its filter weight: a FilmSample. How, is told in the integrators guide and the camera guide. Because the sampler is reset at every Pixel Sample, the row's sampler copy carries nothing over from one sample to the next.

Why the thread count cannot show. A Work Result is exact on one machine with one binary (ADR 0022, render guide, section 5). The sampler and the integrator make each Pixel Sample a pure function of the Scene, the seed, the pixel and the sample index. This crate adds the other two rules: each pixel adds its Pixel Samples in ascending sample index, and threads share out rows, never the samples of one pixel.

Stopping early. Cancellation, from umbra-render, wraps an AtomicBool, a true/false flag that many threads can read and write safely. cancel() sets it, and render_row reads it before doing any work. A row already running finishes first, so a render stops within one row's time. Then the whole render returns Rendered::Cancelled, and whatever was computed is dropped: a Work Result is all of its Work Unit or nothing.

Several at once. render takes &self and the Renderer is Sync, so a Worker can render several Work Units at once from different threads. Each render uses rayon's current pool, so the pool the caller installs sets the thread count. umbra-cluster's CPU Local Worker runs its renders on its own pool, and asks for about two Work Units per eight threads (render guide, section 3).

Renderer::new prepares what every render shares: the Decomposition, the sampler's randomisation for the Render Job's seed (computed once), and the Scene's integrator. It fails only as Decomposition::new does, with umbra-render's Error. render then builds the Render Job's Halton sampler and hands the Work Unit to the integrator. Both are told in section 3. A Work Unit that is not one of the Render Job's is a bug, and render panics.

Part II · Implementation

How the crate is built

umbra-cpu is a std crate, outside the no_std core: it may allocate and use threads. It depends on umbra-render for the contract, on umbra-integrators, umbra-sampling, umbra-scene and umbra-math, and on rayon. umbra-cluster depends on it (arc42 §5.1, ADR 0033).

Design decisions

In plain wordsMost of what's interesting here is what the code is careful not to do. It makes one flexible, slower call per Work Unit and millions of fast, fixed ones inside it. And it reserves memory once per Work Unit and never per Pixel Sample.

One dyn call per Work Unit, a static loop inside

trait Integrator: Sync + fmt::Debug {
    fn render(&self, job: &Job<'_>, unit: WorkUnit) -> Rendered;
}
struct PixelLoop<I>(I);
impl<I: RayIntegrator + Sync + fmt::Debug> Integrator for PixelLoop<I> { /* … */ }

// in Renderer::new
integrator: Box::new(PixelLoop(scene.integrator())),

The core avoids dyn on the per-ray path: there, every choice is a closed enum (ADR 0006). A seam called at most once per Work Unit may be dyn, because one indirect call is nothing next to thousands of Pixel Samples. So the Renderer holds a private Box<dyn Integrator>, and behind it PixelLoop<I> is generic over the core's RayIntegrator: the compiler builds one specialised pixel loop per integrator type. Integrators whose Pixel Samples are not one ray each, such as BDPT or SPPM, will bring CPU drivers of their own behind the same seam.

Memory: per Work Unit, never per Pixel Sample

Asking the operating system for memory is slow and, with many threads, contended. ADR 0008 allows it per Render Job and per Work Unit, never per Pixel Sample. The sampler's digit permutations, a table that depends only on the seed, are built once by Renderer::new into a private Randomization enum (None, PermuteDigits, Owen), and lent to each render's Halton sampler as a borrowed view. A test in crates/umbra/tests/allocation.rs counts heap blocks while rendering a Work Unit with 4 and with 8 Pixel Samples per pixel, and checks that the counts are equal.

The sampler is built for the Render Job's full Pixel Samples per pixel, not for the Pass. Pixel Sample 5 of a pixel is the same Pixel Sample whether it falls in Pass 1 or, with bigger Passes, in Pass 0: the Passes only group the samples, they never change them.

How it is tested

In plain wordsThe tests treat the crate as a black box with one door: Work Units go in through the Renderer and Work Results come out. They use a camera-only Scene of 40 × 24 pixels, which renders black: no light reaches the camera, but every Pixel Sample still gets its filter weight.
  • renderer.rs, the Renderer's door:
    • a_camera_only_scene_renders_black: 3 × 2 Tiles, every sum black, every weight positive.
    • a_tile_cut_short_by_the_image_has_only_its_pixels: Tile 5 is 8 × 8.
    • work_results_do_not_depend_on_the_thread_count: Work Results on 1 and 4 threads are equal, and so are the single-Pass Film hashes.
    • a_render_is_a_pure_function_of_its_work_unit: rendering the Work Units again, in reverse order, gives equal Work Results.
    • a_cancelled_render_returns_no_work_result: cancel first, get Rendered::Cancelled.
  • scenes.rs builds the Scene with SceneBuilder, the options (seed 0, 16-pixel Tiles), and render_all.
  • crates/umbra/tests/allocation.rs: the counting-allocator test of section 3, rendering through umbra_cpu::Renderer.

The thread-count test compares single-Pass Film hashes only, for the reason in section 5 of the render guide. Run them with cargo nextest run -p umbra-cpu.
