Umbra GPU Programs Guide

A graphics card can run thousands of small programs at once. umbra-gpu-programs holds the programs Umbra gives it. They are not a second renderer written in another language: they call the very same Rust code the CPU runs, compiled a second time for the GPU. This guide explains, in pictures first, what that means and how the crate does it. It assumes no GPU or systems background.

Part I · Concepts

Running the same Rust on a GPU

Three questions run through this part. How can one piece of Rust code run on two very different chips? How does a GPU split a job between thousands of threads? And how do the CPU and the GPU agree on the data they pass each other?

0background · used by every section

The words, in pictures

In plain wordsA GPU is a chip with very many small, simple workers. You give it one small program, and it runs that program many times at once, once per piece of data. Everything in this crate follows from that one idea. The cards below introduce the words; the table after them is a quick reference.

CPU and GPU, host and device

The CPU is the computer's main chip. The GPU (graphics card) is a second chip with its own memory. Code on the CPU side is called the host; code on the GPU is the device. Umbra's GPU is an NVIDIA card, and in this project it is a Render Device: hardware a Worker renders on (GLOSSARY.md).

Kernel, thread, launch, launch index

A kernel is a program the GPU runs. A launch is the host saying “run it N times now”. Each run is a thread, and each thread gets a number, its launch index i. All threads run the same code; the index is how each one knows which piece of data is its own. The number of threads is the launch width.

Target, nvptx64, PTX

A compiler target names the chip a build is for. The CPU's is x86_64-unknown-linux-gnu; NVIDIA GPUs' is nvptx64-nvidia-cuda, “nvptx64” for short. For that target rustc does not emit machine code. It emits PTX: a readable assembly text that NVIDIA's driver finishes compiling for whichever GPU is plugged in.

no_std, on a GPU

Rust's standard library std assumes an operating system: files, a heap, printing. A GPU thread has none of that. A crate marked #![no_std] uses only core, the part of Rust that needs nothing from an OS. Umbra's core crates were written that way from the start (ADR 0014), which is why they compile for the GPU at all.

1umbra-gpu-programs · lib.rs · Cargo.toml · ADR 0028, ADR 0014

One core, two machines

In plain wordsUmbra does not write its rendering maths twice, once for the CPU and once for the GPU. It writes it once and asks the Rust compiler to build it twice. umbra-gpu-programs is the small extra piece the GPU build needs: the entry points the GPU starts from. On the CPU build the programs are switched off, and the crate keeps only the few structs the CPU and the GPU pass each other, so the host can use the very same definitions.

lib.rs makes the switch. #![cfg_attr(target_arch = "nvptx64", …)] applies an attribute on the GPU build only, and #[cfg(target_arch = "nvptx64")] on a module keeps or drops it, depending on the target:

// The GPU's programs on `nvptx64`, `no_std` there; on the host, the layout
// they share with `umbra-gpu` alone (ADR 0028, ADR 0033).
#![cfg_attr(target_arch = "nvptx64", no_std)]
// `ptx-kernel` entry points and inline PTX, on `nvptx64` only: the only
// unstable features of the workspace (ADR 0027).
#![cfg_attr(target_arch = "nvptx64", feature(abi_ptx, asm_experimental_arch))]
// No `f64` on the GPU (ADR 0028): `clippy.toml` lists it.
#![warn(clippy::disallowed_types)]

mod launch;
#[cfg(all(target_arch = "nvptx64", feature = "math-program"))]
mod math;
#[cfg(feature = "math-program")]

Cargo.toml lists the core crates as dependencies on every target: umbra-geometry, since the layout converts its Ray into a RayRecord, and umbra-camera, umbra-integrators, umbra-sampling, umbra-spectrum and umbra-math, since the wavefront's records hold the core's camera, filter, sensor, integrator and digit permutations, and the stages run the core. The library is an ordinary rlib, which umbra-gpu depends on for the layout. umbra-gpu's build script asks for a cdylib instead, with cargo rustc --lib --crate-type cdylib, which is what the nvptx64 target links into one PTX module (ADR 0033).

Why does the core compile for the GPU at all? Because ADR 0014 wrote it for that from day one: no_std without alloc, f32 only, closed enums instead of trait objects, no recursion. ADR 0028 adds that the core works on values: a core function takes and returns Copy values and never sees a queue, a buffer or a thread index. The GPU-specific parts (thread indices, buffers, OptiX) all live here, in the programs.

Two unstable compiler features are needed, so the workspace builds with a pinned nightly rustc (ADR 0027): abi_ptx for extern "ptx-kernel" entry points, and asm_experimental_arch for inline assembly on nvptx64. umbra-gpu-programs is the only crate allowed to switch on unstable features, and only on its nvptx64 build, so a host build compiles it on stable features alone; scripts/check.sh fails if any other crate does.

2umbra-gpu-programs · programs.rs · __raygen__trace, read_ray, write_hit · optix.rs · launch_index_x

Programs, launches and the launch index

In plain wordsThe host puts a list of rays in GPU memory and starts one thread per ray. Every thread runs the same function. The first thing it does is ask “what is my number?”. Thread 7 then reads ray 7, works on it, and writes its answer in slot 7 of a results list. No thread touches another's slot, so they never get in each other's way, and the order in which they finish does not matter.

Here is the ray-generation program in full, from programs.rs. Read it as “what one thread does”:

extern "ptx-kernel" fn __raygen__trace() {
    let params = launch_params();          // the host's settings (section 4)
    let i = optix::launch_index_x();       // which thread am I?
    if i >= params.count {
        return;                             // no ray for me
    }
    let ray = read_ray(params.rays, i);    // my ray
    let trace_ray = TraceRay { origin: ray.o, direction: ray.d, tmin: 0.0, tmax: f32::MAX };
    let [t, kind] = optix::trace(params.handle, trace_ray, [0, HitKind::Miss as u32]);
    write_hit(params.hits, i, HitRecord { t: f32::from_bits(t), kind });   // my slot
}

extern "ptx-kernel" tells rustc to emit this function as a GPU entry point, the kind a launch can start. #[unsafe(no_mangle)] (above it in the source) keeps its name exactly __raygen__trace in the PTX, because the host looks it up by that name, and OptiX reads the prefix __raygen__ to know what kind of program it is.

The rays and hits are not Rust slices. The host passes their device addresses: plain 64-bit numbers saying where in GPU memory the arrays start. read_ray turns the address into a pointer, steps i records forward with wrapping_add, and reads one RayRecord. write_hit does the same for a HitRecord. Those two reads and writes are unsafe: the compiler cannot check the host's promise that the arrays are long enough (section 12).

Only the x part of the launch index is read. OptiX launches can be up to three-dimensional (width × height × depth), but a list of rays needs one dimension.

Maths used here
address(ray i) = rays + i × 24
Finding record i. A RayRecord is 24 bytes (six f32s), so record i starts 24·i bytes after the first. (rays as *const RayRecord).wrapping_add(i as usize)
address(hit i) = hits + i × 8
The same for results. A HitRecord is 8 bytes: t and kind. write_hit
active threads = min(width, count)
The guard. Threads with i ≥ count return before touching memory, so no thread reads or writes past the arrays.
3umbra-gpu-programs · programs.rs · __miss__trace, __closesthit__trace, __intersection__sphere · optix.rs · trace, set_payload · ADR 0026

OptiX programs: one ray's trip

In plain wordsFinding what a ray hits is the slow part of ray tracing, and NVIDIA GPUs have special hardware for it. OptiX is the library that drives that hardware. You don't write one big program for OptiX; you write a few small ones and OptiX calls each at the right moment: “start here”, “test this shape”, “you hit something”, “you hit nothing”. The answer travels back in two small numbers called the payload.

The four kinds of program. OptiX recognises a program by its name's prefix. The crate has one of each that the tracer bullet of #126 needs, tracing one triangle and one sphere:

  • __raygen__trace: ray generation, where a thread starts (section 2).
  • __intersection__sphere: intersection. It reads the Sphere from its shader binding table record, builds a core Ray from the ray's origin and direction in the sphere's own space (object_ray_origin, object_ray_direction), calls sphere.intersect(&ray, optix::ray_tmax()), and on a hit calls optix::report_intersection(hit.t_hit). OptiX keeps the report only if t lies inside the ray's interval.
  • __closesthit__trace: closest hit, once, for the nearest accepted hit. optix::hit_primitive() says whether it was a built-in triangle (OptiX's hit kinds 0xFE and 0xFF, front and back face) or a custom primitive, which can only be the sphere here. It writes the hit's distance, optix::ray_tmax(), as raw bits into payload 0 and the HitKind into payload 1.
  • __miss__trace: miss, when nothing was hit. It sets payload 1 to HitKind::Miss; payload 0 keeps its starting value, so t on a miss means nothing.

The payload is how the programs answer ray generation: two 32-bit registers that ride along with the ray, set with optix::set_payload(PAYLOAD_T, …) and optix::set_payload(PAYLOAD_KIND, …). A register holds a u32, so the distance t goes in as to_bits() and comes back with f32::from_bits: the same 32 bits, re-labelled, not converted. The host's pipeline must declare exactly two payload values; umbra-gpu does.

tmax is f32::MAX, not infinity. The ray is followed from tmin = 0 to tmax, and OptiX's validation mode reports an infinite tmax as an invalid ray, so the program uses the largest finite f32.

Rules used here
PAYLOAD_T = 0, PAYLOAD_KIND = 1
Two payload registers. They match the pipeline's two payload values; optix::trace passes both in and gets both out.
Miss = 0, Triangle = 1, Sphere = 2
HitKind, #[repr(u32)]. Stored as its number in HitRecord::kind; the host converts it back and rejects any other value, since device memory may hold any bits.
t = f32::from_bits(payload 0)
Bits, not a conversion. to_bits and from_bits move the exact 32 bits of the float through an integer register.
0 ≤ t ≤ tmax = f32::MAX
The ray's interval. Finite, because OptiX rejects an infinite tmax. In an intersection program ray_tmax() is the closest hit so far, so Sphere::intersect only looks for nearer ones.
each built-in: some program types only
Checked when the module is created. Calling, say, report_intersection from a miss program makes OptiX refuse the whole module on the host, not fail at run time.

Talking to the host: shared layouts

In plain wordsThe CPU and the GPU pass each other raw bytes, not Rust values. For that to work, both must agree exactly where each field sits: “the ray count is the 4 bytes starting at byte 24”. Umbra writes each shared struct once, fixes its layout with #[repr(C)], and has the compiler check every byte position. If either side ever disagreed, the build would fail instead of the GPU reading garbage.

Launch parameters are OptiX's way to hand every thread the same small block of settings. The pipeline names a variable, here params, and OptiX copies the host's bytes into it before the launch. The variable lives in the GPU's constant memory (.const in PTX): read-only during a launch and cheap when every thread reads the same address. rustc cannot put a Rust static there, so programs.rs declares it in assembly, sized by the compiler:

mod params {
    use crate::launch::LaunchParams;
    use crate::wavefront::WavefrontParams;

    const SIZE: usize = if size_of::<LaunchParams>() > size_of::<WavefrontParams>() {
        size_of::<LaunchParams>()
    } else {
        size_of::<WavefrontParams>()
    };
    ...                                   // both at most 8-byte aligned, asserted
    core::arch::global_asm!(
        ".visible .const .align 8 .b8 params[{size}];",
        size = const SIZE,
    );
}

Rust can't read that variable as a struct either, so launch_params() reads it field by field, each at the offset the compiler computes with offset_of!:

fn launch_params() -> LaunchParams {
    LaunchParams {
        handle: optix::launch_param_u64::<{ offset_of!(LaunchParams, handle) }>(),
        rays: optix::launch_param_u64::<{ offset_of!(LaunchParams, rays) }>(),
        hits: optix::launch_param_u64::<{ offset_of!(LaunchParams, hits) }>(),
        count: optix::launch_param_u32::<{ offset_of!(LaunchParams, count) }>(),
    }
}

The four fields: handle names the scene to trace (OptiX calls it a traversable handle; the host built it), rays and hits are the device addresses of the two arrays, and count is the number of rays. A RayRecord is an origin and a direction as plain [f32; 3] arrays; a HitRecord is the distance t and the HitKind as a u32.

Maths used here
8 + 8 + 8 + 4 = 28 → 32
Size with padding. A struct's size rounds up to a multiple of its largest alignment, 8 for u64. size_of::<LaunchParams>() == 32, asserted.
offsets 0, 8, 16, 24
Field positions. #[repr(C)] keeps fields in written order, each at the next multiple of its alignment. offset_of!(LaunchParams, count) == 24, asserted.
3 × 4 + 3 × 4 = 24  ·  4 + 4 = 8
The records. RayRecord is 24 bytes with d at 12; HitRecord is 8 bytes with kind at 4. No padding in either.
5umbra-gpu-programs · stages.rs · __raygen__camera, __raygen__film · wavefront.rs · WavefrontParams, DeviceSlice · ADR 0026, ADR 0028

The wavefront's stages: a Pixel Sample in two launches

In plain wordsThe tracer bullet gives each thread one ray. The renderer gives each thread one Pixel Sample, and splits the work on it into stages, one program each. The host launches the camera stage over every Pixel Sample of a batch of Work Units, then the film stage over all of them again. What one stage leaves for the next waits in a queue in GPU memory, one slot per Pixel Sample. Both stages call the same core functions the CPU calls for a Pixel Sample; only the order of the work is the GPU's own.

The film stage in full, from stages.rs, without its #[expect] and #[unsafe(no_mangle)] lines:

extern "ptx-kernel" fn __raygen__film() {
    let params = wavefront_params();                 // the whole WavefrontParams
    let i = optix::launch_index_x();               // which Pixel Sample am I?
    let view = params.scene.as_ref()[0].view();      // the core's SceneView
    let queue = params.queue;
    let lambda = SampledWavelengths::from_parts(
        queue.lambda.read(i),
        SampledSpectrum::from(queue.pdf.read(i)),
    );
    let rgb = view
        .sensor()
        .to_sensor_rgb(SampledSpectrum::from(queue.radiance.read(i)), &lambda);
    params.film_samples.write(i, FilmSampleRecord {
        rgb: [rgb.r, rgb.g, rgb.b],
        weight: queue.filter_weight.read(i),
    });
}

The parameters, read whole. The tracer's programs read LaunchParams field by field with ld.const (section 4). A WavefrontParams is 128 bytes of nested records, so wavefront_params reads it in one go instead: optix::launch_params_address converts the address of params in constant memory into a generic one with cvta.const.u64, and the stage reads a WavefrontParams from there. params is now sized for the larger of the two structs.

Tables through DeviceSlice. Each field of WavefrontParams is a DeviceSlice<T>, a device address and a length that the host made. On nvptx64, a DeviceSlice<T> is AsRef<[T]>, so params.scene.as_ref()[0] is the SceneRecord, and SceneRecord::view builds the core's SceneView over it. The filter's and the sensor's tables in that record are DeviceSlice<f32>s, which the core reads as it reads a Vec on the CPU. The queue's slices are read and written value by value with read(i) and write(i, value), each checking i against the length.

Which Pixel Sample. In the camera stage, thread i finds its Work Unit with unit_of, a binary search for the last WorkUnitRecord whose first Pixel Sample is not after i; WorkUnitRecord::pixel_sample then gives its pixel and sample index. Each thread builds its own sampler from the SamplerRecord (SamplerRecord::sampler, a Halton sampler) and starts it at that Pixel Sample, so it draws the same numbers the CPU draws for the same Pixel Sample. It keeps the wavelengths with SampledWavelengths::to_parts, which the film stage turns back with from_parts.

So far a path is its camera ray. The camera stage calls the integrator's li in one step. The stages that split li, intersection and shading, arrive with the Shapes and lights that need them (section 14).

Maths used here
size(params) = max(32, 128) = 128
One variable for every launch. programs.rs sizes params for the larger of LaunchParams and WavefrontParams, and asserts that neither needs more than its 8-byte alignment.
launch width = Pixel Samples in the batch
One thread per Pixel Sample. The host launches exactly that many threads for each stage, so every i has a Pixel Sample.
address(lambda i) = lambda + 16 i
Finding slot i. A [f32; 4] is 16 bytes. DeviceSlice::read and write check i < length first; a failed check panics, which traps (section 7).
6umbra-gpu-programs · math.rs · math_launch.rs · __raygen__math, MathFunction, MathParams · #146

The math program: the GPU's maths, checked

In plain wordsOn the GPU, sin, exp and friends come from NVIDIA's maths library, not from the one the CPU uses. They give slightly different answers in the last digit or so. To know how different, the tests need the GPU to compute, say, expf for four million chosen inputs. The math program does exactly that: each thread takes one input, calls the same umbra_math function the renderer calls, and writes the answer. The host then compares every answer with the CPU's.

The math program is a second ray-generation program. It reuses everything the tracer already has: the same pipeline, the same params variable, the same launch. The host picks it instead of __raygen__trace through the shader binding table's ray-generation record. It traces no ray.

extern "ptx-kernel" fn __raygen__math() {
    let params = math::math_params();
    let i = optix::launch_index_x();
    if i >= params.count {
        return;
    }
    let Ok(function) = MathFunction::try_from(params.function) else {
        optix::trap()                       // an id that names no function: a bug
    };
    let result = function.evaluate(math::read_args(params.args, i));
    math::write_result(params.results, i, result);
}

Which function? MathFunction is an enum of 18 variants, one per umbra_math function under test: Fma, Sqrt, Floor, Ceil, Roundf, Sinf, SinOfSinCos, CosOfSinCos, Tanf, Asinf, Acosf, Atan2, Erf, Expf, Powf, Logf, Atanhf, Coshf. Its number on the wire is its position in that list: u32::from(function) one way, MathFunction::try_from(id) the other, which fails with UnknownMathFunction on any id past the end.

Its arguments are always three f32s, [a, b, c]; a function takes as many as it needs, in order, and ignores the rest. MathFunction::evaluate is one match: Self::Fma => umbra_math::fma(a, b, c), Self::Atan2 => umbra_math::atan2(a, b) (so the arguments are [y, x, _]), Self::SinOfSinCos => umbra_math::sin_cos(a).0, and so on.

Why these functions? On nvptx64, umbra-math takes its C maths from CUDA's libdevice (__nv_expf, __nv_powf, …) where glibc serves the CPU (ADR 0028). The two libraries differ, and the GPU's are allowed to be approximate, since a GPU Worker promises only statistical equality with the CPU (ADR 0026). The test measures how far apart they are and holds each function to the bound umbra-math documents. The comparison is not bit for bit, except for the primitives whose bound is 0.

The math program only exists with the math-program feature (section 11). Production PTX has no math program.

Maths used here
ULP = the gap to the next f32
Unit in the last place. Floats are not evenly spaced: the gap doubles each time the size doubles. Counting errors in ULPs makes “1 off in the last place” mean the same at 0.001 and at 1000.
ord(x) = ±(bits of |x|)
dist(a, b) = |ord(a) − ord(b)|
Distance in ULPs, as the test computes it. Positive floats sort the same way as their bit patterns read as integers. Giving negatives a minus sign lines all floats up on one number line, both zeros at 0. (ordinal in tests/gpu/libdevice.rs.)
id = position in MathFunction::ALL
The function's number. 0 = Fma … 17 = Coshf; anything from 18 up is UnknownMathFunction, and the program traps.
|sin_cos error| ≤ 2⁻²⁰ for |x| ≤ 2²⁰
An absolute bound. sin_cos uses Umbra's own argument reduction and the GPU's fast approximate sine and cosine, so near zeros of the sine a relative (ULP) bound makes no sense; the test bounds the plain difference instead. Beyond 2²⁰ it is libdevice's sinf/cosf, within 2 ULP.
7umbra-gpu-programs · programs.rs · #[panic_handler] · optix.rs · trap · ADR 0014

When something goes wrong: trap

In plain wordsOn the CPU, a Rust panic prints a message and stops the program. A GPU thread can't print and has nowhere to unwind to. So in this crate a panic pulls the emergency brake: the PTX instruction trap, which stops the whole launch. The host then sees the launch fail with a CUDA error. That is fine, because in Umbra a panic always means a bug, never normal control flow.

A no_std crate that is linked into a final program must say what a panic does. This one says:

/// A panic is a bug (ADR 0014): it aborts the launch, which the host reports
/// as a CUDA error.
#[panic_handler]
fn panic(_: &PanicInfo<'_>) -> ! {
    optix::trap()
}

The return type ! means “never returns”. optix::trap() has the same type: it is a single trap; instruction in inline assembly, marked noreturn. The PanicInfo, with its message, is ignored, since there is nowhere to show it.

ADR 0014 keeps bounds-checked indexing and debug_assert! in the core even though they can panic: they catch bugs. On the GPU such a check compiles into a branch to trap, and the bug shows up as a failed launch on the host, where umbra-gpu turns it into an Error.

Rules used here
panic ⇒ bug
Never control flow. The core never uses a panic on purpose and never relies on unwinding (ADR 0014).
panic → trap → launch aborted
The whole launch stops, not just one thread. No partial results are trusted; the host reports the error.
Part II · Implementation

How the crate is built

umbra-gpu-programs is small: eight files, seven entry points, and a public API that is only the shared layout. umbra-gpu's build script compiles it to PTX, and umbra-gpu depends on it as an ordinary crate, on the host, for that layout.

9umbra-gpu-programs · launch.rs · wavefront.rs · math_launch.rs · ADR 0028

One layout, two targets

In plain wordsThe struct the host fills and the struct the program reads must be identical. The surest way is to have only one. So launch.rs and wavefront.rs are written once, inside umbra-gpu-programs, which compiles on both targets, and umbra-gpu depends on it like on any other crate and uses its very types. Two copies of the struct can't drift apart if there is only one.

On the host side, umbra-gpu lists the crate under [dependencies] and imports the types, in umbra-gpu/src/records.rs. Since the types are this crate's, umbra-gpu cannot implement cudarc's DeviceRepr on them directly (Rust's orphan rule), so it wraps each in a transparent newtype, whose layout is that of the type it holds:

use umbra_gpu_programs::{
    FilmSampleRecord, HitKind, HitRecord, LaunchParams, RayRecord, SamplerRecord, SceneRecord,
    WavefrontParams, WorkUnitRecord,
};

#[derive(Debug, Clone, Copy, Default)]
#[repr(transparent)]
pub(crate) struct DeviceCopy<T>(pub(crate) T);

For that to work the file must compile on both targets, so it uses only core and the no_std core crates (launch.rs converts umbra-geometry's Ray into a RayRecord with From<&Ray>; wavefront.rs holds umbra-camera's, umbra-integrators' and umbra-sampling's types; math_launch.rs uses core alone), and every type is #[repr(C)], whose layout is defined (ADR 0028 rejects relying on repr(Rust) agreeing on two targets: likely, but not guaranteed). Below each type, a const block of assertions is evaluated by the compiler; a false one is a compile error:

const _: () = {
    use core::mem::offset_of;

    assert!(size_of::<LaunchParams>() == 32, "`LaunchParams` is 32 bytes, the last 4 padding");
    assert!(offset_of!(LaunchParams, handle) == 0, "`handle` is at byte 0");
    assert!(offset_of!(LaunchParams, rays) == 8, "`rays` is at byte 8");
    assert!(offset_of!(LaunchParams, hits) == 16, "`hits` is at byte 16");
    assert!(offset_of!(LaunchParams, count) == 24, "`count` is at byte 24");
};

math_launch.rs adds one more: size_of::<MathParams>() <= size_of::<crate::launch::LaunchParams>(), since a math launch reuses the params variable, which is at least as large as LaunchParams. wavefront.rs asserts its records the same way: WavefrontParams is 128 bytes, SceneRecord 1 056, DeviceSlice 16.

The wavefront's records hold the core's own types. A SceneRecord is the core's CameraKind, FilterKind<DeviceSlice<f32>>, PixelSensor<DeviceSlice<f32>> and VolPathIntegrator; a RandomizerRecord holds DigitPermutations<DeviceSlice<u16>>. Those core types are #[repr(C)] and generic over the storage of their tables, so the host moves each table to device memory with their map_storage and copies the rest byte for byte (ADR 0028). A DeviceSlice<T> is a device address and a length; making one is unsafe (from_raw_parts), since the device trusts it. RandomizerRecord's Debug is written by hand, because DigitPermutations' reads its storage, which the host cannot.

HitRecord::kind is a plain u32, not a HitKind. Device memory may hold any bits, and a Rust enum with an impossible value is undefined behaviour, so the host reads a number and matches it against the HitKind discriminants, failing with umbra_gpu::Error::HitKind on anything that isn't 0, 1 or 2. MathParams::function is a u32 for the same reason, converted on the device with TryFrom.

The Sphere of the intersection program crosses the boundary too, in its hit group's shader binding table record. It comes from umbra-geometry and is copied byte for byte; read_sphere's SAFETY comment records that its layout is the same on both targets and that the record is 16-byte aligned.

10umbra-gpu-programs · optix.rs · ADR 0026, ADR 0028

OptiX's device API in inline PTX

In plain wordsIn C++, a GPU program talks to OptiX through functions from NVIDIA's header files, like optixGetLaunchIndex(). Rust can't use those headers, and Umbra may not copy them (their licence forbids it). But underneath, each of those functions is one call to a built-in with a fixed name, such as _optix_get_launch_index_x. So optix.rs writes those calls directly, in the GPU's assembly language, one small safe Rust function per built-in.

The simplest wrapper, the launch index:

pub(crate) fn launch_index_x() -> u32 {
    let x: u32;
    // SAFETY: the built-in reads the launch state, writes only `x` and has
    // no precondition.
    unsafe {
        asm!("call ({x}), _optix_get_launch_index_x, ();", x = out(reg32) x, options(nomem, nostack));
    }
    x
}

Floats need a detour. OptiX checks the PTX type of every operand, and the f32 ones must be .f32 registers. But Rust's asm! on nvptx64 only offers integer register classes (reg32, reg64). So each float passes through a .f32 register declared inside the call's own { } scope and is moved bit for bit with mov.b32:

asm!(
    "{{ .reg .f32 %t; call (%t), _optix_get_ray_tmax, (); mov.b32 {t}, %t; }}",
    t = out(reg32) t,
    options(nostack)
);

Launch parameters are loaded with ld.const. The offset is a const generic, launch_param_u64::<OFFSET>(), so it is a number fixed at compile time, written straight into the instruction: "ld.const.u64 {w}, [params+{o}];" with o = const OFFSET. The wavefront's stages read their parameters whole instead: launch_params_address returns the generic address of params, from "cvta.const.u64 {a}, params;", and stages.rs reads a WavefrontParams through it (section 5).

trace is the long one. optixTrace becomes _optix_trace_typed_32, which always takes 32 payload registers in and 32 out. Only the first two are live (size = 2); the rest are passed as zeros and their outputs discarded. Its other fixed choices: the default payload type, ray time 0, visibility mask 0xFF, no ray flags, hit group record 0 (SBT offset 0, stride 1) and miss record 0. The function carries #[expect(clippy::too_many_lines)] for its one long operand list.

Where the names come from. The built-ins' names, operands and constants (HIT_KIND_TRIANGLE_FRONT_FACE = 0xFE, HIT_KIND_TRIANGLE_BACK_FACE = 0xFF) are interoperability facts of OptiX 9.0's ABI, written by hand from its documentation. No header text is copied: most of the OptiX SDK's headers are under NVIDIA's proprietary licence (ADR 0026, NOTICE). Building needs no OptiX SDK.

Rules used here
one built-in per wrapper
One safe function, one unsafe block, one built-in, with its // SAFETY: comment (ADR 0007).
.f32 via mov.b32
Exact bits. mov.b32 copies the 32 bits without converting, so the float is unchanged.
program types per built-in
Misuse fails early. Each wrapper's doc lists where it is valid (e.g. report_intersection: intersection programs). OptiX rejects a module that breaks this when the host creates it.
11umbra-gpu-programs · Cargo.toml · math_launch.rs · ADR 0027, ADR 0028

Smaller design decisions

In plain wordsThree more choices shape the crate. It is compiled by the ordinary Rust compiler for the oldest GPU generation the target supports, and the driver adapts it to newer cards. The test-only math program is behind a switch (a Cargo feature) that production builds leave off. And the numbers that name the math functions are generated from the enum itself, so they can't get out of step.

Upstream rustc, at the target's default GPU

The PTX comes from the ordinary Rust compiler's NVPTX backend (part of LLVM), not from a third-party GPU compiler; ADR 0028 rejected Rust-CUDA and hand-written CUDA C++. The programs are built for the target's default GPU generation, sm_70, with PTX ISA 7.0. The driver compiles that PTX for any newer GPU, including the test machine's. -C target-cpu is deliberately not set: the pinned nightly treats it as part of the ABI and would refuse to link against the prebuilt core, which was built without it.

The math program behind a feature

Cargo.toml declares math-program = []. With it off, mod math, mod math_launch, their re-exports and __raygen__math are all compiled out by #[cfg(feature = "math-program")], so production PTX, and the production host, carry nothing that only tests need.

Function ids by macro

A MathFunction's id must be the same number on both sides, and TryFrom<u32> must cover every variant. Rather than keep a hand-written list in step, the macro math_functions! takes the variants once and generates both the enum and MathFunction::ALL, the same list as a slice. A variant's id is then simply its index:

fn try_from(id: u32) -> Result<Self, Self::Error> {
    usize::try_from(id)
        .ok()
        .and_then(|index| Self::ALL.get(index))
        .copied()
        .ok_or(UnknownMathFunction)
}

No f64

#![warn(clippy::disallowed_types)] switches on the workspace's clippy.toml ban on f64 for this crate, as for the core (ADR 0028). Only umbra-math's backends may use it.

12umbra-gpu-programs · every #[expect(unsafe_code)] · ADR 0007

The unsafe boundary

In plain wordsRust's unsafe marks code the compiler can't check, where the programmer promises it is correct. Umbra forbids it by default. The GPU is an exception, because there is no safe way to reach it: talking to OptiX, keeping entry-point names, and reading or writing memory the host handed over. Each such spot is as small as possible, carries a written reason, and is wrapped so the code around it stays safe.

Each exception is a #[expect(unsafe_code, reason = "...")] on the narrowest item possible, here one function, or a small module: params, a module made just for it (“the narrowest item an expect can sit on”), and wavefront.rs's device, which holds DeviceSlice's device access. Inside, each unsafe block holds one operation and a // SAFETY: comment. A memory read reads like this:

#[expect(
    unsafe_code,
    reason = "reads a buffer the host wrote, by its device address (ADR 0007, ADR 0028)"
)]
fn read_ray(rays: u64, i: u32) -> RayRecord {
    let record = (rays as *const RayRecord).wrapping_add(i as usize);
    // SAFETY: the host points `rays` at `count` records, aligned and
    // initialised, and the caller checked `i < count`.
    unsafe { record.read() }
}

The safety argument has two halves: a promise the host keeps (the buffers are count records long, aligned and filled) and a check the program makes (i < count). For writes there is a third: only thread i writes slot i, so no two threads write the same memory.

None of this can be checked by Miri or AddressSanitizer, which don't run on a GPU. ADR 0007 therefore makes the GPU tests on the test machine the verification (section 13).

13umbra-gpu-programs · built by umbra-gpu/build.rs · scripts/check.sh · ADR 0026

How it is built and tested

In plain wordsThe crate has no tests of its own: its programs cannot run on an ordinary computer, and on the host it holds only the layout, whose assertions run at compile time. Two kinds of checking cover it. Everywhere, including CI, it is compiled for the GPU and linted, which catches compile errors and any core crate that needs std. On the one machine with the GPU, umbra-gpu's tests run the programs for real and compare the results with the CPU.

Building. umbra-gpu's build.rs runs a nested cargo rustc --lib --crate-type cdylib on this crate for nvptx64-nvidia-cuda, which links the library into one PTX module, umbra_gpu_programs.ptx, in release, without debug information, in a target directory of its own. It removes the host build's RUSTFLAGS and compiler wrappers, which are for the CPU. If CUDA's libdevice.10.bc is found it is passed as a link argument, and the toolchain's llvm-bitcode-linker inlines the __nv_* maths functions into the PTX. Without it, as in CI, the programs still build, with a warning, but the PTX keeps unresolved .extern functions and the GPU can't run it.

Linting. The workspace's ordinary clippy run covers the host build of the layout. scripts/check.sh also runs clippy for nvptx64 on this crate and on the core crates it uses. Its unstable step fails if any crate other than this one enables #![feature(...)].

Running. tests/gpu/optix.rs traces rays at the triangle (expected hits worked out by hand) and the sphere (expected hits from the core's own Sphere::intersect on the CPU, agreeing to a few ULP). tests/gpu/libdevice.rs uses the math program to sweep about four million f32 inputs, subnormals included, through each function and compares with glibc within its bound. It also checks that the primitives keep subnormal results instead of flushing them to zero. tests/gpu/renderer.rs runs the two stages: it renders the camera-only Scene File in batches on the GPU and Work Unit by Work Unit on umbra-cpu's Renderer, and checks one black Work Result per Work Unit whose pixels' sums of filter weights are the CPU's within a relative 10−6. A second test checks that a cancelled batch returns Rendered::Cancelled for every Work Unit.

Rules used here
no host tests
No program runs on a CPU, so there is nothing to test there; the layout's conversions run in umbra-gpu's tests. There is also no example.
nvptx64 build = no_std check
The target has no std, so any core crate that pulled it in would break this build (ADR 0028).
