Umbra Render Guide

A picture is not rendered in one go. Umbra cuts the job into small pieces of work, renders the pieces on many cores (and, later, many machines), and adds the answers into one Film as they come back, in whatever order they arrive. umbra-render does the cutting and the adding up, and says what the rendering of one piece must give back. The rendering itself is done by a renderer per Render Device: umbra-cpu on a CPU, umbra-gpu on a GPU. This guide explains each step in pictures first and formulas second. It assumes only school maths.

Part I · Theory

How an image is put together

A pixel's colour is an average of many guesses, the Pixel Samples. Umbra computes those guesses in pieces, on different threads and later on different machines. This part explains how the pieces are cut, why their answers are kept as sums, and why the order of adding them up is a question at all.

In plain wordsSix words carry this whole guide. A Pixel Sample is one guess at one pixel's colour. A Tile is a rectangle of pixels. A Pass is a run of sample numbers, the same run in every pixel. A Work Unit is one Tile for one Pass: a piece of work small enough to hand to one machine. A Work Result is the answer to one Work Unit. The Film adds all the answers together.

A pixel is two sums

In plain wordsA pixel's colour is a weighted average of its Pixel Samples: multiply each sample's colour by its weight, add those up, and divide by the sum of the weights. The trick is to not divide yet. As long as the two sums are kept apart, answers computed at different times or on different machines can simply be added together. The division happens once, at the very end.

For each pixel the Film keeps two running totals, exactly as pbrt-v4's RGBFilm does: the sum of w × colour for red, green and blue, and the sum of the weights w. In Umbra this pair is a PixelSum:

pub struct PixelSum {
    pub rgb: [f64; 3],   // Σ weight · rgb, for red, green, blue
    pub weight: f64,     // Σ weight
}

Each Pixel Sample arrives as a FilmSample from umbra-integrators: its colour in the sensor's RGB, and its filter weight. Adding one sample is an +=:

impl AddAssign<FilmSample> for PixelSum {
    fn add_assign(&mut self, sample: FilmSample) {
        let FilmSample { rgb, weight } = sample;
        for (sum, c) in self.rgb.iter_mut().zip([rgb.r, rgb.g, rgb.b]) {
            *sum += f64::from(weight * c);   // multiply in f32, add in f64
        }
        self.weight += f64::from(weight);
    }
}

The multiplication happens in 32-bit floats (f32), like everything else in the rendering core. Only the running sums are 64-bit (f64). A sum can reach millions of samples, and every addition onto a big total drops some of the small number's digits. With f64's 16 digits instead of f32's 7, those losses stay far below what the eye can see (ADR 0001). A second +=, between two PixelSums, merges one Work Result's sums into another's. That is the Film's whole job.

With Umbra's filter every Pixel Sample has the same weight (see the camera guide's pixel filters), so Σ w is simply “number of samples × w”. The Film still keeps it as a sum, as pbrt-v4 does, so nothing changes when filters with varying weights arrive.

Cutting the job into Work Units

In plain wordsBefore anything is rendered, the image is cut into squares (Tiles), and the list of sample numbers is cut into runs (Passes). Every pairing of one Tile with one Pass is a Work Unit. The cut depends only on the image size and the Render Job Options, never on how many machines are helping. So the same job always gives the same Work Units, and each Work Unit always means the same pixels and the same samples.

Decomposition::new takes the image's resolution and the RenderJobOptions, and stores just six numbers: the resolution, the Tile size, the Tiles across, the Tile count, the Pixel Samples per Pass and per pixel. Every question about the cut is then answered by a little arithmetic, without any list in memory:

pub fn tile_bounds(&self, tile: TileIndex) -> TileBounds {
    let column = tile.0 % self.tiles_x;          // (each converted to i32)
    let row = tile.0 / self.tiles_x;
    let min = Point2i::new(column * self.tile_size, row * self.tile_size);
    let max = Point2i::new(
        (min.x + self.tile_size).min(self.resolution.x),   // cut short at the edge
        (min.y + self.tile_size).min(self.resolution.y),
    );
    TileBounds { min, max }
}

pub fn sample_indices(&self, pass: PassIndex) -> Range<u32> {
    let start = pass.0 * self.samples_per_pass;
    start..(start + self.samples_per_pass).min(self.samples_per_pixel)
}

TileBounds is pbrt-v4's Bounds2i as its tiles use it: min is the top-left pixel, and max is one past the bottom-right one, so width() is just max.x − min.x. work_units() lists every Work Unit in the order they are handed out, Pass by Pass and, inside a Pass, by Tile number. contains(unit) says whether a Work Unit belongs to this Render Job at all.

The defaults are 32 × 32-pixel Tiles, Passes of 64 Pixel Samples, and pbrt-v4's 16 Pixel Samples per pixel. A default render therefore has a single Pass, [0, 16), and one Work Unit per Tile. Two things can go wrong, and new returns them as a Error: TooManyTiles when the Tile count doesn't fit in a u32, and TileTooLarge when the Tile size doesn't fit in an i32.

Handing out the work

In plain wordsThe Coordinator keeps the list of Work Units. Each Worker asks for more whenever it has room, so a fast machine simply asks more often: nobody has to measure who is fast. Work goes out Pass by Pass. At the very end, when nothing is left to hand out, an idle Worker gets a copy of the oldest unfinished Work Unit, so one slow machine can't hold up the finish. Whichever copy comes back first counts, and the other is thrown away.

The scheduler belongs to umbra-cluster (ADR 0009). Today it serves one in-process Local Worker, which pulls Work Units exactly as above; the network, failed Workers and the speculative tail arrive with #128 and #129. umbra-render provides the four pieces it needs:

  • The order. Decomposition::work_units() lists the Work Units Pass-major: all Tiles of Pass 0 in raster order, then all of Pass 1, and so on. The whole image improves evenly, and a slow Pass of one Tile never holds back the later Passes of that Tile, as it would if each Tile's Passes went out together (“Tile-major”, rejected in ADR 0009).
  • Concurrent rendering. Cancellation and Rendered let a Worker render several Work Units at once, each with its own stop request; the CPU's renderer is Sync, so it does that from different threads (CPU guide). A CPU Worker keeps about two in flight per eight threads, to hide the network's delay.
  • Cancelling a copy. A Cancellation is a shared flag. When the first copy's Work Result wins, the scheduler sets the flag of the other copy, which stops at its next row on a CPU (section 7).
  • Dropping duplicates. Film::accept remembers every Work Unit it merged and answers Acceptance::Duplicate for a second Work Result of the same one (section 6). Every Pixel Sample counts exactly once.

Copies and reassignments after a Worker fails are routine, so duplicates are routine too. Before ADR 0022, two copies' Work Results were compared through a hash, to catch a faulty Worker. Now the Cluster is assumed healthy, and the second one is simply not read.

What keeps the cores busy, and what the Pass size is for

The Pass size (--spp-per-pass) looks like the knob that spreads work over a machine's cores, but it is not. A Worker fills its cores on two levels, and neither depends on the Pass size:

  1. Several Work Units at once. A CPU Worker asks for ⌈threads ⁄ 4⌉ Work Units, about two per eight threads (capacity in umbra-cluster's local_worker.rs): 16 on the P620's 64 threads.
  2. The rows of each Work Unit at once. Inside one Work Unit, umbra-cpu shares the Tile's rows out over the same rayon pool, and a free thread steals the next row (CPU guide).

Sixteen Work Units of 32 rows each make 512 rows to share among 64 threads, whatever the Pass size. What the Pass size sets is how big one Work Unit is along the samples, as the Tile size sets it across the image:

So the Pass size changes how the work is packaged, never how much of it there is:

  • The cost of one Work Unit is about the Tile's pixels times the Pass's Pixel Samples. A smaller Pass makes it cheaper.
  • What a failure loses. A Worker that dies loses its Work Units in flight, which are rendered again elsewhere. Smaller Work Units mean less to redo (ADR 0009 rejected a single Pass for this reason).
  • The end of the render. The last Work Units decide when the image is done; when they are small, nobody waits long on one of them, and a speculative copy is cheap.
  • Overhead. Every Work Unit costs an assignment, a Work Result buffer and a merge, whatever its size. Very small Passes spend more of the render on that.
  • The last bits of the image. The Film adds Pixel Samples Pass by Pass, so another Pass size rounds differently (section 4). The noise is the same; the bits are not.

The Pass size helps fill the cores only when there are too few Work Units to go round. That happens with a small image (few Tiles) and one Pass, and above all on a Cluster: every Worker wants several Work Units in flight, and a GPU Worker wants about 16 at once for one batch. More Passes multiply the Work Units, Tiles × Passes, without changing the image's statistics. Even then the rows inside each Work Unit keep a CPU Worker's threads busy; the cost is balance between Workers, not idle cores.

Why the order of additions matters

In plain wordsComputers store numbers with a fixed number of digits. After every addition, the answer is rounded to fit. Because of that rounding, adding the same numbers in a different order can give a slightly different answer in the last digit. In school maths, (a + b) + c always equals a + (b + c). On a computer it often doesn't. Swapping just two numbers, a + b versus b + a, is always safe.

A 64-bit float stores a number as 53 binary digits times a power of two. Near 1, the gap between neighbouring storable numbers is about 2 × 10−16. That gap is called an ULP. It grows with the number: near 1 000 000 it is about 10−10. Every addition rounds to the nearest storable number, so it may be off by up to half an ULP.

Two facts follow, and the rest of this guide leans on both:

  • Swapping two numbers is safe. a + b and b + a are the same exact sum, rounded the same way. Floating-point addition is commutative.
  • Regrouping three or more is not. (a + b) + c rounds after a + b; a + (b + c) rounds after b + c. Different roundings can give different last digits. Floating-point addition is not associative.

The Film adds Work Results onto its pixels as they arrive. If one pixel receives three or more Work Results, the order they arrive in is the order of its additions. Arrival order depends on which machine was faster, on the network, on luck. So a Film that must be the same bits every time has to control the order of additions, or make sure the order cannot matter. Section 5 tells how Umbra deals with that.

fl(a + b) = (a + b)(1 + δ),   |δ| ≤ 2−53

fl(a + b) = fl(b + a)
Commutative. The order of two numbers never matters.
fl(fl(a + b) + c) ≠ fl(a + fl(b + c)), in general

What stays exactly the same

In plain wordsUmbra promises that one Pixel Sample, on one machine with one program, always gives exactly the same bits. That lets you re-run a single pixel later to see how it was computed. A Work Result is just as exact: the same Work Unit always gives the same sums, whatever the number of threads. For the whole Film the promise is softer. If a pixel receives three or more Work Results, the order they arrive in may change its last digit. Never the picture you see.

Why bother? Exactness turns every difference into a clue. If a pixel looks wrong, umbra trace will compute its Pixel Samples again, with recording switched on (ADR 0011). That only helps if the re-run follows the very same path as the render. And the tests can compare whole Films bit for bit, where a 1-in-1016 difference would otherwise be lost in noise.

The history. ADR 0004 first promised a bit-identical Film for every render of a Render Job, in any arrival order. To keep that promise, the Coordinator would have merged each Tile's Passes in Pass order, holding any Work Result that arrived early. ADR 0022 dropped that: the buffer and the waiting were complexity for a property of the last bit. Today the Film merges each Work Result the moment it arrives. What remains exact:

  • a Pixel Sample, and so a Work Result, on one machine with one binary;
  • a Film whose pixels each receive at most two Work Results, which includes every default render (one Pass);
  • so the invariance tests compare single-Pass Films, or compare Work Results, never multi-Pass Films merged in different orders.

Images from different machines, or multi-Pass Films merged in different orders, are only promised to look the same.

How often does the order actually matter? Less often than you might fear. Every number the Film adds is built from f32 products, which carry 24 significant binary digits, and the Film adds them in f64, which holds 53. The sum of such numbers needs no rounding at all, so the order cannot matter, as long as the running total stays below about 229, roughly half a billion, times the smallest non-zero Pixel Sample contribution. An ordinary pixel stays far inside that. A firefly, a rare Pixel Sample billions of times brighter than its neighbours, or a huge number of Pixel Samples, can step outside it, and only then does the arrival order show in the last bits.

Checking and merging a Work Result

In plain wordsWhen a Work Result arrives, the Film asks three questions. Is it for a Work Unit of this Render Job at all? Has this Work Unit already been merged? Does it hold exactly one sum per pixel of its Tile? If it is new and well formed, the Film adds its sums onto the matching pixels. If it is a second answer for a Work Unit already merged, the Film throws it away without reading it. The other two failures can only be bugs, so they stop the program.
pub fn accept(&mut self, result: &WorkResult) -> Acceptance {
    let unit = result.unit();
    assert!(self.decomposition.contains(unit), /* … */);
    if self.merged.contains(&unit) {
        return Acceptance::Duplicate;                      // discarded unread
    }
    let bounds = self.decomposition.tile_bounds(unit.tile);
    assert_eq!(result.pixels().len(), bounds.area(), /* … */);
    self.merged.insert(unit);
    let width = self.width();
    let rows = result.pixels().chunks_exact(bounds.width());
    for (y, row) in (bounds.min.y..).zip(rows) {
        let start = Self::offset(width, bounds.min.x, y);
        merge_row(&mut self.pixels[start..start + row.len()], row);
    }
    Acceptance::Merged
}

The Film holds three things: the same Decomposition as the renderers, one PixelSum per pixel of the image (all zero to start), and a HashSet<WorkUnit> of the Work Units merged so far. merge_row is a zip of the two rows with the += of section 1. is_complete() is true once the set holds as many Work Units as work_units() lists.

The Film hash. To compare two Films quickly, Film::hash boils every bit of every sum down to one 64-bit number, a FilmHash, printed as 16 hex digits. It uses FNV-1a: start from a fixed number, and for every byte, mix the byte in with XOR and multiply by a fixed prime. Equal Films give equal hashes; Films that differ in a single bit almost surely don't. It is meant for tests and for the Render Job Report, not for security.

How a render ends

In plain wordsThis crate does not render. Each Render Device, a CPU or a GPU, has a crate of its own with a renderer that turns Work Units into their Work Results: the CPU's one at a time, the GPU's a batch at a time. What they share lives here: the Work Unit they are given, the stop request they listen to, and the two ways a render can end. Either every Pixel Sample was computed and the Work Result comes back, or someone asked to stop and nothing comes back.
pub enum Rendered {
    Done(WorkResult),   // every Pixel Sample was computed
    Cancelled,          // stopped early; what was computed is dropped
}

pub struct Cancellation { cancelled: AtomicBool }
// new, cancel, is_cancelled

Two renderers, one contract. umbra_cpu::Renderer is built from a &Scene and its &RenderJobOptions, and renders one Work Unit at a time: render(unit, &cancel) -> Rendered. umbra_gpu::Renderer is built from the same two on one GPU, new(ordinal, &scene, &options), and renders a batch: render(&units, &cancel) returns one Rendered per Work Unit, in order, or Cancelled for every one, and an Error when the GPU fails. A GPU Worker keeps Renderer::CAPACITY Work Units in flight, 16 for now, and the wavefront runs each stage once over all their Pixel Samples (ADR 0026). Both use this crate's WorkUnit, Cancellation and Rendered. umbra-cluster wraps the renderers in an enum of its own and picks one by the Worker's Render Device; today the enum has only the CPU's, and the GPU's joins it with the GPU Local Worker (#128).

Stopping early. Cancellation wraps an AtomicBool, a true/false flag that many threads can read and write safely. cancel() sets it; a renderer reads it with is_cancelled() as often as suits its Render Device. The CPU's checks it before each row of the Tile, so a running row finishes first; the GPU's checks it before a batch and between its stages. Either way, a cancelled render returns Rendered::Cancelled and drops whatever it computed: a Work Result is all of its Work Unit or nothing.

What every renderer must keep. The Work Result it returns has one PixelSum per pixel of the Work Unit's tile_bounds, holding that Pass's sample_indices and no others (section 2), or Film::accept panics (section 6). The Coordinator, the Film and each renderer build their own Decomposition from the same Scene resolution and RenderJobOptions, so all of them cut the job the same way.

Part II · Implementation

How the crate is built

umbra-render is a std crate, outside the no_std core: it may allocate, write files and use a hash set. It sits on top of umbra-integrators, umbra-scene and umbra-math, and on neither rayon nor anything from NVIDIA. umbra-cpu, umbra-gpu, umbra-cluster and the umbra binary depend on it (arc42 §5.1, ADR 0015, ADR 0033).

pbrt-v4 renders in one process and has no Work Units: its RGBFilm both accumulates the sums and writes the image. Umbra splits that in two. The sensor and the filter live in umbra-camera, inside the core. The sums and their merging live here, outside it. The part of RGBFilm that turns sums into output RGB is Film::finish, and Image::write writes the file. Rendering is in neither: pbrt-v4's pixel loop, ImageTileIntegrator::Render, has its counterpart in umbra-cpu.

9umbra-render · rendered.rs, film.rs · ADR 0004, ADR 0022, ADR 0033

Design decisions

In plain wordsMost of what's interesting here is what the code is careful not to do. It does not render: that is each Render Device's job, in a crate of its own. It names every outcome instead of returning true or false. And it reads the second answer for a Work Unit not at all. How the CPU's renderer keeps its calls cheap and its memory per Work Unit is told in the Umbra CPU Guide.

A contract, not a renderer

Until ADR 0033, this crate also held the CPU's renderer and its rayon. Now it holds only what is the same on every Render Device, and umbra-cpu and umbra-gpu each depend on it alone of the three. A crate boundary, not a module boundary, is what makes both renderers use only the contract's public API. It also keeps the Film's build free of threads and of anything from NVIDIA, and a change to the Film rebuilds no GPU program.

Outcomes are enums, identifiers are newtypes

pub enum Acceptance { Merged, Duplicate }
pub enum Rendered { Done(WorkResult), Cancelled }
pub struct TileIndex(pub u32);
pub struct PassIndex(pub u32);
pub struct FilmHash(pub u64);

accept could have returned a bool, but true would not say whether it means “merged” or “was a duplicate”. Rendered::Done carries its Work Result, so a cancelled render simply has none to misuse. A TileIndex can't be passed where a PassIndex is expected, although both are a u32 inside. Error is #[non_exhaustive], so new errors can join without breaking callers.

Merge on arrival, duplicates unread, bugs loud

The Film keeps a HashSet<WorkUnit> of what it has merged, and nothing else about history: no early-arrival buffer, no per-Pass copies (one Film-sized buffer per Pass was rejected in ADR 0004 for its memory). A duplicate is spotted from its WorkUnit alone. A Work Unit outside the job, or a Work Result of the wrong size, can only come from a bug in Umbra, so accept panics instead of returning an error that someone might ignore.

The Film hash

pub fn hash(&self) -> FilmHash {
    const OFFSET_BASIS: u64 = 0xcbf2_9ce4_8422_2325;
    const PRIME: u64 = 0x0100_0000_01b3;
    let bytes = self.pixels.iter().flat_map(|p| {
        [p.rgb[0], p.rgb[1], p.rgb[2], p.weight]
            .into_iter()
            .flat_map(|v| v.to_bits().to_le_bytes())
    });
    FilmHash(bytes.fold(OFFSET_BASIS, |h, b| (h ^ u64::from(b)).wrapping_mul(PRIME)))
}

An iterator over every byte of every sum, folded into one number. to_bits gives the float's exact bit pattern, so 0.6 and 0.6000000000000001 hash differently. FNV-1a is short, fast and needs no dependency; it is not meant to resist someone forging a collision.

How it is tested

In plain wordsThe tests treat the crate as a black box with one door: Work Results go into the Film. They make the Work Results themselves, with sums chosen so the answer is known, for the Work Units of a camera-only Scene of 40 × 24 pixels. The renderers that make real Work Results are tested in their own crates.
  • film.rs, the Film's door:
    • single_pass_work_results_merge_to_the_same_film_in_any_order: four orders (in order, reversed, interleaved, rotated), the same FilmHash and the same pixels.
    • a_duplicate_leaves_the_film_unchanged, a_work_result_lands_on_its_tile, the_passes_of_a_tile_add_up: see the diagram.
    • a_finished_film_is_each_pixels_weighted_mean_in_srgb: Film::finish against the BT.709 matrix.
  • image.rs, the final image: an_exr_extension_writes_an_exr_with_the_pixels, and an_unknown_extension_is_invalid_input_and_writes_nothing.
  • scenes.rs builds the Scene with SceneBuilder and the options (seed 0, 16-pixel Tiles).
  • The renderers: umbra-cpu's tests/umbra_cpu/ (thread count, order, cancellation; see the CPU guide), and the counting-allocator test in crates/umbra/tests/allocation.rs, which renders through umbra-cpu.

Note what the tests avoid: they never compare multi-Pass Films merged in different orders, for the reason in section 5. Run them with cargo nextest run -p umbra-render.
