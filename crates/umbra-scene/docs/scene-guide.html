Umbra Scene Guide

Before a renderer can draw anything, it needs a complete, checked description of what to draw: the camera, the film, the filter, the sampler, and later the shapes, lights and materials. In Umbra that description is the Scene, and umbra-scene is the crate that builds it, stores it and lends it to the rendering code. This guide explains how, in pictures first. It assumes no computer-science background.

Part I · Concepts

Describing what to render

A renderer runs the same small piece of code billions of times, once per Pixel Sample. Every one of those runs asks the Scene questions: where is the camera, how is the filter shaped, and later, what does this ray hit. This part explains how the Scene is organised so that those questions are fast, safe and identical on every machine.

1umbra-scene · scene.rs · Scene · GLOSSARY.md “Scene”, “Scene File”

What a Scene is

In plain wordsA Scene File is like a written recipe: plain text that a person wrote, maybe with mistakes. The Scene is the kitchen after someone has read the recipe, checked it and laid out every ingredient, measured and ready. The rendering code never reads the recipe. It only reaches into the prepared kitchen.

The project's glossary defines the Scene as “the complete, validated description of what is rendered: geometry, materials, lights, media, camera and render settings, independent of the file format it was read from. Every Worker holds an identical replica.” Each part of that sentence is a design choice:

  • Complete. Nothing is left for later. Every setting the file did not give takes pbrt-v4's default, so the rendering code never has to ask “was this set?”.
  • Validated. Mistakes are caught once, before any pixel is rendered. A Scene that exists is a Scene that makes sense (section 7).
  • Independent of the file format. A Scene does not remember that it came from a .pbrt file. Tests build Scenes directly in Rust, with no file at all.
  • The same everywhere. Many machines may render one image together. Each holds its own copy of the Scene, and the copies must be identical (section 6).

On this branch the Scene is still small. It holds the film's resolution, one perspective camera, one Gaussian pixel filter, the CIE 1931 pixel sensor, the Halton sampler's randomisation and the volumetric path integrator. Shapes, lights and materials come with later milestones (section 14).

Rules used here
only SceneBuilder::build makes a Scene
No half-made Scenes. Scene's fields are private, so other code can't assemble one by hand and skip the checks.
Scene has no setters
Immutable. Once built, a Scene only answers questions: full_resolution(), randomize_strategy(), integrator(), view().
one Scene per Render Job
Short-lived. A Scene lives for exactly one Render Job and is then dropped all at once (ADR 0008).
2umbra-scene · scene.rs · SceneBuilder, build · ADR 0008

Building, then rendering

In plain wordsA Scene's life has two phases. First, while it is being built, you may change anything, in any order. Then build() is called and the Scene is frozen. From then on many threads read it at the same time. Since nobody can change it, nobody has to wait for anybody else.

A builder is a common pattern: an object whose only purpose is to collect settings and then make something else. SceneBuilder starts with every setting at pbrt-v4's default. Each setter replaces one group of settings and hands the builder back, so calls can be chained:

let mut builder = SceneBuilder::new();
builder
    .film(FilmParameters { resolution: Point2i::new(64, 48) })
    .filter(GaussianFilterParameters { radius: Vector2f::new(2.0, 2.0), sigma: 0.5 });
let scene = builder.build()?;   // the builder is used up here

The setters only store settings. All the real work, and all the checking, happens in build. This is why the order of the setters doesn't matter. The camera, for example, needs the film's resolution to compute its matrices, but it only gets it inside build, when every setting is known.

build takes the builder by value (self, not &self). In Rust that means the builder is moved into the function and can't be used afterwards. The compiler itself enforces the end of the building phase.

Rules used here
fn film(&mut self, film: FilmParameters) -> &mut Self
Setters store and chain. Each replaces one group and returns the builder. camera takes its parameters by reference, since they hold a 4 × 4 matrix.
pub fn build(self) -> Result<Scene, Error>
One place checks. build is the only function that validates and the only one that can fail.
build(self): the builder moves in
No changes after freezing. Once build has run there is no builder left to change, and the Scene has no setters.
threads share &Scene
Shared reading. Any number of shared references can read a value at once in Rust. Writing would need exclusive access, and nobody writes.
3umbra-scene · arena.rs · Arena<T> · uses umbra-geometry Handle<T> · ADR 0008

Arenas and handles instead of pointers

In plain wordsObjects in a scene refer to each other: a sphere uses a material, a triangle belongs to a mesh. One way is to store the other object's address in memory, a pointer. Umbra does something simpler. It keeps all objects of one kind in one numbered row, an arena, and refers to an object by its number in that row, a handle. Like a seat number in a theatre: “row materials, seat 2”.

Why go to this trouble? A number has properties a pointer lacks:

  • It means the same thing everywhere. “Material 1” is the second material on every machine and in every copy of the Scene. A memory address means nothing once the data is copied to another machine or to a GPU (section 6).
  • It is small and simple. A handle is a 32-bit number. It can be copied freely, it needs no lifetime annotations in Rust, and it doesn't keep anything alive.
  • It is checked. Looking up a handle checks that the number is inside the arena. A bad number gives “nothing” (None), never a crash or garbage.
  • It is typed. A Handle<T> remembers, at compile time, which type it points to. You can't use a material's handle in the spheres' arena by mistake: the program does not compile.

ADR 0008 records the alternatives Umbra rejected: references into one big memory block (&'scene T), whose lifetimes spread through every function signature, and Arc<T>, which counts references on the hottest code path.

Rules used here
handle = position in the arena
Minted in order. push appends the object and returns the handle of its position: 0, 1, 2, … Nothing is ever removed, so a handle never goes stale.
get(handle) -> Option<&T>
Checked look-up. Some(&object) if the position exists, None if it is past the end.
at most u32::MAX objects per arena
Handles are 32 bits. push refuses with Error::TooManyObjects once an arena is full, rather than mint a handle that would wrap around.
Handle<A> ≠ Handle<B>
Typed. The compiler rejects a handle used on the wrong arena. Not checked: a handle from another Scene of the same type (ADR 0008 accepts this).
4umbra-scene · scene.rs · Scene::view · uses umbra-integrators SceneView · ADR 0014

Lending the Scene to every Pixel Sample

In plain wordsThe rendering code that runs per Pixel Sample lives in special crates, the core, that are not allowed to reserve memory. That way the same code can run on a graphics card later. So the core can't own a Scene, because a Scene owns memory. Instead the Scene lends it a small bundle of read-only references, the SceneView. Borrowing costs nothing and allocates nothing.

Rust's word for a temporary loan is a borrow, written &. The '_ in SceneView<'_> is a lifetime: the compiler's note that the view may not outlive the Scene it borrows from. If someone tried to drop the Scene while a view still existed, the program would not compile.

pub fn view(&self) -> SceneView<'_> {
    SceneView::new(&self.camera, self.filter.view(), &self.sensor)
}

ADR 0008 first said that per-sample code reads &Scene. ADR 0014 changed that to a SceneView, because a Scene contains Vecs and a crate without alloc can't even name a Vec. On a graphics card, the same view will point into device memory instead (ADR 0028).

Not reserving memory per Pixel Sample is a tested promise, not a hope. A test in the umbra binary crate, rendering_allocates_per_work_unit_not_per_pixel_sample, builds a Scene with SceneBuilder, renders a Work Unit with N and then 2N Pixel Samples, and checks that both runs reserve memory the same number of times.

Rules used here
per-sample code gets SceneView, never &Scene
The core sees borrowed slices. The owning Scene stays outside the core (ADR 0014).
allocations per Work Unit, never per Pixel Sample
The allocation boundary. Memory is reserved per Render Job (the Scene), per Work Unit (the result buffer) and outside rendering. Checked by a counting-allocator test (ADR 0008).
SceneView<'a> cannot outlive the Scene
Lifetimes. The borrow checker proves every view is gone before its Scene is dropped.
5umbra-scene · options.rs · RenderJobOptions, Seed · arc42 §8.2, §8.8

Render Job Options

In plain wordsThe Scene says what to draw. The Render Job Options say how to organise the work of drawing it: how many Pixel Samples per pixel, how big the pieces of image handed out to Workers are, how many samples go in each round, and which random seed to start from. Two renders with the same Scene can use different options. Tiles and Passes organise the work; the number of samples and the seed decide the noise you see.

The options use three words from the glossary. A Tile is a square block of pixels. A Pass is a range of sample numbers, the same range in every pixel: with 64 per Pass, Pass 0 is samples 0 to 63 of every pixel, Pass 1 is samples 64 to 127. A Work Unit is one Tile for one Pass: the piece of work the Coordinator gives a Worker.

The seed chooses which random numbers the samplers use. With the Scene, the pixel and the sample number, it fixes every Pixel Sample exactly (ADR 0022): render twice with the same seed and you get the same image; change the seed and the noise changes. Seed wraps an i32, as pbrt-v4's --seed is an int, and converts to the u32 the samplers take by keeping its bits.

The options live in umbra-scene although the Scene doesn't use them, because three other parts need them: the renderer, the cluster and the binary (arc42 §5.3). Putting them next to the Scene avoids a crate just for one struct.

Maths used here
Tiles = ⌈W ⁄ t⌉ × ⌈H ⁄ t⌉
How many Tiles. ⌈ ⌉ means “round up”: 200 ⁄ 64 = 3.1, so 4 columns. W, H: the film's resolution; t: tile_size.
Passes = ⌈spp ⁄ p⌉,   last = spp − (Passes − 1) · p
How many Passes, and the length of the last. spp: spp; p: spp_per_pass. With the defaults, 16 and 64, there is one Pass of 16.
Work Units = Tiles × Passes
How many pieces of work. The default film and options give 40 × 23 Tiles and one Pass: 920 Work Units.
u = s if s ≥ 0, else s + 232
The seed's bits. An i32 read as a u32: −1 becomes 4 294 967 295. From<Seed> for u32, via cast_unsigned.
6umbra-scene · design, not built yet · ADR 0003 · arc42 §5.3, §8.2

One Scene, many Workers

In plain wordsUmbra is built to render one image on many machines at once. Only one machine, the Coordinator, reads the Scene File. It builds the Scene and sends a copy to every other machine, the Workers. Each Worker then has an identical Scene and renders its share of the work. Because objects refer to each other by numbers rather than memory addresses, the copy works as-is on the other side.

Arc42 §5.3 adds one detail: what is sent is the builder's arenas, not a finished Scene. Each Worker then calls build itself. So the code that checks a Scene and builds its BVH runs the same way on every machine, and the BVH, which is large, never crosses the network.

Status on this branch. None of this is built yet. The README lists “serialising a Scene for replication, with remote Workers” under not here yet. What is in place is the groundwork: arenas with handles, a Scene that is Clone and holds no pointers between objects, and umbra-scene's dependency on umbra-integrators with the core's serde feature switched on. That feature is wired through the core crates, but no type derives Serialize yet.
Rules used here
replicate the Scene, never the Scene File
Parsed once. Workers need no files and no .pbrt grammar, and all start from identical data (ADR 0003).
send the builder's arenas; each Worker calls build
No BVH on the wire. Building it locally is cheaper than sending it (ADR 0003, arc42 §5.3).
no pointers between Scene objects
Copyable as-is. The same property lets a GPU Worker copy arena slices to device memory byte for byte (ADR 0028).
7umbra-scene · error.rs · Error

When a Scene can't be built

In plain wordsSometimes the settings make no sense: a film with no pixels, or a filter too small to work with. Instead of crashing, build returns a value that says what went wrong. In Rust such a value is a Result: either Ok with the Scene, or Err with the reason. The caller must look at it before it can use the Scene.
variantwhenits message (Display)
EmptyResolution { resolution }build: a side of the film is below 1the film's resolution 0 x 10 has no pixel
FilterRadiusTooSmallbuild: a filter radius is below 1⁄32a filter radius is below 1/32
TooManyObjects { type_name }Arena::push: the arena is fullmore than 4294967294 objects of type `f32`

Rust's ? operator makes handling these short. Written after a call, it means “if this is an error, return it from my function too; otherwise unwrap the value”. The README's example ends with builder.build()? for this reason.

Error is an enum with one named variant per reason, and each variant carries the data needed to explain it: the bad resolution, or the type whose arena is full. It derives thiserror::Error, which gives it Display, for a human-readable message, and std::error::Error, so it fits Rust's usual error handling. Every Umbra crate names its error Error and keeps it in error.rs. It is marked #[non_exhaustive]: code that matches on it must keep a catch-all branch, so new reasons can be added later without breaking that code.

Strictness is a project-wide choice. ADR 0003 rejects any lenient mode: “a wrong image costs more than a refused Render Job”. Nothing is built when there is an error.

Rules used here
Result<Scene, Error>
Errors are values. build never panics on bad settings; the caller decides what to do.
first problem wins
Checked in order. The film, then the filter. Arena overflow is reported by push, at the moment it happens.
#[non_exhaustive]
Room to grow. Shapes, lights and materials will bring new reasons to refuse a Scene.
Part II · Implementation

How the crate is built

umbra-scene is a std crate outside the core. It depends on five core crates and is used by umbra-parser, umbra-render, the renderers in umbra-cpu and umbra-gpu, umbra-cluster and the umbra binary (ADR 0015, arc42 §5.1). It is small: under 500 lines of Rust in four modules.

9umbra-scene · scene.rs · SceneBuilder::build, build_camera, imaging_ratio, default_screen_window

Settings in, core objects out

In plain wordsThe builder holds settings in the shape a Scene File gives them: numbers and choices. build turns each group into the ready-to-use object the core needs: matrices for the camera, tables for the filter, response curves for the sensor. After that, nobody has to look at the raw settings again.
pub fn build(self) -> Result<Scene, Error> {
    let resolution = self.film.resolution;
    if resolution.x < 1 || resolution.y < 1 {
        return Err(Error::EmptyResolution { resolution });
    }
    let GaussianFilterParameters { radius, sigma } = self.filter;
    if radius.x * 32.0 < 1.0 || radius.y * 32.0 < 1.0 {
        return Err(Error::FilterRadiusTooSmall);
    }
    let (shutter_open, shutter_close) = self.camera.shutter();   // swapped if reversed
    Ok(Scene {
        resolution,
        camera: self.build_camera(shutter_open, shutter_close),
        filter: GaussianFilter::new_in(radius, sigma, |n| vec![0.0; n]).into(),
        sensor: PixelSensor::cie1931(imaging_ratio(shutter_close - shutter_open)),
        randomize: self.sampler.randomize,
        integrator: self.integrator,
    })
}

The checks come first, so the core constructors are only ever called with values they accept. GaussianFilter::new_in would itself panic on a radius below 1⁄32 (its FilterSampler::new_in documents this); checking here turns that panic into an ordinary error. The |n| vec![0.0; n] closure is how the Scene lends memory to a core crate that can't allocate: the filter asks for n floats and the Scene hands over a Vec.

build_camera follows pbrt-v4's PerspectiveCamera::Create: it moves the camera to the rendering space with CameraTransform::new, picks the screen window, and calls PerspectiveCamera::new. The result is converted into the closed enum CameraKind with .into(). Both steps are explained in the camera guide.

10umbra-scene · arena.rs · umbra-geometry handle.rs · ADR 0008

Inside Arena<T> and Handle<T>

In plain wordsAn arena is a thin wrapper around Rust's growable list, Vec, that only allows adding and reading. A handle is a 32-bit number with an invisible label saying which type it points to. The label costs zero bytes: it exists only for the compiler.
pub fn push(&mut self, item: T) -> Result<Handle<T>, Error> {
    let index = u32::try_from(self.items.len())
        .ok()
        .filter(|&i| i < u32::MAX)
        .ok_or_else(|| Error::TooManyObjects {
            type_name: core::any::type_name::<T>(),
        })?;
    self.items.push(item);
    Ok(Handle::new(index))
}

pub fn get(&self, handle: Handle<T>) -> Option<&T> {
    self.items.get(usize::from(handle))
}

The new object's handle is the arena's current length: the first object gets 0, the second 1. push reads as a chain of small steps on an Option: convert the length to a u32 (try_from fails if it doesn't fit), keep it only if it is below u32::MAX, and otherwise turn the missing value into an error naming the type. The last ? returns that error early. get is Vec::get, which returns None past the end instead of panicking.

The rest of the interface is new, as_slice (every object in handle order: what a SceneView will borrow), len and is_empty. There is no way to remove or replace an object, so a handle stays valid for the arena's whole life.

In umbra-geometry, Handle<T> implements Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash and Debug by hand. Deriving them would demand that T implement them too, which makes no sense for a number. The marker is PhantomData<fn() -> T> rather than PhantomData<T>, which keeps a handle Send and Sync whatever T is.

Why does Arena exist when the Scene has no arena yet? The camera, the filter and the sampler are one per Render Job and are held by value (ADR 0008), so a camera-only Scene has nothing to put in an arena. The type was written ahead, with its tests, so that Shapes can use it as soon as they arrive (README, “Per-type arenas before their first type”).

Rules used here
only a SceneBuilder pushes
Handles are minted in one place. A built Scene's arenas are immutable and per-sample code reads them as slices (the doc comment of Arena; ADR 0008).
Handle::new(index) is public
A handle is not proof of existence. Anyone can make Handle::new(7); that is why get checks and returns an Option. The crate's test does exactly this.
usize::from(handle)
A lossless conversion. A u32 always fits a usize on Umbra's targets; From is the idiomatic Rust way to say “this can't fail”.
11umbra-scene · scene.rs · Scene, Scene::view · ADR 0014

Inside Scene and its view

In plain wordsThe Scene is a plain struct of six private fields. Most are small values. One, the filter, owns its tables on the heap. Another, the sensor, refers to colour curves that are built into the program. The view is a second, lighter struct that points at three of those fields.
pub struct Scene {
    resolution: Point2i,
    camera: CameraKind,
    filter: FilterKind<Vec<f32>>,
    sensor: PixelSensor<'static>,
    randomize: RandomizeStrategy,
    integrator: VolPathIntegrator,
}

The fields are private. Outside the crate, a Scene can only be made by SceneBuilder::build and read through four methods: view, full_resolution (“both sides are positive”, which build guarantees), randomize_strategy and integrator. Scene derives Clone: a copy per NUMA node inside one Worker remains possible later (ADR 0008, arc42 §8.14).

FilterKind<S> is generic over its storage S. The Scene picks Vec<f32>, owned memory; the view gets &[f32], borrowed slices. Same filter code, two kinds of storage. The sensor's lifetime is 'static because the CIE 1931 colour-matching curves are constant tables compiled into the program.

One part of the Scene's job is not in this struct: the sampler's seed and its number of Pixel Samples. Those are Render Job Options. The digit permutations that a seed chooses are computed by umbra-cpu's Renderer, once per Render Job.

Rules used here
std crate, outside the core
Owns, so may allocate. The owning Scene, the builder and (later) BVH construction live outside the seven no_std core crates (ADR 0014, ADR 0015).
umbra-integrators with features = ["serde"]
Ready for replication. umbra-scene turns on the core's serde feature (arc42 §5.2); the derives come with replication.
no Film in the Scene
Only the resolution. The Film lives in umbra-render; the other RGBFilm parameters arrive with #84.
12umbra-scene · options.rs · RenderJobOptions, Seed

Inside RenderJobOptions and Seed

In plain wordsTwo small Rust tricks keep the options safe. Sizes use a number type that can't hold zero, so “zero samples” or “Tiles of size zero” can't even be written down. And the seed gets its own named type, so it can't be mixed up with any other number.
pub struct Seed(pub i32);

impl From<Seed> for u32 {
    fn from(seed: Seed) -> Self {
        seed.0.cast_unsigned()
    }
}

pub struct RenderJobOptions {
    pub seed: Seed,
    pub tile_size: NonZeroU32,
    pub spp_per_pass: NonZeroU32,
    pub spp: NonZeroU32,
}

Seed is a newtype: a struct around a single value, which gives that value its own type. A function that takes a Seed can't be handed a Tile size by mistake. Its conversion is a From implementation, so the renderer writes options.seed.into() where a u32 is wanted.

The sizes are NonZeroU32. A zero Tile size would mean dividing the image by zero; zero Pixel Samples would mean an image with nothing in it. With this type, the check happens once, wherever an option is made, and code that reads the options never has to check again. tile_size.get() gives the plain u32 back.

Default gives seed 0, 32 × 32 Tiles and Passes of 64 Pixel Samples (arc42 §8.8), and pbrt-v4's default of 16 Pixel Samples per pixel. The expect("32 is not zero") calls inside it can never fail; they exist because NonZeroU32::new returns an Option and the reason it can't be None deserves to be written down.

The fields are public and the struct is Copy: options are a plain bundle of numbers, with no rule linking one field to another. Command-line overrides such as --spp are not implemented yet; arc42 §5.3 assigns them to the umbra binary, which will apply them on top of what the Scene File gives.

Rules used here
NonZeroU32 for every size
Make the bad value unrepresentable. No zero Tiles, Passes or sample counts can exist.
Seed(pub i32)
A newtype for an identifier. pbrt-v4's --seed is an int, so Umbra accepts the same values.
Workers are not an option
Options never include the machine list. Which Workers join is not a Render Job Option and never changes the Film (ADR 0003 as amended, arc42 §8.2).
13umbra-scene · tests/umbra_scene

Tests

In plain wordsThe crate's tests check two things through its public interface: that an arena gives every object its own handle and gives nothing for a bad handle, and that build accepts the defaults and refuses the two kinds of bad settings. Rendering a Scene is tested where rendering lives, in umbra-render.
  • arena.rs: handles are minted in order, each gives back its own object, slices come in handle order, and a handle past the end gets None.
  • builder.rs: the defaults build to pbrt-v4's 1280 × 720 film; a film with a zero or negative side, and a filter radius of 0.01, are refused with the exact error expected.
  • Elsewhere, Scenes built with SceneBuilder feed umbra-render's and umbra-cpu's tests and the counting-allocator test in the umbra crate (section 4).

Run them with cargo nextest run -p umbra-scene. The README's example is also a doc test, since lib.rs includes the README as the crate's documentation.

Not here yet

In plain wordsToday's Scene describes a camera looking at nothing. The crate is shaped for what comes next: arenas waiting for Shapes, a builder waiting for more directives, a Scene waiting to be sent over the network.
  • Shapes, lights and materials, each in its own arena, from #79 on. Arc42 §5.3 sketches one add_* method per arena on the builder (for example add_shape), which is where handles will be minted.
  • The BVH, built deterministically inside build (ADR 0004), with a check that its depth fits the fixed traversal stack.
  • The other RGBFilm parameters (crop window, sensor, ISO, white balance, …) with #84.
  • Serialising a Scene for replication to remote Workers (section 6).
  • The parser as the first real adapter in front of SceneBuilder, and command-line overrides of the Render Job Options.
  • pbrt-v4's default sampler, zsobol; until then the builder defaults to halton.
