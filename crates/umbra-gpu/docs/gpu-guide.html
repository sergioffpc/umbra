Umbra GPU Guide

A graphics card can follow thousands of rays at the same time. umbra-gpu is the part of Umbra that talks to the card. It loads NVIDIA's ray-tracing library, OptiX, hands it the GPU programs, sends rays over, and reads the answers back. Today it traces one triangle and one sphere, as a first test of the whole path, and holds the GPU's Renderer, which has the CPU's shape but cannot be built until the GPU renders a Scene. This guide explains each idea in pictures first and code second. It assumes no background in GPUs.

Part I · Concepts

How a GPU traces rays

What a GPU is, why it suits ray tracing, how NVIDIA's OptiX library organises the work, and how Rust code can call a library written in C without losing its safety.

0background · used by every section

The words, in pictures

In plain wordsA GPU is a second computer inside your computer. It has its own memory and runs its own programs. Your normal program on the CPU is the host; the GPU is the device. The host prepares work, copies it over, tells the GPU to start, and copies the answers back. The four pictures below cover every word the rest of the guide uses.

CPU and GPU

The CPU (central processing unit) runs your program. It has a few powerful cores, each good at complicated, branching work. The GPU (graphics processing unit) has thousands of simple cores that are best when they all do the same kind of work on different data. NVIDIA GPUs also have RT cores: small circuits built only to test rays against boxes and triangles.

Host and device

The host is the CPU side: your Rust program and the computer's RAM. The device is the GPU side: the GPU and its own memory (VRAM). A number in RAM is invisible to the GPU until the host copies it over. CUDA is NVIDIA's software for doing that: allocate GPU memory, copy, start programs. Umbra reaches CUDA through the Rust crate cudarc.

Kernel, thread, warp, launch

A kernel is a program written to run on the GPU. Starting it is a launch. A launch runs the same kernel many times at once; each copy is a thread, and each thread gets its own number, its launch index. Umbra gives thread i ray i. The GPU moves threads in bundles of 32 called warps: the 32 threads of a warp execute each instruction together.

PTX, the driver, OptiX

PTX is a text format for GPU programs, a kind of portable assembly language. It is not tied to one GPU model. The NVIDIA driver, installed on the machine, turns PTX into the real machine code of whatever GPU is there. OptiX is NVIDIA's ray-tracing library. It ships inside the driver, as libnvoptix.so.1, and uses the RT cores.

Why a GPU for ray tracing

In plain wordsEvery ray is its own little question: “what does this ray hit first?” The answer for one ray never depends on another. That is exactly the kind of work a GPU loves: give each of thousands of threads one ray, and let them all work at once. The catch: threads march in groups of 32. When some rays of a group hit and others miss, the group has to do both kinds of work, one after the other.

A CPU core runs one ray at a time very fast. A GPU runs each ray slower, but tens of thousands at once, and its RT cores search the geometry in hardware. For a ray tracer, which may follow billions of rays per image, the GPU wins by sheer numbers. ADR 0026 therefore makes every GPU a Worker of its own from the first milestone, rendering beside the CPU Workers.

In umbra-gpu today, a launch has one thread per ray. Thread i reads ray i, traces it, and writes hit i. No thread needs another's result, so they never wait on each other.

Maths used here
warps = ⌈N ⁄ 32⌉
How many warps a launch needs. ⌈ ⌉ means “round up”: 1 000 rays need 32 warps, not 31.25. N is the launch width, count in trace_launch.
idle lanes = 32 · ⌈N ⁄ 32⌉ − N
Wasted lanes in the last warp. At most 31, so it only matters for tiny launches.
warp of thread i = ⌊i ⁄ 32⌋,   lane = i mod 32
Where a thread sits. ⌊ ⌋ rounds down; mod is the remainder. Thread 70 is lane 6 of warp 2.
2umbra-gpu · records.rs · DeviceRepr · ADR 0028

Two memories, copies between

In plain wordsThe GPU cannot read the CPU's memory. So the host packs data into plain records, copies the bytes to the GPU, and later copies the answers back. The copy does not translate anything: the bytes land exactly as they were. That only works if both sides agree, to the byte, on where every field sits. And a record must never hold a CPU address: on the GPU it would point at nothing.

Rust normally lets the compiler arrange a struct's fields however it likes. That is no good when another program, compiled separately, reads the same bytes. So every shared type is #[repr(C)]: fields in written order, laid out by C's rules. And every one carries compile-time assertions on its size and on each field's offset. If a field ever moved, the build would fail before any wrong byte reached a GPU.

records.rs marks five types with DeviceRepr through a small macro, device_repr!: DeviceCopy<LaunchParams>, DeviceCopy<RayRecord>, DeviceCopy<HitRecord>, SbtRecord<()> and SbtRecord<Sphere>, plus DeviceCopy<MathParams> with the math-program feature. DeviceCopy<T> is a #[repr(transparent)] wrapper with T's layout: the shared records belong to umbra-gpu-programs and DeviceRepr to cudarc, and Rust lets a crate implement another crate's trait only for a type of its own (section 10). The marker is an unsafe impl: the compiler cannot check the promise, so the code states it in a // SAFETY: comment.

// SAFETY: a `#[repr(C)]` type of `f32`s, integers and byte arrays,
// or a transparent wrapper of one, with no pointer to host memory,
// whose layout the device shares ...
#[expect(unsafe_code, reason = "copying records to and from the GPU (ADR 0007, ADR 0028)")]
unsafe impl DeviceRepr for $t {}

The data that comes back from the GPU could, in principle, be any bits. So the host never trusts it blindly. A HitRecord stores its kind as a plain u32, and the host converts it with umbra-gpu-programs' HitKind::try_from, which refuses any number other than 0, 1 or 2 (section 13).

Rules used here
#[repr(C)] + size_of / offset_of asserted
Fixed layout. umbra-gpu-programs' launch.rs is compiled for the host and for the GPU, and its const _: () = { assert!(…) } blocks run in both builds, for x86_64 and for nvptx64 (section 10).
no host pointers inside a record
Copyable. Records hold f32s, integers, byte arrays and device addresses only. ADR 0028 and arc42 §8.12 state the same rule for every future Scene arena type.
read back: any bits → validated value
Untrusted input. Of the copied types, the host reads back only HitRecord, which has no padding, and checks its kind before using it.
3umbra-gpu · optix.rs · GasInput, DeviceContext::gas_sizes, build_gas · tracer.rs

Acceleration structures

In plain wordsTesting every ray against every shape would be far too slow. So shapes are sorted into a tree of boxes: a big box around everything, smaller boxes inside it, and shapes at the bottom. A ray that misses a box skips everything inside. OptiX builds this tree for you, once; it is called a geometry acceleration structure, or GAS. Triangles are tested by the RT cores themselves. Any other shape, such as Umbra's sphere, gives OptiX only a box, and a small program of yours finishes the test.

Building a GAS takes two OptiX calls, wrapped by DeviceContext. First gas_sizes (optixAccelComputeMemoryUsage) asks how much GPU memory the build needs: room for the result, and scratch room for the work. Then build_gas (optixAccelBuild) builds into those buffers and returns the traversable handle. In tracer.rs, build_gas_from_input allocates both buffers, runs the build, waits for the stream, and keeps only the result; the scratch buffer is freed.

let sizes = context.gas_sizes(input)?;
let temp = stream.alloc_zeros::<u8>(sizes.temp)?;
let mut buffer = stream.alloc_zeros::<u8>(sizes.output)?;
// ... context.build_gas(stream, input, (temp, ...), (output, ...))?
stream.synchronize()?;

The build options never change: BUILD_FLAG_PREFER_FAST_TRACE (the tree is built once and traced many times) and GEOMETRY_FLAG_DISABLE_ANYHIT (Umbra has no any-hit program, section 4). The Gas struct keeps three things alive together: the handle, the GAS buffer, and the vertices or box it was built from.

Maths used here
p(t) = o + t · d
A ray. Start at the origin o, walk t times the direction d. OptiX looks for hits with 0 ≤ t ≤ tmax; the programs use tmax = f32::MAX.
box = [c − r, c + r] on each axis
The sphere's box. From sphere.bounds(): for the test sphere, centre (0, 0, 10) and radius 2, it runs from (−2, −2, 8) to (2, 2, 12).
tnear = max over axes of min(tlo, thi)
tfar = min over axes of max(tlo, thi)
tlo = (lo − o) ⁄ d,   thi = (hi − o) ⁄ d
Box test, the “slab” method. On each axis the ray is between the box's two walls for a stretch of t. It is inside the box where all stretches overlap, so it enters the box when tnear ≤ tfar. The RT cores do this; the figure below copies it.
|o + t d − c|² = r²
a t² + b t + c′ = 0,   t = (−b ± √(b² − 4ac′)) ⁄ 2a
Ray against sphere. A point is on the sphere when its distance from the centre is r. That gives a quadratic in t, with a = d·d, b = 2 (o − c)·d, c′ = |o − c|² − r². No real root: miss. The core's Sphere::intersect solves it the careful pbrt-v4 way, with error bounds; see the Umbra Math Guide for the numerics.

OptiX programs and the pipeline

In plain wordsOptiX does not take one big GPU program. It takes several small ones, each with a job, and calls them for you at the right moments. One program makes a ray and asks OptiX to trace it. While OptiX searches, it may call an intersection program to test a custom shape. When the search is over, it calls the closest-hit program if something was hit, or the miss program if not. Those two leave their answer in the ray's payload, a couple of numbers that travel back to the first program.
pub(crate) enum Programs {
    Raygen(&'static CStr),
    Miss(&'static CStr),
    Hitgroup { closest_hit: &'static CStr, intersection: Option<&'static CStr> },
}

The intersection program is an Option: None for the triangle's hit group, Some(c"__intersection__sphere") for the sphere's. Both hit groups share the same closest-hit program; it asks OptiX which kind of primitive it was called for.

A few settings must agree between the Module and the Pipeline, so one function, pipeline_compile_options, makes them for both: one GAS traced directly (TRAVERSABLE_GRAPH_FLAG_ALLOW_SINGLE_GAS), two payload values, triangles and custom primitives, and the name of the launch-parameter variable, c"params" (LAUNCH_PARAMS_VARIABLE). The pipeline's link options set max_trace_depth: 1: only the ray-generation program traces; the hit and miss programs never start rays of their own.

When a compile fails, OptiX writes an explanation into a text buffer. Every compiling call hands it a 4 096-byte log (LOG_SIZE), and the error carries that text back to the user (section 13).

Rules used here
payload = [ t as bits, HitKind as u32 ]
Two 32-bit values per ray. A payload slot holds a u32, so the closest-hit program stores t with f32::to_bits and the ray-generation program gets it back with f32::from_bits: the same 32 bits, read two ways. It starts as [0, Miss].
num_payload_values = 2
num_attribute_values = 2
max_trace_depth = 1
Pipeline limits. Two payload values, OptiX's minimum of two attribute values (which triangles use for their barycentric coordinates), and tracing from ray generation only.
Validation::All if debug_assertions
Checked in debug builds. Tracer::new turns on OptiX's validation mode in builds with debug assertions: slower, but OptiX then reports misuse. Release builds use Validation::Off.

The shader binding table

In plain wordsThe pipeline knows the programs, but not which one to call for which shape, nor with which data. The shader binding table (SBT) answers that. It is a set of records in GPU memory. Each record has a 32-byte header, an opaque ticket that OptiX writes and that names a program group, followed by whatever data that program should read. Umbra's sphere record carries the whole Sphere, so the intersection program knows where the sphere is.

Why one table per geometry? A hit group table is an array: OptiX finds record k at base + k × stride, so all its records must have the same size. The triangle's hit group record is 32 bytes and the sphere's 304. Rather than pad the small one, Umbra keeps two separate hit group records and builds a fresh table for each launch, pointing at the one hit group of the geometry being traced (Tracer::binding_table). Since each launch traces exactly one GAS with one primitive, OptiX only ever needs record 0.

let (hitgroup, hitgroup_stride) = match geometry {
    Geometry::Triangle => (self.triangle_hitgroup.device_ptr(&self.stream).0, size_of::<SbtRecord<()>>()),
    Geometry::Sphere => (self.sphere_hitgroup.device_ptr(&self.stream).0, size_of::<SbtRecord<Sphere>>()),
};

The records themselves are written once, in Tracer::new, by the helper record: pack the header, attach the data, copy the record to the GPU with clone_htod.

Maths used here
k = sbt-offset + sbt-stride × geometry index + instance offset
Which hit group record. OptiX's rule. The programs trace with offset 0 and stride 1; the GAS has one build input with one SBT record, so its geometry index is 0; there are no instances. So k = 0.
address = hitgroup + k × hitgroup_stride
Where record k is. With k = 0 it is simply hitgroup. The stride still has to be right, and is 32 or 304. stride() converts it to the u32 OptiX takes.
304 = 32 + 272,   304 mod 16 = 0
Sizes and alignment. Header plus Sphere; OptiX wants records 16-byte aligned (OPTIX_SBT_RECORD_ALIGNMENT), which align(16) gives.
6umbra-gpu · optix.rs Api · optix/ffi.rs FunctionTable · ADR 0007

How Rust talks to C safely

In plain wordsOptiX is a C library. Rust can call C functions, but the Rust compiler cannot check what happens on the other side, so every such call sits in an unsafe block: a spot where the programmer promises the rules are kept. Umbra keeps those spots tiny. Each OptiX call gets one small Rust function with a safe signature; inside it, one unsafe line with a comment saying why it is fine. Everything above that layer is ordinary, checked Rust.

How OptiX is found. Umbra does not link to OptiX when it is built. At run time, Api::load opens the driver's library with the libloading crate and looks up the one function it exports, optixQueryFunctionTable. Calling that with ABI version 105 fills a table of 52 function pointers: OptiX 9.0's whole host API. From then on every OptiX call goes through a slot of that table.

Structs written by hand. OptiX's calls take C structs: options, build inputs, the SBT. NVIDIA's header files that define them are under a proprietary licence, so Umbra copies none of them (ADR 0026, NOTICE). Instead optix/ffi.rs writes each struct from the facts of the ABI: the size, and the offset of every member Umbra sets. Members Umbra leaves at zero are lumped into zeroed arrays of the right size, such as unused: [u64; 21] in BuildInputTriangleArray. Each struct ends with assertions like these:

const _: () = {
    assert!(size_of::<ShaderBindingTable>() == 64, "64 bytes");
    assert!(offset_of!(ShaderBindingTable, miss_record_base) == 16, "byte 16");
    assert!(offset_of!(ShaderBindingTable, hitgroup_record_base) == 32, "byte 32");
    assert!(offset_of!(ShaderBindingTable, callables) == 48, "byte 48");
};

One safe wrapper per call. Here is the whole shape of one, ProgramGroup::record_header. A missing slot becomes an error instead of a crash (function turns None into Error::OptixFunction), and any non-zero result code becomes an error with OptiX's own name for it (Api::check):

let pack = function(api.table.sbt_record_pack_header, "optixSbtRecordPackHeader")?;
let mut header = [0; SBT_RECORD_HEADER_SIZE];
// SAFETY: `header` is `OPTIX_SBT_RECORD_HEADER_SIZE` writable bytes.
let result = unsafe { pack(self.handle, header.as_mut_ptr().cast()) };
api.check("optixSbtRecordPackHeader", result, &[])?;
Ok(header)

Cleaning up. Every OptiX object must be destroyed, and only after everything made from it. Each wrapper owns its OptiX handle and destroys it in Drop, and holds an Rc (a shared, counted reference) to the object it came from, so the parent outlives it (section 11).

Maths used here
offset of slot k = 8 · k bytes
table size = 52 × 8 = 416 bytes
Where a function pointer sits. A function pointer is 8 bytes on a 64-bit machine, and the slots are packed in order. launch is slot 41, at byte 328.
OptixResult: 0 = success, else an error code
How C reports failure. No exceptions in C: every call returns a number. Api::check turns non-zero into Error::Optix, asking optixGetErrorName (slot 0) for a readable name such as OPTIX_ERROR_INVALID_VALUE.
one unsafe operation per block, one // SAFETY: each
ADR 0007's rules. The expect(unsafe_code) sits on the narrowest item possible, the single function. Lints enforce the comments.
7umbra-gpu · build.rs · ADR 0028, ADR 0014

From Rust to PTX

In plain wordsThe GPU programs are written in Rust, in a separate crate, umbra-gpu-programs. Before umbra-gpu itself compiles, its build script runs a second, nested Rust compile of those programs for the GPU, which produces a PTX text file. That text is pasted into umbra-gpu as a string constant. Nothing from NVIDIA is needed for this step, except one optional file of maths functions, libdevice.

libdevice is CUDA's library of maths functions for the GPU (sinf, expf, powf, …) in LLVM bitcode form. umbra-math's GPU backend calls them. find_libdevice looks for it at UMBRA_LIBDEVICE, then under CUDA_PATH, CUDA_HOME and /usr/local/cuda. When found, the toolchain links the functions straight into the PTX. When not found, as on CI, which has no CUDA, the programs still compile, but every maths function stays an unresolved .extern .func, and the build prints a warning. Such PTX cannot run, so Tracer::new checks the text first:

if PTX.contains(".extern") {
    return Err(Error::UnlinkedPtx);
}

The nested build drops the outer build's RUSTFLAGS and compiler wrappers: those are for the host CPU (CI sets -C target-cpu=x86-64-v3, which the GPU target does not know). It also leaves the GPU target's default CPU, sm_70, alone; the driver compiles sm_70 PTX for any newer GPU. With umbra-gpu's math-program feature on, it passes --features math-program to the programs too; the feature also turns on umbra-gpu-programs/math-program in Cargo.toml, so the host sees the math program's layout.

Why --crate-type cdylib. In its own manifest, umbra-gpu-programs' library is an ordinary rlib, which is what umbra-gpu needs to use its layout (section 10). The nested cargo rustc --lib --crate-type cdylib asks for a cdylib instead, which the nvptx64 target links into one PTX module, umbra_gpu_programs.ptx.

Rules used here
libdevice linked ⇒ no ".extern .func" in the PTX
Checked twice. build.rs fails the build if libdevice was linked and an .extern .func is still there; Tracer::new refuses PTX with any .extern.
env removed: RUSTFLAGS, CARGO_ENCODED_RUSTFLAGS, CARGO_BUILD_RUSTFLAGS, RUSTC_WRAPPER, RUSTC_WORKSPACE_WRAPPER, CARGO_TARGET_DIR, CARGO_BUILD_TARGET
Host settings stay on the host. programs_build builds the command and strips these.
rerun when a program source, Cargo.lock or UMBRA_LIBDEVICE / CUDA_PATH / CUDA_HOME changes
Rebuilt when it must be. rerun_if_sources_change reads the dep-info file of the nested build, which lists every source file it used, the core crates' included.

How the crate is built

umbra-gpu is a std crate, outside the no_std core. It depends on umbra-geometry and umbra-math, on umbra-gpu-programs for the layout it shares with the GPU, on umbra-render and umbra-scene for the Renderer's Work Units and Scene, on cudarc for the CUDA driver and on libloading for OptiX; its build script also compiles umbra-gpu-programs to PTX (arc42 §5.1, ADR 0033). Today it holds the tracer bullet of #126: one triangle and one sphere, traced through OptiX and read back on the host. Its Renderer has the shape of the CPU's, but no wavefront behind it yet.

9umbra-gpu · tracer.rs · Tracer::trace, trace_launch, launch

One trace call, step by step

In plain wordsA call to trace is a round trip. Pack the rays and copy them to the GPU. Make room there for the answers. Tell OptiX what to trace and where everything is. Start one thread per ray and wait. Copy the answers back and turn each one into a Rust value. The figure below lets you walk through it one step at a time.
pub fn trace(&self, geometry: Geometry, rays: &[Ray]) -> Result<Vec<Option<Hit>>, Error> {
    if rays.is_empty() { return Ok(Vec::new()); }
    let count = u32::try_from(rays.len()).map_err(|_| Error::TooMany("rays"))?;
    let records: Vec<_> = rays.iter().map(|ray| DeviceCopy(RayRecord::from(ray))).collect();
    let ray_buffer = self.stream.clone_htod(&records)?;
    let mut hit_buffer = self.stream.clone_htod(&vec![DeviceCopy(HitRecord::default()); rays.len()])?;
    self.trace_launch(geometry, count, &ray_buffer, &mut hit_buffer)?;
    self.stream.clone_dtoh(&hit_buffer)?.into_iter().map(DeviceCopy::hit).collect()
}

Note the last line. DeviceCopy<HitRecord>::hit returns Result<Option<Hit>, Error>, and collecting an iterator of Results into a Result<Vec<…>> stops at the first error. So one bad hit kind fails the whole call rather than slipping through.

launch is generic over the parameter type P: DeviceRepr, so the same function serves DeviceCopy<LaunchParams> for a trace and DeviceCopy<MathParams> for a math launch. It copies the parameters to the GPU, calls Pipeline::launch with width threads, and waits with stream.synchronize(). A buffer's device address comes from cudarc's device_ptr or device_ptr_mut, which return the address together with a guard value. trace_launch keeps its guards in named variables (_rays_read, _hits_written) until launch has synchronised the stream, so the buffers stay marked as in use for the whole launch.

Maths used here
bytes in = 24 N + 8 N + 32,   bytes out = 8 N
Traffic per call. N ray records of 24 bytes, N empty hit records of 8 bytes, one 32-byte LaunchParams; then N hit records back. 1 024 rays move about 33 KB in and 8 KB out.
N ≤ u32::MAX = 4 294 967 295
Launch width limit. OptiX takes the width as a u32; more rays than that is Error::TooMany("rays"). An empty slice returns an empty Vec without touching the GPU.
10umbra-gpu · umbra-gpu-programs src/launch.rs · records.rs DeviceCopy<T> · ADR 0033

The layout shared with umbra-gpu-programs

In plain wordsThe host writes records and the GPU reads them, and both are compiled separately, for different machines. The safest way to make them agree is to have only one description. So the file launch.rs lives in umbra-gpu-programs, which compiles for the host as well as for the GPU, and umbra-gpu depends on it like on any other crate. One file, two compilers, the same bytes.
# Cargo.toml: the layout the host shares with the device (ADR 0033); its programs are
# built for `nvptx64` by the build script, not by this dependency.
umbra-gpu-programs = { workspace = true }

// records.rs
#[derive(Debug, Clone, Copy, Default)]
#[repr(transparent)]
pub(crate) struct DeviceCopy<T>(pub(crate) T);

On the host, umbra-gpu-programs holds only launch.rs (and, with the feature, math_launch.rs), whose types are pub and re-exported at its root; its programs, its OptiX bindings and its unstable features exist only in the nvptx64 build. The layout depends on core and umbra-geometry, so it compiles in both worlds, and it brings the conversion both sides agree on: From<&Ray> for RayRecord, which copies the six floats.

What only the host needs stays in records.rs. cudarc copies a type only if it implements DeviceRepr, and Rust's orphan rule forbids umbra-gpu to implement cudarc's trait for umbra-gpu-programs' types. So each record crosses the bus wrapped in DeviceCopy<T>, whose #[repr(transparent)] gives it exactly T's layout, and the promise is made for the wrapper (section 2). DeviceCopy<HitRecord>::hit turns a record into Option<Hit>, matching its kind against the HitKind discriminants and failing with Error::HitKind on any other number.

Where the line is. umbra-gpu-programs owns everything that runs on the GPU: the five entry points, the OptiX device calls in inline PTX, the panic handler. umbra-gpu owns everything on the CPU: loading, compiling, building, launching, copying. They meet only in the shared layout and in the entry-point names. umbra-gpu uses umbra-gpu-programs twice: as a dependency for the layout, and from its build script, which compiles it to PTX.

Maths used here
offset(count) = 8 + 8 + 8 = 24
size = round up(24 + 4, to 8) = 32
Why LaunchParams has padding. A struct's size is rounded up to its largest alignment, here 8 (the u64s), so 28 becomes 32. The device's params variable is sized from size_of::<LaunchParams>().
MathParams = 24 bytes ≤ 32
One variable, two uses. A math launch puts MathParams into the same params variable, which an assertion proves is big enough.
kind ∈ {0, 1, 2}, else Error::HitKind(kind)
Checking the way back. DeviceCopy::hit searches [Miss, Triangle, Sphere] for the number; any other is Error::HitKind.
11umbra-gpu · README.md “Design decisions” · ADR 0026, ADR 0028

Design decisions

In plain wordsFour choices shape the crate. It needs nothing from NVIDIA to build, only to run. It compiles the GPU programs itself, in a nested build. It keeps one small table per shape instead of one shared table. And it lets Rust's reference counting decide the order in which OptiX objects are destroyed.

Nothing from NVIDIA at build time

cudarc loads libcuda.so.1 and libloading loads libnvoptix.so.1 when the program runs, both from the installed NVIDIA driver. So the crate builds on machines with no GPU and no CUDA, CI included, and the release image ships nothing from NVIDIA (ADR 0026). In a container, OptiX needs the NVIDIA Container Toolkit's graphics capability: NVIDIA_DRIVER_CAPABILITIES=compute,graphics (arc42 §7). Without it, Api::load fails with Error::OptixLibrary.

The programs built by a nested cargo

See section 7. The rejected alternatives are in ADR 0028: Rust-CUDA (an external code generator long unmaintained), hand-written CUDA C++ (a second implementation, sharing no code with the core), and putting the device code in a module of this crate (mixing std and no_std). ADR 0033 adds that this crate's build script would then compile its own crate for nvptx64, a build that recurses into itself.

One Renderer per Render Device

Renderer has the shape of umbra-cpu's: new(&Scene, &RenderJobOptions), then render(WorkUnit, &Cancellation) -> Rendered, over umbra-render's device-neutral contract (ADR 0033). umbra-cluster chooses between the two by the Worker's Render Device. Until the wavefront arrives, new returns Error::NoRenderer for every Scene, and the type holds an Infallible, so no value of it exists and render is match self.unbuilt {}.

One shader binding table per geometry

See section 5. Each launch traces one GAS directly, with a table holding that geometry's one hit group record and the shared ray-generation and miss records.

Field order as drop order

pub struct Tracer {
    // Declared first, so that it drops before the CUDA memory below and the
    // context the stream holds.
    pipeline: Pipeline,
    raygen: CudaSlice<SbtRecord<()>>,
    ...
    sphere_hitgroup: CudaSlice<SbtRecord<Sphere>>,
    stream: Arc<CudaStream>,
}

Rust drops a struct's fields in the order they are written. The pipeline goes first, while the CUDA context it was built on still exists; the stream, which holds that context, goes last.

A math program, for the tests only

Checking the GPU's maths needs the GPU to run maths functions on chosen inputs. Rather than a second pipeline, a second ray-generation program, __raygen__math, joins the same pipeline when the math-program feature is on. A math launch selects it by its SBT record and puts MathParams in the same params variable. Production builds contain none of it.

Rules used here
child holds Rc<parent>
Destruction order by construction. Module → DeviceContext; ProgramGroup → Module; Pipeline → context and every group; DeviceContext → Api, which keeps the library loaded while its function pointers are in use.
no OptiX header copied
Licence. Bindings hold only facts of the ABI: slot order, struct layout, constants (ADR 0026, NOTICE). Building needs no OptiX SDK.
driver ≥ OptiX 9.0 (ABI 105)
Run-time requirement. An older driver lacks the table or a slot: Error::Optix from optixQueryFunctionTable, or Error::OptixFunction.

The unsafe and FFI boundaries

In plain wordsUmbra forbids unsafe code by default. The GPU path is a declared exception, because there is no safe way to reach a GPU. The exception is fenced in: you can find every spot by searching for expect(unsafe_code, each spot does one dangerous thing, and each says in writing why it is fine. Since no memory checker runs on the GPU, the GPU tests are what verify these promises.
wherewhat is unsafewhy it is fine (from its SAFETY comment)
Api::loadLibrary::new, library.get, the query callthe driver's library has no preconditions on load; the symbol has the type the ABI fixes; the table passed is writable and of the size given
Api::error_namecall optixGetErrorName; read its C stringit takes any code and returns a static NUL-terminated string; null is checked first
DeviceContext::new, Dropcreate, destroythe CUDA context outlives the OptiX one; destroyed once, after every object holding an Rc of it

ProgramGroup::new, record_header, Dropcreate, pack a header, destroyone descriptor whose names outlive the call; the header buffer is exactly 32 writable bytes
Pipeline::new, launch, Droplink, launch, destroythe options and groups are valid for the call; for a launch, the parameters and records stay alive until the stream is synchronised
DeviceContext::gas_sizes, build_gasmeasure, build a GASthe host arrays the build input points into (boxed, kept in _keep) outlive the call; buffers are the sizes OptiX asked for
records.rs device_repr!unsafe impl DeviceRepr#[repr(C)] plain data, no host pointers, layout shared and asserted

One subtle case is worth a look. An OptiX build input does not contain the buffer address directly; it points at a small host array that holds it. build_input puts that array in a Box, so it has a fixed address even when the build input is moved, and returns the box beside the input. The caller keeps it in a variable named _keep until the OptiX call returns.

let flags = &raw const arrays.1;

14umbra-gpu · tests/gpu · .config/nextest.toml · ADR 0026

The GPU tests

In plain wordsThe GPU's answers are checked against the CPU's. Rays are traced through OptiX, and the same rays are intersected by the core's own code on the CPU; the distances must agree to a few units in the last digit. A second set of tests runs maths functions on the GPU over millions of inputs and compares them with the CPU's maths library. CI has no GPU, so these tests are a separate test program, run by hand on the machine with the GPU.
  • tests/gpu/optix.rs: the two tracing tests above, through the public API only (Tracer, Geometry, Hit).
  • tests/gpu/libdevice.rs: every libdevice function that umbra-math's GPU backend calls, evaluated with Tracer::evaluate on about four million f32 inputs (every 1 021st bit pattern, plus extra subnormals, plus special values), and compared with glibc on the CPU within the bound umbra-math documents.
  • The test binary is named gpu (tests/gpu/main.rs). nextest's default profile, and those inheriting from it such as ci, filter out binary(=gpu); cargo nextest run --profile gpu runs only it, on the P620. Add --no-capture to see the measured errors.

Maths used here
close(a, b) ⇔ |a − b| ≤ 4 ε · max(|a|, |b|, 1)
“Agree to a few ULP.” ε is f32::EPSILON, about 1.19 × 10−7, the gap between 1 and the next f32. For t ≈ 8 the allowed difference is about 3.8 × 10−6. close in tests/gpu/optix.rs.
ULP distance(a, b) = |ordinal(a) − ordinal(b)|
Counting floats between two results. Each f32 gets a whole number, its position in the ordered list of all f32s; the distance is how many steps apart they are. 0 ULP means bit-identical. A NaN against a number counts as farther than any distance.
fma(2⁻¹⁴⁹, 1, 0) = 2⁻¹⁴⁹, not 0
Subnormals survive. the_primitives_keep_subnormals checks that tiny numbers are not “flushed to zero”, which shows the GPU code was built with flush-to-zero off.
15umbra-gpu · roadmap · arc42 §4

Not here yet

In plain wordsToday the crate is a test bench: one triangle, one sphere, rays in, hits out. It proves the riskiest parts work: the toolchain, OptiX from Rust, and the shared layout. The real GPU renderer is built on top of it, feature by feature, in later issues.
  • The SceneView upload: copying the Scene's arenas to the GPU byte for byte, which their #[repr(C)] layout allows (ADR 0028, arc42 §8.12). Arrives with #127.
  • The wavefront queues: structure-of-arrays queues between GPU stages, one kernel per stage, as pbrt-v4's GPU renderer does. Also #127.
  • A Renderer that renders: its shape is here, its wavefront arrives with #127. The GPU Local Worker in a child process of the Coordinator comes with #128.
  • More shapes: each new Shape becomes an OptiX custom intersection program that calls the core, as the sphere does; triangles stay in hardware (arc42 §8.12).
Rules used here
statistical equality with the CPU
What a GPU Worker promises. Not the same bits as the CPU: the GPU has its own maths functions and summation order (ADR 0026). The owner compares images by eye (ADR 0031).
the core works on values
No queues in the core. Core functions take and return Copy values; the GPU driver owns the queues (ADR 0028).
